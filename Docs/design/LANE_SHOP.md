# 레인 상점 공용 구조 (ILaneShop)

PM 지시로 코드를 옮기기 전에, `SupportShop`(도움소)·`GamblingShop`(도박소)·`UnitUpgradeShop`(강화소)
세 컴포넌트를 실제로 읽고 무엇이 진짜 같고 무엇이 다른지 먼저 정리한다.

## 정말 같은 것 (인터페이스에 넣을 것)

1. **컴포넌트 형태**: 셋 다 `[RequireComponent(typeof(Selectable), typeof(OwnedByPlayer))]`.
   레인 안에 서 있는 플레이어 소유 건물이고, 선택하면 하단 명령 그리드에 칸이 뜬다.
2. **파괴 불가·적 타겟 자동 제외**: 셋 다 `TakeDamage`가 아예 없다. `UnitAttacker`/`UnitCombat`은
   `EnemyDummy.Active`만, 문 공격 폴백은 `DestructibleGate.Active`만 훑기 때문에, 이 두 레지스트리에
   등록되지 않는 것만으로 "적이 못 때린다"가 저절로 성립한다 — 별도 방어 코드가 필요 없다.
   (별도 구현이 아니라 **애초에 존재하지 않는 코드로 성립하는 공통점**이라 인터페이스에 넣을
   멤버는 없다. 새 상점을 만들 때 지키기만 하면 된다.)
3. **소유자 해석 패턴**: 셋 다 `OwnedByPlayer.OwnerId` → `PlayerContext.Get(ownerId)`를 캐시 없이
   그때그때 조회하는 `OwnerContext` 프로퍼티를 갖는다(플레이어 컨텍스트 자체가 자주 안 바뀌어서
   캐시할 이유가 없다).
4. **평평한 슬롯 목록**: 하단 12칸 그리드 중 일부(지금은 9칸, `UnitCommandResultSlotOrder`)를
   빌려 쓴다. 상점은 "0번부터 SlotCount-1번까지 칸이 있다"만 답하고, 그 칸이 시각적으로 어느
   격자 위치에 그려지는지는 전혀 모른다 — `GameHud`가 논리 인덱스 ↔ 시각 슬롯 매핑을 갖는다.
5. **표시(자주 조회)와 설명(가끔 조회)의 분리**: 하단 그리드는 0.4초마다 9칸씩 다시 확인한다
   (자원이 떨어져 못 쓰게 됐는지 등). 반면 툴팁 문자열은 마우스가 그 칸 위에 있을 때만 필요하다.
   그래서 "이름/색/사용 가능 여부"(자주, 저렴해야 함)와 "툴팁 문자열"(가끔, 조립 비용 있어도 됨)을
   서로 다른 메서드로 나눈다. `UnitUpgradeShop`은 이미 라벨을 레벨이 바뀔 때만 다시 만들도록
   캐시해뒀다 — 이 원칙을 인터페이스 문서에도 명시해서 앞으로 만드는 상점이 매번 새로 만들지
   않게 한다.
6. **"대상이 필요한가"는 칸 스스로 답한다**: 도움소는 광역 스킬(땅 클릭)과 연금술(유닛 클릭)과
   마나포션(클릭 불필요, 즉시 실행)이 한 상점 안에 섞여 있다. 도박소·강화소는 전부 즉시 실행이다.
   "이 칸을 누르면 커서로 대상을 찍어야 하는가"를 상점이 슬롯 단위로 답하게 하면, `GameHud`는
   스킬 종류·상점 종류를 몰라도 대상 지정 모드 진입 여부를 결정할 수 있다.
7. **실행은 한 곳, 재검증 필수**: 셋 다 "눌렀다"를 받는 함수 하나(`TryCastX`/`TryRoll`/향후 통합될
   `TryUse`)가 있고, 그 함수 **자신이 다시 한 번 비용·쿨다운·해금 여부를 확인**한다 — 화면에 표시된
   `available`을 신뢰하지 않는다(그 사이에 다른 곳에서 자원을 썼을 수 있다). 실패하면 예외 없이
   `false`만 반환한다.

## 정말 다른 것 (인터페이스에 넣지 않을 것 — 각 상점 내부 구현으로 남긴다)

- **상태 저장 모양**: 도움소는 `Dictionary<SupportSkillData, float>`(스킬별 쿨다운 시각), 도박소는
  `GamblingProgress`(해금 여부 + 누적 사용 횟수, PlayerContext 소유), 강화소는 `UnitUpgrades`
  (트랙별 레벨, PlayerContext 소유). 셋 다 모양이 다르고, 다를 수밖에 없다 — 억지로 하나의 상태
  클래스로 통일하지 않는다.
- **화폐**: 도움소는 마나+골드, 도박소는 골드 또는 자원(목재 등), 강화소는 골드 단일. 인터페이스는
  화폐 개념 자체를 모른다 — `available`(bool) 하나로 충분하다.
- **대상 지정의 실제 의미**: "땅 클릭"이 도움소에서는 "이 지점에 광역 피해"이고, 강화소·도박소는
  대상 지정 자체가 없다. 인터페이스는 "Ground/Unit/None"이라는 종류만 답하고, 그 종류가 실제로
  무엇을 하는지는 상점이 안다.
- **슬롯 배치 규칙**: 도박소는 3칸 그리드에서 줄을 맞추려고 특정 인덱스(7, 8)를 항상 빈 칸으로
  낸다. 이건 그 상점만의 사정이라, `LaneShopSlotView.Empty`를 answer로 내놓을 수 있게만 허용하고
  (label이 null/빈 문자열이면 빈 칸), 어떤 인덱스를 비울지는 상점이 정한다.
- **효과 적용 방식**: 광역 피해·구속·버프(도움소), 도박 굴리기(도박소), 레벨업+영구 배율(강화소) —
  전부 도메인 로직이라 인터페이스 밖에 있다.

## 결론 — 인터페이스 모양

이미 만들어 둔 `Assets/Scripts/Units/ILaneShop.cs`가 위 내용을 그대로 반영하고 있어서
**바꿀 필요가 없다**: `SlotCount`, `GetSlotView(index)`(저렴·자주), `GetSlotTooltip(index)`
(비쌀 수 있음·가끔), `TryUse(index, target)`(재검증 필수, 실패 시 false만).

`GamblingShop`·`UnitUpgradeShop`은 이미 이 인터페이스를 구현하고 있다. 이번 작업은
`SupportShop`을 여기 맞추고, `GameHud`가 `SupportShop`이라는 구체 타입을 더 이상 몰라도
되게(그리고 지금 전혀 안 쓰이고 있던 `GamblingShop`/`UnitUpgradeShop`도 하단 그리드에서
실제로 뜨게) 만드는 것이다 — **동작은 바꾸지 않는다**: 도움소의 마나/골드 비용, 쿨다운,
스킬 효과, 툴팁 내용은 전부 그대로 옮기기만 한다.
