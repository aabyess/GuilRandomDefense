# 멀티플레이 전환 영향 분석

> 작성: 구현담당1, 2026-08-28
> 목적: 서버 권위(server-authoritative) 멀티플레이 전환 시 기존 스크립트들이 받는 영향을 정리한다.
> 네트워킹 프레임워크(Netcode for GameObjects / Mirror / Photon 등)는 아직 미정이므로,
> 실제 API 이름 대신 "서버 권위", "클라이언트 요청", "플레이어별 인스턴스화" 같은 개념 수준으로만 서술한다.
> 코드 변경은 포함하지 않는다.

## 용어

- **서버 권위(server-only)**: 최종 결정은 서버(또는 호스트)만 내리고, 클라이언트는 결과를 통보받아 표시만 한다.
- **클라이언트도 가능**: 클라이언트가 계산해도 결과가 플레이어마다 달라지거나 조작 가능해지지 않는 경우.
- **각자 로컬이어도 무방**: 애초에 다른 플레이어와 동기화될 필요가 없는 순수 로컬 상태(주로 UI).

## Units/

### Selectable.cs
1. **현재**: `static List<Selectable> All`로 씬의 선택 가능 오브젝트를 전역 등록/해제. `IsSelected`는 자기 자신이 보유.
2. **결정 주체**: 각자 로컬이어도 무방 — "무엇이 선택되었는지" 자체는 순수 UI 상태이며 다른 플레이어에게 보일 필요가 없다. 다만 이 오브젝트가 "누구 소유인지"는 별도로 서버 권위 데이터가 필요하다(현재 이 클래스엔 소유권 개념 자체가 없음).
3. **전환 난이도**: 하 — 레지스트리 패턴 자체는 유지 가능. 소유권 필드 추가 정도로 대응 가능.

### SelectionManager.cs
1. **현재**: 마우스 입력을 받아 `Selectable.All`을 순회하며 드래그박스/클릭 선택을 전부 로컬에서 판정.
2. **결정 주체**: 각자 로컬이어도 무방 — 선택 판정 로직 자체는 동기화 불필요. 단, `Selectable.All`에는 다른 플레이어 소유 유닛도 섞여 있으므로 "내 유닛만 선택 가능"하도록 소유권 필터가 추가로 필요하다.
3. **전환 난이도**: 중 — 선택 로직은 안 바뀌지만, 필터가 없으면 다른 플레이어 유닛을 마음대로 선택/조작하는 버그가 생긴다.

### UnitMover.cs
1. **현재**: 우클릭 시 로컬에서 즉시 `NavMeshAgent.SetDestination` 호출. 이동 시뮬레이션도 각 클라이언트가 프레임마다 로컬로 계산.
2. **결정 주체**: 서버만 — 목적지는 클라이언트가 "요청"만 하고, 실제 위치는 서버가 계산해 모든 클라이언트에 동기화해야 한다. 안 그러면 위치 조작(치팅) 및 클라이언트 간 위치 불일치가 생긴다.
3. **전환 난이도**: 상 — "입력 → 즉시 실행" 구조를 "입력 → 서버 요청 → 서버 시뮬레이션 → 결과 브로드캐스트"로 바꿔야 한다. NavMeshAgent를 서버 전용으로만 돌릴지, 클라이언트 예측+보정을 넣을지도 프레임워크 결정 후 판단 필요.

### UnitAttacker.cs
1. **현재**: 매 프레임 `FindObjectsByType<EnemyDummy>`로 전체 씬을 스캔해 사거리 내 가장 가까운 적을 로컬에서 찾고, `target.TakeDamage()`를 로컬에서 직접 호출.
2. **결정 주체**: 서버만 — 데미지 판정·hp 차감은 반드시 서버 권위. 안 그러면 클라이언트가 데미지를 조작하거나, 여러 클라이언트가 같은 몹에 각자 데미지를 넣어 중복 차감이 발생한다. 타겟 "제안"은 클라이언트가 해도 되지만 최종 적용은 서버 승인이 필요하다.
3. **전환 난이도**: 상 — 데미지 적용 지점 전체를 서버로 옮겨야 하고, 매 프레임 전역 스캔 방식도 서버 전용 로직으로 재설계 필요.

### GoldWallet.cs
1. **현재**: 씬에 컴포넌트 1개, `TrySpend`/`Add`로 로컬 상태를 직접 변경, `OnGoldChanged` 이벤트로 UI 통보.
2. **결정 주체**: 서버만 — 골드는 재화이므로 서버 권위 필수. 표시(현재 잔액 읽기)는 클라이언트 로컬이어도 무방.
3. **전환 난이도**: 중상 — API 형태(`Gold`/`TrySpend`/`Add`/`OnGoldChanged`)는 재사용 가능하지만, "씬에 1개" → "플레이어별 인스턴스, 실값은 서버 보유·클라이언트는 동기화된 값만 읽기"로 바뀌어야 한다. `TrySpend`를 클라이언트가 직접 호출하는 지금 방식은 요청→검증→반영 구조로 전환 필요.

### GachaController.cs
1. **현재**: `TryRoll()`이 클라이언트에서 `gachaTable.Roll()`(`Random.Range`)을 직접 호출하고, `goldWallet.TrySpend`도 로컬에서 처리.
2. **결정 주체**: 서버만 — 랜덤 결과를 클라이언트가 굴리면 원하는 결과만 받아들이는 조작이 가능해진다. 골드 차감도 서버 권위 필요.
3. **전환 난이도**: 상 — "요청(버튼 클릭) → 서버가 골드 검증+차감+Random 실행 → 결과를 요청자에게만 전달"로 전면 재작성. 최근 고친 "먼저 굴리고 결과 있을 때만 차감" 순서 자체는 서버 로직으로 그대로 옮기면 된다.

### UnitInventory.cs
1. **현재**: 씬에 리스트 하나, `Add`/`Remove`로 유닛 목록 관리, `OnInventoryChanged` 이벤트.
2. **결정 주체**: 서버만 — 보유 자산이므로 서버 권위. "씬에 1개"인 지금 구조부터 플레이어별로 나뉘어야 한다.
3. **전환 난이도**: 중 — `List<UnitData>` 기반이라 로직 복잡도는 낮지만, "플레이어별 인스턴스화"와 "서버 권위" 두 가지를 동시에 적용해야 한다.

### CombineSystem.cs
1. **현재**: `TryCombine`이 `inventory.Remove`/`Add`를 로컬에서 직접 호출, `gachaTable.RollFromGrade`도 로컬 `Random`.
2. **결정 주체**: 서버만 — 인벤토리 변경과 랜덤 결과 둘 다 서버 권위 필요. `GetCombinableUnits`처럼 읽기 전용 조회는 서버 값의 동기화된 복제본 기준으로 클라이언트에서 미리보기용으로 돌려도 무방.
3. **전환 난이도**: 상 — GachaController와 동일 패턴(클라이언트 요청 → 서버 검증(개수 충분한지)+처리 → 결과 통보)으로 전환.

## Waves/

### WaypointPath.cs
1. **현재**: 씬에 배치된 고정 `Transform[]`, 상태 변경 없는 순수 데이터/기즈모.
2. **결정 주체**: 각자 로컬이어도 무방 — 모든 클라이언트가 동일 씬을 로드하면 자연히 동일 값을 갖는 정적 데이터.
3. **전환 난이도**: 하 — 수정 불필요.

### WaypointMover.cs
1. **현재**: 매 프레임 로컬로 `Vector3.MoveTowards` 이동, `currentIndex`가 로컬 상태.
2. **결정 주체**: 서버만 — 몹 위치는 모든 플레이어가 동일하게 봐야 하는 공유 상태. 서버가 이동을 시뮬레이션하고 위치를 동기화해야 한다.
3. **전환 난이도**: 상 — 로컬 시뮬레이션 → "서버 시뮬레이션 + 클라이언트 보간(interpolation)"으로 재설계. 지금처럼 각 클라이언트가 독립적으로 `MoveTowards`를 돌리면 랙/타이밍 차이로 플레이어마다 몹 위치가 달라진다.

### WaveSpawner.cs
1. **현재**: `SpawnRound`가 로컬에서 `Instantiate`, `EnemyDummy.Initialize`/`WaypointMover.SetPath`·`SetMoveSpeed`까지 전부 로컬 호출.
2. **결정 주체**: 서버만 — 스폰은 반드시 서버(또는 호스트)만 해야 클라이언트마다 다른 몹을 보는 문제가 없다. 클라이언트는 서버가 스폰한 결과를 통보/동기화받아 표시만 한다.
3. **전환 난이도**: 상 — 로컬 `Instantiate`를 네트워크 스폰으로 바꿔야 하지만, 코루틴 기반 간격 스폰 로직(`SpawnRoutine`) 자체는 서버에서 그대로 재사용 가능.

### RoundManager.cs
1. **현재**: 로컬 `Update`에서 `roundTimer` 감소, `EnemyDummy.Active.Count`로 패배 판정, `currentRound` 증가.
2. **결정 주체**: 서버만 — 라운드 진행/타이머/패배 판정은 모든 플레이어에게 동일해야 하는 게임 전역 상태. 클라이언트는 서버가 브로드캐스트하는 값만 표시.
3. **전환 난이도**: 상 — 지금처럼 각 클라이언트가 독립적으로 `Update`를 돌리면 라운드가 클라이언트마다 다르게 진행된다. 서버 단일 인스턴스만 로직을 실행하고, 클라이언트는 읽기 전용 뷰로 전환.

## EnemyDummy.cs (Units/, Waves/ 양쪽에서 참조됨)
1. **현재**: `static List<EnemyDummy> Active`로 씬의 살아있는 몹을 전역 등록, `TakeDamage`가 로컬에서 hp 차감 후 `Destroy(gameObject)`를 직접 호출.
2. **결정 주체**: hp 차감·사망 판정은 서버만. `Active` 레지스트리의 등록/해제 자체는 각 클라이언트가 자기 화면 기준으로 유지해도 되지만, **패배 판정에 쓰이는 카운트는 서버가 가진 권위 있는 목록을 기준으로 해야 한다** — 지금 `RoundManager`가 이 static list를 직접 읽고 있어 위험하다.
3. **전환 난이도**: 상 — `TakeDamage`를 클라이언트가 직접 호출하면 안 되고(서버 요청 → 서버 차감 → 결과 동기화), `Destroy`도 서버가 네트워크 디스폰으로 처리해야 클라이언트 화면이 일치한다.

## Data/ (ScriptableObject)

### UnitData.cs / SkillData.cs / EnemyData.cs / WaveData.cs
1. **현재**: 전부 순수 데이터 정의(SO), 런타임 상태 없음, 값은 에셋에 미리 구워짐.
2. **결정 주체**: 각자 로컬이어도 무방 — 모든 클라이언트가 동일 빌드/에셋을 가지므로 자동으로 동일한 값. 동기화 대상 아님(정적 참조 데이터).
3. **전환 난이도**: 하 — 수정 불필요. 단, 프레임워크에 따라 네트워크 메시지에서 SO 참조를 식별할 방법(ID 매핑 등)이 필요할 수 있음 — 프레임워크 결정 후 논의.

### GachaTable.cs
1. **현재**: `Roll()`/`RollFromGrade()` 내부에서 `Random.Range` 호출. 데이터(entries/weight/pool)는 정적이지만, "굴리는 행위"는 결과를 확정하는 행위다.
2. **결정 주체**: 서버만 — 데이터 자체는 로컬이어도 무방하지만, `Roll()`을 실제로 호출해 결과를 확정하는 주체는 반드시 서버여야 한다(`GachaController`와 동일 이슈).
3. **전환 난이도**: 하(데이터) / 상(호출 주체) — SO 자체는 안 바뀌지만, `Roll()`을 어디서 호출하느냐가 핵심이므로 서버 전용 컨텍스트에서만 실행되도록 호출 지점을 제한해야 한다.

## 전환 순서 제안

우선순위는 "모든 플레이어가 반드시 동일하게 봐야 하는 상태부터"를 기준으로 잡았다. 아래 시스템일수록 위 시스템에 의존하므로 순서를 지키지 않으면 재작업이 늘어난다.

1. **선행조건 (코드 작업 아님)**: 네트워킹 프레임워크 선정 + 기본 연결/씬 동기화 확립.
2. **권위(authority) 골격 확립**: "이 코드는 서버에서만 실행된다"를 구분하는 최소 골격(서버 전용 체크 또는 서버 전용 매니저 클래스)을 먼저 만든다. 이후 모든 항목이 이 위에 얹힌다.
3. **공유 게임 상태를 서버 권위로 전환**: `RoundManager`, `WaveSpawner`, `WaypointMover`(이동), `EnemyDummy`(hp/사망) — 모든 플레이어가 무조건 동일하게 봐야 하는 값들이라 가장 시급하고, 아래 항목들이 여기에 의존한다.
4. **유닛 소유권 개념 도입**: `Selectable`/`SelectionManager`/`UnitMover`/`UnitAttacker` — "이게 내 유닛인가" 필터링과 이동/공격 명령의 서버 검증.
5. **플레이어별 자산 분리**: `GoldWallet`, `UnitInventory` — 씬에 1개 → 플레이어 N개 인스턴스, 서버 권위 값으로.
6. **조작 방지가 중요한 랜덤/변경 로직**: `GachaController`, `CombineSystem` — 4·5번에서 소유권과 플레이어별 자산이 갖춰진 뒤에 붙여야 자연스럽다.
7. **UI**: 항상 마지막. 위 시스템들이 서버 권위 이벤트/동기화 값을 노출한 뒤, UI는 그 값을 표시만 하도록 재배선한다.

`Data/`의 SO 4종(UnitData/SkillData/EnemyData/WaveData)은 이 순서에 포함하지 않는다 — 정적 데이터라 변경이 필요 없다.
