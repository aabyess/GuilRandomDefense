# `RRD순번` 다중 행 감사 — ⓐ/ⓑ/ⓒ 판정

조사: 리서치담당 / 2026-09-06
요청: PM — 「`ORIGINAL_UNLISTED_SKILL_EFFECTS.csv`에서 같은 (유닛,스킬)이 여러
`RRD순번`을 차지하는 게 진짜 여러 효과(ⓐ)인지, 한 효과의 다단 표기(ⓑ)인지, 섞여
있는지(ⓒ) — 사장님 02번 결정(원작 밀도 맞추기)의 분모가 여기 걸려 있다」

## 결론 한 줄

**ⓒ다. 그리고 PM이 제시한 세 갈래보다 더 나쁘다** — 같은 스킬 **안에서도** 어떤
`RRD순번` 쌍은 "항상 같이 나가는 별개 효과"(ⓐ)이고 다른 쌍은 "if/else로 갈리는 같은
자리의 다른 결과"(ⓑ)다. 표본이 아니라 **원문 제어흐름을 기계적으로 추적**해서 확인했다.

## 방법 — 표본이 아니라 구조 추적

`계산식`이 같다/다르다로는 못 가른다(아래 예시가 보여주듯 다른 값이어도 같은
if/else의 두 갈래일 수 있다). 대신 **JASS 원문의 `if`/`elseif`/`else`/`endif` 중첩을
직접 추적**해서, 각 `RRD`/`UnitDamagePointLoc`/`UnitDamageTargetBJ` 호출이 **어느
if문의 어느 분기(then/else)에 있는지 경로**를 기록했다. 두 호출이 **같은 if문의 서로
다른 분기**에 있으면 그 둘은 **같은 판에 절대 같이 안 나간다** — 즉 같은 자리(ⓑ). 그런
관계가 없으면 서로 독립적으로 같이 나갈 수 있는 별개 효과(ⓐ)로 본다.

## 실제 사례 둘 — 원인이 서로 다르다

### 사례1: `H05N`/`Tasigi_03` (4행 → 실제 2개)

```jass
if(Trig_Tasigi_03_Func003Func001C())then
  call RRD(...,400000.00,...ATTACK_TYPE_MAGIC,...)                    // RRD순번1
  if GetUnitPointValue(...)<200 then
    call RRD(...,대상최대체력×계수,...ATTACK_TYPE_NORMAL,...)          // RRD순번2
  endif
else
  ...
  call RRD(...,400000.00,...ATTACK_TYPE_MAGIC,...)                    // RRD순번3 (순번1과 완전히 같은 식)
  if GetUnitPointValue(...)<200 then
    call RRD(...,대상최대체력×계수,...ATTACK_TYPE_NORMAL,...)          // RRD순번4 (순번2와 완전히 같은 식)
  endif
endif
```

`Func003Func001C()`가 참인지 거짓인지에 따라 **타겟팅 방식만 다르고**(지정 대상 vs
그룹에서 무작위 픽) **피해는 완전히 동일한 두 갈래**로 나뉜다. 즉 **원작 실제 판정은
항상 "400000 확정타 1개 + 조건부(대상 포인트값<200) 최대체력%타 1개" = 2개**다.
`RRD순번`이 4개인 건 **코드가 타겟팅 분기 때문에 통째로 두 번 복사된 결과**다 —
**ⓑ**.

### 사례2: `H08V`/`Nami_Skill_2` (3행 → 실제 2개, 그중 하나는 조건부)

```jass
if UnitHasItem(caster, udg_Item_nami[...]) == true then
  if GetRandomInt(1,100) < 33 then
    call RRD(...,800000.00,...)   // RRD순번1
  else
    call RRD(...,400000.00,...)   // RRD순번2
  endif
endif
// 아이템 유무·확률과 무관하게 항상 실행됨:
call RRD(...,400000.00,...)       // RRD순번3
```

`RRD순번3`(항상 발동, 400000)은 **아이템 유무와 무관하게 매번 나간다** — 이건
진짜 별개 효과(ⓐ)다. 그런데 `RRD순번1`·`RRD순번2`(800000/400000)는 **서로 다른
값인데도 같은 `if GetRandomInt<33`의 다른 분기라 절대 같이 안 나간다** — 이건 값이
달라도 ⓑ(같은 자리의 다른 결과, 33%/67% 확률 갈림)다. **게다가 이 자리 자체가
아이템을 가진 경우에만 발동하는 조건부 보너스**라 "매번 확정으로 붙는 값"으로 세면
안 된다.

→ **"값이 다르면 ⓐ"라는 단순 규칙도 틀린다.** 값이 달라도 if/else 형제면 ⓑ다.
공식 기계 판정(같은 if문 조상 공유 + 분기 다름 = 배타)만이 정확하다.

## 자동 측정 — 84개 다중행 그룹 중 67개 원문 추적 완료

`ORIGINAL_UNLISTED_SKILL_EFFECTS.csv`(304행, 153개 (유닛,스킬) 그룹, 그중 84개가
2행 이상)를 위 방법으로 기계 추적했다. `Trig_<스킬트리거>_Actions` 함수를 찾아
`if/elseif/else/endif` 중첩을 파싱하고, `RRD`/`UnitDamagePointLoc`/
`UnitDamageTargetBJ`/`UnitDamageTarget` 호출마다 분기 경로를 기록한 뒤, **같은
if문에서 분기가 다른 호출끼리 묶어(연결요소) 그 묶음을 1개로 세는 방식**으로
"실제 구분되는 효과 슬롯 수"를 계산했다.

| | 값 |
|---|---:|
| 다중행 그룹 (전체) | 84 |
| 원문 추적 성공 | 67 |
| 원문 추적 실패(아래 참고) | 17 |
| 추적된 67개 그룹의 CSV 행 합 | 197 |
| 그중 실제로 찾아낸 원문 호출 수 | 136 |
| 분기-배타 묶음 적용 후 "실제 슬롯" 수 | **100** |

**197행 → 100슬롯(49% 감소).** 표본 2개가 아니라 67개 그룹 전체에 같은 방법을 적용한
결과다. PM이 별도로 계산한 3-소스 합계 "355→217"(1.64배)과 **같은 방향, 비슷한
크기**다 — 서로 다른 방법(PM: 그룹당 1개로 뭉갬 / 나: if-else 분기만 배타 처리하고
진짜 동시발동은 살림)인데도 수렴한다는 게 교차검증이다.

**전체 파일(304행, 69개 단일행+84개 다중행) 투영**: 단일행 69개는 원래도 정확(69) +
측정된 다중행 67개(100) + 미측정 17개(같은 비율 가정 시 약 19 추정) ≈ **188 전후**.
raw 304 대비 **약 1.62배 부풀려져 있다** — PM의 1.64배와 사실상 일치.

## 2026-09-06 후속 — 나머지 17개 그룹도 전수 완료(투영 아니라 실측)

PM 요청대로 **17개 전부 콜백 함수까지 따라 들어가 실측했다.** 원인은 죽음이 아니라
**피해가 `ForGroupBJ(...,Condition(...),function Trig_X_FuncNNNA)`로 등록되는 별도
콜백 함수 안**에 있어서였다(예: `Trig_Tichi_skill_2_tr_Func003Func007A`). 콜백까지
같은 방식(if/else 배타 추적)으로 펼쳐서 17개 전부 해소했다.

| | CSV행 | 원문 호출 발견 | 배타처리 후 실제 슬롯 |
|---|---:|---:|---:|
| 17개 그룹 합계 | 38 | 34 | **34 (감소 0%)** |

**중요: 이 17개는 앞의 67개(49% 감소)와 완전히 다른 성격이다.** `ForGroupBJ`
콜백 패턴은 대부분 "스킬의 여러 단계(Stage)마다 범위 안 유닛을 한 번씩 치는" 구조라
**콜백마다 서로 다른 단계의 진짜 별개 타격**이었다 — if/else로 갈라진 복사본이
아니라 **ⓐ(진짜 여러 효과)가 압도적**이었다. `Tasigi_03` 유형(같은 트리거 안
if/else 복사)은 67개 그룹 쪽에 몰려 있었고, 콜백형 스킬 쪽엔 거의 없었다.

### 정정 — 앞서 낸 "188 추정(304건 대비)"은 철회한다

67개 그룹의 감소율(49%)을 17개에도 그대로 적용해서 "약 19개로 더 준다"고 투영했던
게 **틀렸다** — 실측하니 17개는 거의 안 줄었다(38→34, 11%). 두 하위집합의 성격이
이렇게 다르다는 걸 실측 전엔 몰랐다 — **투영이 위험하다는 걸 스스로 증명한 사례라
남긴다.**
