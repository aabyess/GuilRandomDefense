# 매칭 키 신뢰도 — 무엇으로 원작/자산을 찾아도 되고, 무엇으로는 안 되는가

2026-09-06, 구현담당3. PM 지시 — 오늘 하루 라벨 문제가 다섯 번 나왔다(더미 이름 접두사·
`해당없음` 표기·파일명 흔함/안흔함·`skillName` 필드, 그리고 이 문서를 쓰게 만든 계기인
`skillName` 내용 불일치 조사). 다음 사람이 여섯 번째를 밟지 않게 정리한다.

## 왜 이게 반복되는가

**사람이 붙인 이름은 그 사람의 의도이지 데이터가 아니다.** 이름은 붙이는 순간의 최선의
판단을 담을 뿐이고, 그 판단은 나중에 새 정보로 바뀌거나(예: 006이 처음엔 다른 이름으로
잠정 배정됐다가 재확정된 사례들), 다른 목적으로 재활용된다(예: `skillName`이 "이 스킬을
설명하는 라벨"로 쓰이다가, 나중에 다른 채널의 값으로 내용이 갈아끼워지면서 라벨만 남는다).
**이름은 그 이름을 붙인 시점의 스냅샷이고, 데이터는 그 뒤에도 계속 움직인다** — 이 프로젝트
전체 규모(원작 유닛 매핑 불가, 채널 4개가 각자 독립적으로 배정, 여러 세션이 동시에 수정)에서
이 간극은 저절로 벌어진다.

**구조적으로 강제되는 것만 안전하다** — guid, enum 필드, 코드가 실제로 읽는 필드처럼
"어긋나면 뭔가 눈에 보이게 고장 나는" 것들이다. 사람이 텍스트로 적어 넣고 아무것도 그
텍스트를 검증하지 않는 것(파일명, 설명 속 라벨, `skillName` 같은 "설명용" 필드)은
어긋나도 아무것도 안 고장 나서, 아무도 모르는 채로 남는다.

## 신뢰 가능

| 키 | 왜 안전한가 | 어떻게 검증됐나 |
|---|---|---|
| `.meta`의 `guid` | 참조가 이 값으로 걸리므로, 틀리면 즉시 "참조가 깨짐"으로 드러난다(Unity가 nullReference로 보여준다). 사람이 손으로 안 맞춰도 되고, `Tools/check_assignment_invariants.py`(④·⑥)가 참조·에셋 존재를 기계적으로 대조한다. | 이 세션 내내(006~019 채우기, 사이드보스 자산 등) guid로 참조를 걸 때마다 실제로 깨지면 컴파일·체크 스크립트가 바로 잡아냈다 — 실패 모드가 시끄럽다. |
| `StoryData.order` | `MapGenerator.BuildStoryZone`이 파일명이 아니라 이 필드 값으로 정렬해 `StoryManager.stories`를 배선하고, `RewardDistributor.GrantStoryReward`도 이 필드로 특정 스토리를 분기한다(스토리12 특성포인트 지급, 이번에 스토리7 고대의 배 지급). **필드 자체가 게임 로직의 입력**이라 틀리면 즉시 잘못된 보상이 나간다. | 05번(고대의 배) 작업 때 13개 자산 전부의 `order`를 직접 읽어 파일명 숫자와 1:1 일치함을 확인했고, `MapGenerator.cs:1696-1701`(`OrderBy(story => story.order)`)이 실제로 이 필드만 본다는 걸 코드로 확인했다. |
| `UnitGrade` 실제 필드(`UnitData.grade`, enum 값) | 코드가 등급 판정을 전부 이 필드로 한다(뽑기 풀, 조합표, `GrantHeroKillExperienceToLane`의 초월함·영원한 필터 등). 파일명·설명의 "등급 접두사"는 사람이 옮겨 적은 것이고, 이 필드는 원본이다. | 01번(영웅 XP) 작업에서 `identity.Data.grade != UnitGrade.Transcendent && != UnitGrade.Eternal`로 실제 필터링에 썼고, 정상 동작 확인. |
| `SkillData_원작0NN_{uid}.asset` **파일명의 uid** (06번① 한정) | 이 채널만 예외적으로 신뢰 가능하다 — `Tools/translate_hidden_recipes.py`의 `build_master_uid_map()`이 이 파일명 패턴에서 **정규식으로 직접** uid를 뽑아 최우선 채널로 쓴다(파일명이 곧 데이터 계약). 다른 채널(더미 이름, `skillName`)과 달리 이 패턴은 "이름이면서 동시에 그 이름을 코드가 파싱해 실제로 쓴다"는 점에서 구조적 강제에 가깝다. | 07번 조사 때 `translate_hidden_recipes.py`를 직접 실행해 190개 uid 매핑을 뽑아봤고, 이 패턴에서 나온 값들이 실제로 게이트/회수 채널과 일치하는 것을 확인했다. |

## 신뢰 불가

| 키 | 왜 위험한가 | 실제로 어떻게 깨졌나 |
|---|---|---|
| 더미 이름 접두사 (예: "루치 개틀링 더미") | 제작자가 "이 더미는 대충 이 캐릭터 거겠지"로 붙인 라벨이지, 실제 소유권을 검증한 적이 없다. | PM 보고(2026-09-06): **10건**이 실제 주인과 다르다(루치 접두사인데 실제는 캐럿, 에넬 접두사인데 실제는 와이퍼 등). `DUMMY_CHANNEL_MISSING.csv`에 `진짜주인_유닛ID`·`진짜주인_등급`·`표기_불일치` 열이 새로 생겼다 — 나(구현담당3)는 이 조사를 직접 하지 않았고 PM 보고를 그대로 옮긴다. |
| `skillName` 필드 | "이 스킬을 부르는 이름"일 뿐 코드가 매칭에 쓰지 않는다(이번 조사로 `Tools/*.py` 15개 스크립트 전부 확인 — 전부 쓰기 전용, 읽어서 매칭하는 곳 0건). 그런데도 사람 눈에는 "이 파일의 정체"로 읽혀서, 실제 `effects`가 다른 채널(더미 추적)로 나중에 갈아끼워져도 라벨이 안 따라간다. | 구현담당1 발견 + 이번 조사로 확인: `희귀함_윤현모`(skillName=A0UZ, 원작 실측 추가피해 5000인데 실제 effects.multiplier=9000), `희귀함_이상혁`(skillName=A06D, 실측 15000인데 실제 6000) — 둘 다 1채널 원본표(`ORIGINAL_UNIT_ABILITIES.csv`)와 직접 대조해 확정. ⚠️ **같은 모양(더미 추적 설명 + 1채널 실측값 불일치)이 28건 더 있으나, 이건 대부분 정상일 수 있다** — 06번①의 채널 우선순위(2채널/더미채널이 1채널/uabi보다 우선)상 더미채널 값이 정당하게 1채널 값을 덮어썼을 가능성이 크다. 이 28건은 개별 원문 대조 없이는 "버그"로 확정할 수 없다 — [판정불가]로 남긴다. |
| 파일명의 등급 접두사(흔함/안흔함/희귀함 등) | ⚠️ **나(구현담당3)는 이 항목을 직접 검증하지 못했다.** PM이 오늘 라벨 문제 목록에 "파일명 흔함/안흔함"을 넣었다는 것만 전달받았고, 구체적으로 어떤 파일이 왜 어긋났는지는 조사하지 않았다. **이 항목을 "신뢰 불가 확정"으로 읽지 말 것** — 검증 안 된 채로 목록에 올리면 이 문서 자체가 다음 사람을 속인다. 파일명 접두사와 `UnitData.grade` 실제 값이 다른 사례가 있는지는 별도 확인이 필요하다. | (미검증) |

## 참고 — 별도로 걸린 관련 문제 (YAML 이스케이프)

매칭 키 문제는 아니지만 같은 날 같은 조사에서 나왔다: `description` 필드 다수가 `: `
(콜론+공백)를 텍스트 안에 그대로 갖고 있어 **표준 YAML(PyYAML) 파서로는 345개 중 281개가
파싱 실패**한다. PM이 직접 검증(2026-09-05 14:43 최초 커밋 → 15:45 사장님 유니티 저장,
그 사이 정상 동작 확인)해 **Unity 자체 임포터는 관대해서 지금은 안 터진다**는 결론이
났다 — 다만 **우리 파이썬 도구가 PyYAML로 이 파일들을 읽으면 못 읽는다**(이 문서를 준비한
스크립트도 전부 정규식으로 우회했다). 앞으로 `description`을 스크립트에서 쓸 때는
따옴표로 감쌀 것(Unity 자신도 그렇게 쓴다) — 기존 281개는 구현담당1의 파일 쪼개기가
끝난 뒤 한 번에 정리 예정(PM).
