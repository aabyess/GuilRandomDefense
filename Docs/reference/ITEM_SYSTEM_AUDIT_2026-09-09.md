## 2. ✅ 고침 — 이름·툴팁 13건이 원작과 달랐다 (커밋 `a7402b8`)

`war3map.w3t`의 `unam`·`utub`을 직접 파싱해 38종 전수 대조했다. 등급 접미사와 공백
차이(우리가 `grade` 필드로 분리한 **의도된 설계**)를 빼면 13건이 실제로 틀렸다.

### 🔴 다른 아이템의 내용을 물고 있던 것 — 2건

| ID | 고치기 전 | 원작 원문 |
|---|---|---|
| **I000** | `"이름깨짐"` + **I008(저지-거프)의 퀘스트 문구를 복붙** | `목재 구입` / `10000골드를 1의 목재로 변환합니다.` |
| **I00D** | `"미상"` + **I00E(랜덤 특수 도박)의 utub 원문을 복붙** | `돈도박 중급 리메이크` / `60% 확률로 51~450원사이의 돈을 얻습니다.` |

I000은 **이름이 깨진 게 아니라** 멀쩡한 이름이 원작에 있었다(골드→목재 환전).
I00D는 `utip`이 I00E와 글자 그대로 같아(`돈 도박 중급`) 혼동된 것으로 보인다 —
실제로는 I00E가 I00D를 복제해 만든 파생 아이템이다.

### 🔴 적 집단 이름이 달랐다

| ID | 고치기 전 | 원작 |
|---|---|---|
| **I00B** | `퇴치-신림패거리퇴치` | `퇴치-해적단 퇴치` |

숫자(골드1500+목재1, 60초)는 원래도 맞았다. 「신림패거리」의 출처는 불명이다.

[[docs-are-not-evidence]]의 또 한 사례다.

⚠️ `I00E`·`I00F`는 이전에 이미 닫혀 제외. 창작 2개는 대상 아님.

**상점 버튼형**인데, 상점 재고 목록은 `war3mapUnits.doo`에만 있었을 데이터다.
**이 맵에 그 파일이 없다** — 도구 한계가 아니라 데이터 부재(3번째 독립 재확인).
`I000`은 GM 치트 `"올템"`의 `ILOFOO()`로만 생성된다(정식 경로 아님).

✅ **I00B 종결**: 예전 메모의 「퀘스트 보상(60초내 해적단 퇴치)」은 `w3t`의 **툴팁을
인용한 것**이지 생성 근거가 아니었다. 인용 자체는 토씨까지 정확했다 — 하지만
I00B가 `CreateItem`되는 자리는 0건이다. 이건 퀘스트를 **시작시키는 상점 버튼**이다.
근거 폐기, **생성 0건으로 확정**.

### 3-2. 🔴 우리 쪽: 도박을 여는 유닛이 도달 불가

📌 **PM 정정**: 1차 보고의 「도박을 여는 유닛이 0기」는 **틀렸다.**
유닛도 있고 배선도 정확하다. 막힌 지점이 한 칸 뒤였다.

```
Assets/Data/Units/Special/Unit_메타몽_h0BS.asset
  isSystemUnit: 1
  sellTriggersItemGamblePool: {guid: 14d4d41f...}   ← 풀 배선 정상
```

그런데 **이 유닛의 guid(`b5a2630c…`)를 참조하는 자산이 프로젝트 전체에 0건**이다.
가챠 테이블·조합 결과·창고 배치·보상 어디에도 없다. 플레이어가 메타몽을 손에
넣을 방법이 없어 **판매 트리거가 영원히 안 걸린다.**
(원작은 `H0C4`「항해일지」 상점 → `AddUnitToStockBJ('H0BS')`인데, 「항해일지」도 우리 로스터에 없다.)

한편 **재고 카운터는 살아 있다** — `RoundManager.AdvanceRound()`(262행) →
`GrantItemGambleStock()`(357–368행)이 6라운드 stock=1, 9라운드 stock=2를 실제로 넣는다.
문을 열 열쇠만 없다.

## 4. 🔴 효과: `ItemData` 8개 필드 중 **7개를 아무도 안 읽는다**

두 세션이 독립으로 전수 grep해 같은 결과가 나왔다.

| 필드 | 읽는 곳 |
|---|---|
| `itemName` | **1건** — `GameHud.cs:1508` 조합 툴팁의 재료 이름 |
| `hasGrade` · `grade` | **0건** (저장소의 `.grade` 히트는 전부 `UnitData`/`GachaTable` 쪽) |
| `tooltipText` | **0건** — 효과가 문자열로만 있고 띄우는 코드도 없다 |
| `linkedAbilityId` | **0건** — I010처럼 연결값이 확정된 것조차 능력을 주는 코드가 없다 |
| `sellWoodMin`/`Max` | **0건** — 「아이템을 목재로 판매」 기능이 코드에 아예 없다 |
| `designNote` | 0건 (개발자 메모 — 원래 안 읽히는 게 맞다) |

⚠️ 「배선이 빠졌다」가 아니라 **「효과를 담을 수치 필드가 스키마에 없다」**다.
`SkillData`가 `effects[].multiplier`를 갖는 것과 대조된다. 도박을 열어도 **먹으면 아무 일도 안 난다.**

또한 `igol`(가격)·`ilum`(목재가)·`isto`(재고)·`istr`(재고회복)·`ureq`(전제조건)에
**대응 필드가 하나도 없어** 「원작과 같은가」를 물을 수조차 없다.
원작 `ureq` 보유: I00A=R02F · I00B=Rhri · I00C=R02F · I008=R029 · I00F=h08B,R02P(이것만 텍스트로 반영됨).

## 5. 🔴 UI 없음 · 인벤토리가 플레이어별이 아님

**UI**: 인벤토리 패널·슬롯·아이콘 0건, 「아이템 사용」 버튼 0건.
도박 당첨 시 `ItemInventoryRef?.Add(wonItem)`(`GameHud.cs:783`)로 **조용히** 넣기만 한다 —
토스트·로그·사운드 전무. 플레이어는 자기가 뭘 뽑았는지 알 수 없다.

**플레이어 분리** — 새로 발견한 결함:
```
씬            ItemGambleState  4개 (플레이어 0~3, PlayerContext에 각각 배선 ✅)
              ItemInventory    1개 (플레이어 0 슬롯에만)
PlayerContext itemGambleState 필드 O  /  itemInventory 필드 자체가 없음
GameHud:234   FindFirstObjectByType<ItemInventory>()   ← 씬 전역 1개
CombineSystem 씬 64387행 itemInventory: {fileID: 185428506}  ← 같은 그 1개
```
**누가 도박에 이겨도 아이템은 전부 플레이어 0에게 들어가고, 조합도 그 하나를 쓴다.**

원작은 **위에서 아래까지 전부 플레이어별**이다(리서치담당, JASS 원문 확인):
- `udg_Item_Bigmom`·`udg_Item_Kid`·`udg_Item_Ryokugu`·`udg_Item_Zoro` 전부 `item array`,
  `itpool`도 `itempool array`(11개, pid별)
- `ItemGet`은 `pid=GetConvertedPlayerId(GetOwningPlayer(v))`로 풀을 고르고, `v`의 좌표에
  놓고, `v`의 인벤토리에 넣고(`UnitAddItem`), 메시지도 그 소유자에게만 띄운다
- 아이템 보유형 해금도 `GetOwningPlayer(GetTriggerUnit())`로 인덱싱해 **그 주운 사람에게만** 적용

→ **원작 대비 명백한 이탈이다.** 지금은 도달 불가라 증상이 안 보이지만, 도박을 여는 순간 터진다.

## 6. 🟢 창작 아이템 2개가 조합식 3기를 막고 있다 — 가장 싸게 풀리는 것

| 조합식 | 요구 아이템 | 결과 |
|---|---|---|
| `제한_박성호` | 아이템_분실된지갑 | 제한_박성호 (→ `불멸_김용태`의 재료이기도 함) |
| `영원_김영원` | 아이템_어둠의추천서 | 영원_김영원 |

이 둘은 **원작에 없다**:
- 원작 `w3t` 38종에 대응 ID·이름이 없다
- **원작 조합 능력 255개 중 아이템을 재료로 요구하는 것은 0개**(`acat`에 `I0xx` 0건).
  원작은 조합 재료가 **유닛뿐**이고, 아이템은 「주우면 그 소유자에게 영구 효과가 붙는」 방식이다
- 자산도 `itemName` 한 줄뿐 — `tooltipText`도 `designNote`도 없다

소비 코드는 정상이다: `CombineSystem.TryPlanItems`(393–434) → `TryTake`(436–450) →
`TryCombine`(173–179) `itemInventory.Remove(item)`. 레시피의 item guid도 두 자산과 정확히 일치.
**로직 결함 없음, 도달 불가일 뿐이다.**

📌 조합식은 우리 창작 영역이라([[follow-original-everywhere]]) 규칙 위반이 아니다.
문제는 **얻을 방법을 안 만든 채 재료로 걸어 둔 것**이다.
🟢 원작 대조가 필요 없으니 **사장님이 「이 둘을 어디서 주나」만 정하시면 끝난다.**

## 7. 조사 함정 — 다음 세션이 반드시 볼 것

- **`iabi`를 믿지 마라.** I002·I004·I00G·I00J·I00K·I00L·I00O·I00T·I00X·I00Z 등 다수가
  `iabi=A109`를 쓰는데 이 능력은 `Iagi=Iint=Istr=0`인 **무효과 스텁**이다. 툴팁에 적힌
  효과(예: I00Z 「골드 획득량 20%증가」)는 이 필드가 아니라 **별도 JASS 트리거**로 구현된다.
  → `w3t`/`w3a`만으로는 이 숫자들을 검증할 수 없다. [[no-numbers-means-three-things]]
- **`aub1`(능력 설명문)을 믿지 마라.** A171(I00S)·A17Q(I011)은 필드가 0이고 `aub1`이
  전혀 다른 아이템(「폐함대선 판매」·「점 치기」) 내용을 복붙한 상태다 —
  원작 제작자가 능력을 복제하며 설명문만 안 고친 흔적이다.
  진짜 값은 `utub`과 숫자 필드(`Cac1`/`Oae2`/`Hab1`/`Uau2`/`Isx1`)에 있다.
- **🔴 I00Y — 원작 자체가 어긋나 있다.** 불사조의 깃털은 툴팁이 「체력회복 0.3 증가」인데
  연결 능력 A17M의 실제 필드는 `Uau2=0.25`다. 「필드가 진실」 원칙을 여러 번 확인한 것을
  감안하면 **수치 필드를 신설할 때는 0.25**를 쓴다. 우리 툴팁은 원작 툴팁과 같으니 그대로 뒀다.
- **필드로 직접 검증 완료(툴팁과 일치)**: I007(0.15) · I00N(0.05) · I00Q(0.12) · I00H(0.12) ·
  I00R(0.04) · I00V(0.5) · I00W(0.25) · I005(0.01)
- **수치 확인 불가**: I001(`AIaa`)·I00B·I008(`Arpb`)은 스톡 능력이라 `w3a`에 값 자체가 없다.

## 9. 사장님 결정이 필요한 것

1. **창작 아이템 2개를 어디서 줄까** — 라운드 보상 / 스토리 클리어 / 조합 /
   아니면 조합식에서 아이템 요구를 빼기. 유닛 3기가 여기 걸려 있고 **가장 싸다.**
2. **아이템 시스템을 살릴까** — 살리려면 ①메타몽 지급 경로 ②`ItemData` 수치 필드 신설
   ③인벤토리 UI ④플레이어별 인벤토리, **네 가지를 다** 해야 한다. 작은 일이 아니다.
