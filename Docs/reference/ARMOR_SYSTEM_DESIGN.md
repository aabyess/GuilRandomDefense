# 방어력·데미지 타입 시스템 (현행)

**원작 `ORD11.089.w3x`에서 확인한 값으로 구현돼 있다.** 추출·검증 기록은 `UNIT_STATS_RESEARCH.md`.

## 지금 이렇게 되어 있다

```
DamageType   None / AD / AP                                무엇으로 감폭하느냐 (AD|AP = 겸용)
AttackType   Unassigned / Normal / Pierce / Siege / Hero / Chaos / Magic / Spells
                                                           배율표의 어느 행을 타느냐
ArmorType    Unassigned / Normal / Large / Fort / Hero      적의 갑옷
```

**`DamageType`과 `AttackType`은 직교한다.** `DamageType`은 *방어력을 타느냐 마법방어 배율을 타느냐*를
정하고, `AttackType`은 그 위에 곱할 *상성 행*을 고른다. 원작 `war3mapMisc.txt`의 **일곱 행 그대로**다 —
앞의 다섯은 물리, 뒤의 둘은 마법이다. `AD+AP`는 여전히 물리로 취급한다(어떻게 겸하는지 미확인).

### 배율표 (원작 `war3mapMisc.txt` 그대로 — 7행 전수 대조 완료)

| 공격 \ 방어 | Large | Fort | Normal | Hero | |
|---|---|---|---|---|---|
| Normal | 1.00 | **0.75** | **1.25** | 0.90 | 물리 |
| Pierce | **1.25** | 1.00 | **0.75** | 0.90 | 물리 |
| Siege | **0.75** | **1.25** | 1.00 | 0.80 | 물리 |
| Hero | 1.05 | 1.05 | 1.05 | 1.05 | 물리 |
| Chaos | 1.00 | 1.00 | 1.00 | 1.00 | 물리 |
| **Magic** | 1.00 | 1.00 | 1.00 | **0.80** | 마법 — 평타가 마법인 유닛 |
| **Spells** | **0.85** | **0.90** | 1.00 | **0.80** | 마법 — 능력·스킬 피해 |

앞 셋이 **가위바위보다.** Normal→Normal, Siege→Fort, Pierce→Large가 각각 1.25이고 서로 물린다.

**마법도 이 표를 탄다.** 원작은 마법 방어력(워크3 `Aegr`)과 이 표를 **둘 다** 적용한다.
`Magic`은 방어 타입에 거의 무관하고(hero만 0.80), **`Spells`만 large·fort를 깎는다** —
원작이 평타 마법과 스킬 마법을 다르게 취급한다.

> ⚠️ **옛 버그와 헷갈리지 말 것.** 예전엔 마법이 **물리 행**(normal/pierce/siege…)을 탔다.
> 그건 마법 방어 배율과 물리 상성을 둘 다 맞는 것이라 틀렸다. 지금은 **마법 행**을 탄다.
> `DamageTable.RowMatches(DamageType, AttackType)`가 그 짝을 검사하고,
> 안 맞으면 **상성표를 건너뛰고 경고를 한 번 찍는다.**

### 계산 순서 (`EnemyDummy.TakeDamage`)

```
AP     : 원본 × 마법방어배율
그 외  : 원본 × (1−방무뎀비율) × 방어력감폭 + 원본 × 방무뎀비율
공통   : 그 결과 × 상성표[AttackType][ArmorType]      ← 짝이 맞을 때만
방어력감폭 = 워크3 공식, 방깎 하한 −20
```

### 어느 피해원이 어느 행인가

| 피해원 | 코드 | 행 |
|---|---|---|
| 유닛 평타 | `UnitAttacker.cs` — `UnitData.attackType` 그대로 | 유닛이 정한 행 |
| 도움소 스킬 | `SupportShop.cs` 4곳 — `AttackType.Spells` 고정 | **`Spells`** |

**유닛 239종은 전부 `Unassigned`**라 평타는 아직 어느 행도 안 탄다(배율 1.0).
평타가 마법인 유닛을 채울 땐 `damageType = AP` **와** `attackType = Magic`을 **짝으로** 넣어야 한다.

### 왜 `Unassigned`가 기본인가

기본을 `Normal`로 뒀으면 분류 안 한 적이 전부 「normal 갑옷」이 되고, 우리 유닛은 전부 물리라
**배율 1.25가 붙는다** — 아무것도 안 했는데 피해가 25% 오른다. `Unassigned`는 배율 1.0이라
**분류 전까지 동작이 그대로다.**

`Unassigned`는 **우리 것이지 원작에 있는 게 아니다.** 원작은 명시 안 하면 베이스 유닛 값을 상속한다
(1,559종 중 119종만 명시). 분류를 마치면 없애도 된다.

### 「보스」 방어 타입은 없앴다

원작에 그런 타입이 없다. **원작 보스는 11종 전부 `large`를 쓴다** — 「보스」는 방어 타입이 아니라
베이스 유닛(`otbk` vs 라인몹 `ogru`)으로 갈린다. `hero` 방어를 쓰는 건 보스가 아니라
**고레벨 라인몹 5종**이다.

**적 에셋 89개 중 아무도 `armorType`을 저장하지 않아서** 값을 지워도 밀릴 데이터가 없었다(확인함).

`Assets/Prefabs/MobPrefab.prefab`의 `EnemyDummy.damageTable`에 `DamageTable.asset`을 연결했다.
그전까지는 `null`이라 표를 고쳐도 아무 일도 안 일어났다.

→ **표준표를 베끼지 말고 우리가 정한다.** 아래가 그 제안이다.

### ⚠️ 먼저 짚을 것 — 보스가 어려운 이유는 **방어 타입이 아닐 가능성이 크다**

원작에서 확인된 유일한 "타입성 차이"는 **보스 딜링이 따로 필요하다**는 것이다
(*"보잡용 유닛 = 보스를 잡는 데 특화된 능력을 가진 유닛"*, *"다른 패가 보스를 잡을 수 없는 상황에서도 잡을 수 있게"*).

**그런데 조합표의 보잡 능력은 전부 「최대체력 비례 피해」다**:
`보잡(전체체력5%)` 김용태 · `보잡(전체체력4%)` 최상호 · `보스(전체체력5%)` 이이삭.

**배율표가 문제라면 해법은 "배율이 좋은 타입"이지 "%체력 피해"가 아니다.**
%체력 피해는 **체력이 압도적으로 큰 대상**에 대한 해법이다.
→ **보스 난이도는 방어 타입이 아니라 체력 규모에서 나올 가능성이 크다** [추정 · 중간].

이 판단이 아래 제안의 핵심이다: **타입 축은 만들되, 처음엔 배율을 전부 1.0으로 두고
난이도는 체력·방어력 수치로 조절한다.** 표를 먼저 채우면 근거 없는 숫자로 밸런싱하게 된다.

## 2. 방어 타입 — **2종으로 시작할 것을 제안한다**

```csharp
public enum ArmorType { Normal, Boss }
```

### N = 2인 이유

1. **우리 데이터가 이미 가진 구분축이 그것뿐이다.** `EnemyData.isBoss`가 이미 있고,
   `ROUNDS.md`의 적 75종은 **일반 66 / 보스 9**(10·20·30·40·50·60·65·70·75)로 정확히 갈린다(실측).
   **새 축을 만드는 게 아니라 이미 있는 축에 이름을 주는 것이다.**
2. **원작에서 확인된 타입성 차이가 "보스냐 아니냐" 하나뿐이다.** 그 외에는 근거가 없다.
   근거 없는 타입을 만들면 값을 채울 때 전부 지어내야 한다 — 지금 스탯이 그래서 지어낸 값이다.
3. **표 크기.** 3 × 2 = **6칸**. 사람이 머리에 담고 손으로 굴릴 수 있다.
   워크3 표준(7종)을 따르면 3 × 7 = **21칸**이고, 그중 20칸은 근거가 없다.
4. **확장이 안전하다.** enum **맨 뒤에** 값을 붙이고 표에 열을 더하면 된다.
   직렬화된 값이 안 밀린다(`UnitGrade`에서 이미 겪은 그 문제다).

### 배율표 (초기값)

| | `Normal` | `Boss` |
|---|---|---|
| **AD** | 1.0 | 1.0 |
| **AP** | 1.0 | 1.0 |
| **AD+AP** | 1.0 | 1.0 |

**전부 1.0으로 시작한다.** 축은 만들되 값은 근거가 생길 때 채운다.
지금 숫자를 넣으면 그게 곧 밸런스가 되고, 나중에 원작 수치가 나와도 되돌리기 어렵다.

> `AD+AP`가 물리·마법을 **어떻게** 겸하는지 미기재라, 표에서는 일단 한 줄로 둔다.
> "평타 물리 + 스킬 마법"이라면 애초에 배율표 한 줄이 아니라 **피해원마다 타입이 따로** 붙어야 한다(§7 질문 3).

## 4. 계산 순서

**피해 계산은 `EnemyDummy.TakeDamage` 안에서 한다. 공격하는 쪽이 아니다.**

이유: 피해원이 여럿이다 — `UnitAttacker`(평타), `SupportShop`(범위 스킬 2곳). 지금 4개 호출부가 있고
앞으로 는다. **감폭을 공격자 쪽에 두면 새 피해원이 생길 때마다 다시 구현해야 하고, 언젠가 하나가 빠진다.**
방어력은 적이 가진 것이니 적이 적용하는 게 맞다.

```
1. 원본 피해            attacker가 계산해서 넘김 (특성 딜증가는 이미 반영됨)
2. 방깎 적용            유효방어력 = max(−20, 적.방어력 − 누적방깎)
3. 방어력 감폭          AD  : 배율 = armorMul(유효방어력)
                       AP  : 건너뜀 (방어력 무시)
                       AD+AP: §7 질문 3 확정 전까지 AD와 동일 취급
                       방무뎀: 건너뜀 (능력이 켜져 있으면)
4. 타입 배율            × 배율표[공격타입][적.방어타입]     ← 지금은 전부 1.0
5. 최종 피해            hp에서 차감
```

### 감폭 공식 — **워크래프트3 그대로** (`UNIT_STATS_RESEARCH.md` 검산 완료)
```csharp
static float ArmorMultiplier(float armor) =>
    armor >= 0f ? 1f - (0.06f * armor) / (1f + 0.06f * armor)
                : 2f - Mathf.Pow(0.94f, -armor);
```
| 방어력 | −20 | −10 | −5 | 0 | 5 | 10 | 20 |
|---|---|---|---|---|---|---|---|
| 배율 | 1.710 | 1.461 | 1.266 | 1.000 | 0.769 | 0.625 | 0.455 |

### 방깎 하한 = **−20**
원작: *"방어력이 -20이 되면 71%의 데미지가 추가로 들어가며 **이 이상의 방어력 감소는 불필요**"*.
→ 상수 하나로 둔다. **하한이 없으면 방깎 유닛을 쌓을수록 무한히 세지고 밸런싱이 무너진다.**

### 호출부 변경 — 4곳
```csharp
// 지금
public void TakeDamage(float amount, int killerPlayerId)
// 바꿀 것
public void TakeDamage(float amount, DamageType type, int killerPlayerId, bool ignoresArmor = false)
```
`UnitAttacker` 2곳(적·게이트) · `SupportShop` 2곳(범위·지속).
**기본값을 주지 않는다** — 기본 AD로 두면 새 피해원이 조용히 물리로 들어가고, 그걸 나중에 못 찾는다.
(`DestructibleGate.TakeDamage`는 방어력 개념이 없으므로 그대로 둔다.)

## 5. `방무뎀`·`폭발형`은 타입이 아니라 능력이다

| | 근거 |
|---|---|
| `방무뎀` | `이승우`의 **등급 표기는 `(AP)`**인데 능력에 `방무뎀(30%)`이 따로 붙는다 [이미지] |
| `폭발형` | 조합표에 `폭뎀30%`로 나온다. 11버전 추가 범주 [원작] |

→ **`DamageType`에 넣지 않는다.** 계산 3단계에 `ignoresArmor` 훅만 두고,
   어떤 능력이 그걸 켜는지는 **유닛 능력 시스템이 생길 때** 연결한다.

⚠️ **`방무뎀(30%)`의 30%가 무엇인지 모른다**(§7 질문 2). 그전까지 이 훅은 **꺼둔 채로 둔다.**

## 6. 이 설계로 같이 살아나는 것

| 지금 죽어 있는 것 | 살아나나 |
|---|---|
| `UnitData.damageType` (234종 전부 AD, 읽는 코드 없음) | ✅ 3단계가 읽는다 |
| **`UnitTraitData.ArmorShred`**(방깎) — 주석: *"EnemyDummy에 방어력 필드 없음"* | ✅ `armorShred`에 쌓인다 |
| 조합표의 `방깍(45)` · `마방깍오라(9%)` 능력 | ✅ 같은 필드로 들어간다 |
| `방무뎀` | ⏸ 훅만. 30%의 뜻 확정 후 |

**방어력 필드 하나가 AD/AP·방깎·방무뎀을 한꺼번에 연다.** 그게 이 작업의 값어치다.

### ✅ 해소 — 마법방어력 (2026-09-04 구현)

**아래는 "근거가 없어 뺐다"고 쓴 것인데, 원본에 근거가 있었다.** 지금은 들어가 있다:
`EnemyData.magicArmorMultiplier`(기본 1.0) · `EnemyDummy.EffectiveMagicMultiplier` ·
`TraitEffectKind.MagicArmorShred`. **AP 피해에만 곱한다.**

내가 *"넣으면 「마뎀은 방어력 무시」와 충돌한다"*고 본 것은 **둘 다 참이라서** 풀렸다 —
마딜은 **물리** 방어력을 무시하고, **마법** 방어력은 별개 축으로 받는다.

<details><summary>당시에 뺀 이유 (기록)</summary>

### ⚠️ 이 설계로도 **안 살아나는 것**: 마법방어력

조합표에 `마방깍오라`가 따로 있다 = **마법방어력이 별개로 존재한다** [이미지].
그런데 위 설계는 **방어력 하나만** 둔다. AP가 방어력을 무시하니 마법방어는 **AP를 감폭하는 별개 수치**여야 한다.

**일부러 뺐다.** 마법방어를 넣으면 AP도 감폭 대상이 되어 *"마뎀은 방어력 무시"*라는 원작 서술과
어떻게 공존하는지부터 정해야 하는데, 그 근거가 없다. **§7 질문 4로 올린다.**

</details>

## 7. 사장님 확인이 필요한 것

1. **방어 타입을 2종(일반/보스)으로 시작해도 됩니까?** 더 필요하면 무엇이 있어야 합니까?
2. **`방무뎀(30%)`의 30%는 무엇입니까?** 피해의 30%가 방어 무시입니까, 방어력을 30% 무시입니까?
3. ~~`방무뎀(30%)`의 30%~~ → **해소.** 용어집: "평타가 방어를 무시하는 %". 유닛별 수치(30/45/50%).
4. ~~마법방어력을 둡니까~~ → **해소.** 있다. 2026-09-04 구현.
5. **남은 과제**: 능력별 방깎 상한(−75/−80, 7·9·10회)을 `TraitEffect`가 담지 못한다.
   **지금 넣지 않는다** — 유닛별 상한 값을 채울 이름 매핑이 아직 없다.
6. **`AD+AP`는 어떻게 겸합니까?** 평타는 물리·스킬은 마법입니까, 아니면 한 번의 피해를 절반씩 나눕니까?
   → 전자면 **배율표가 아니라 피해원마다 타입을 붙이는** 구조가 됩니다. 설계가 갈립니다.
4. **마법방어력을 둡니까?** 조합표에 `마방깍`이 있으니 원작엔 있습니다.
   둔다면 *"마뎀은 방어력 무시"*와 어떻게 공존합니까 — **물리방어와 마법방어가 별개 수치**라는 뜻입니까?
5. ~~적 75종의 방어력 수치~~ → **원작 답이 나왔다. 그러나 지금 넣지 않는다** (2026-09-04, 리서치담당)

   | | R1 | R75 |
   |---|---|---|
   | 몹 방어력 | 0 | **81** — 대략 라운드 수와 비슷 |
   | 보스 방어력 | 13 | **395** — 몹의 4~5배 |
   | 몹 HP | 135 | 16,210,000 (라운드당 ×1.17) |

   **공식이 아니라 원작자가 하나씩 적어넣은 수기값**이고, 위는 거기서 읽은 추세다.

   ⚠️ **유닛 공격력과 한 세트라 따로 넣으면 안 된다.** 전에 적 방어력만 원작으로 넣었다가
   R75 적 하나 잡는 데 75초가 걸렸다(원래 3초). 원작 몹 HP R75가 16,210,000인데 우리는
   88,237이다 — **184배 차이**라, 유닛 공격력이 같은 배수로 올라가야 성립한다.
   그건 **이름 매핑(원작 1,559종 ↔ 우리 239종)이 풀려야** 가능하다 (리서치담당 최우선 과제).

   → **방어력 「수치」는 보류. 방어 「타입」(`armorType`)은 별개 축이라 따로 간다** (§9).
