# 평타 강화 훅 — 설계안 (미구현, 승인 대기)

> PM 지시(2026-09-04): 구현담당3이 원작 능력 1,628개 중 최대 템플릿(ACbh, "Bash" 469개/29%)을
> 찾았다 — 원작은 평타를 안 버리고 발동 확률형으로 5~50배까지 뻥튀기해서 쓰는데, 우리
> `UnitAttacker`엔 이 훅을 끼울 자리 자체가 없다. **이 문서는 설계안만이다 — 구현하지 않았다.**
> 사장님 승인 후 진행한다.

## 1. 원작 메커니즘 — 워크3 표준 Bash

`ACbh` 기반 469종은 워크3 엔진 내장 "Bash" 어빌리티 그대로다(커스텀 트리거가 아니라 필드
`Hbh1`/`Hbh2`/`Hbh3`로 동작하는 데이터형 어빌리티). 평타가 적중할 때마다:

```
Hbh1 = 발동 확률(%)
Hbh2 = 피해 배수(없으면 배수 없음, 즉 1배 취급)
Hbh3 = 추가 고정 피해
```

**발동하면 평타 적중에 더해 "배수×평타피해 + 고정피해"만큼의 별도 피해 인스턴스가 추가로 들어간다**
(평타를 대체하는 게 아니라 평타 위에 얹힌다 — 구현담당3 DPS 검산과 일치: `평균 = A + p×((M−1)·A + B)`).

3. **등급을 타는 건 "평타 대비 추가피해 배수" 하나뿐**이고, 하위(1.2~1.6배)에서 상위(10~12.5배)로
   뚜렷하게 올라간다. **절대값(Hbh3)은 원작 자체 공격력 스케일이라 그대로 못 옮긴다** — 반드시
   "그 유닛의 평타 대비 비율"로 환산해서 옮겨야 한다([[name-mapping-impossible]]과 같은 이유:
   두 게임의 절대 스케일이 다르므로 비율만 의미가 있다).

## 2. ⚠️ 미확정 — 착수 전 반드시 확인

- **`Hbh3`(추가피해)가 방어력 감폭을 타는가?** 워크3 표준 Bash는 추가피해가 평타와 같은 피해
  파이프라인을 타므로(같은 공격 타입) **방어력에 걸린다**는 게 기본 가정이지만, 구현담당3이
  트리거 오버라이드 여부를 리서치담당에게 확인 요청해뒀다. **이 답이 나와야 §3의 훅 위치가
  확정된다.**
- **`w3a` 정의값과 실제 트리거 적용값이 다를 수 있다** — 확인 중.

이 둘이 풀리기 전까지는 아래 설계를 "방어력을 탄다"는 가정으로 작성했다. 반증되면 §3만 고치면 된다.

## 3. 어디에 끼우나

`UnitAttacker.Update()`, 기존 평타 호출 바로 뒤:

```csharp
// 기존 (UnitAttacker.cs:220 부근)
target.TakeDamage(AttackDamage, DamageTypeOf, AttackTypeOf, owner?.OwnerId ?? -1);

// 추가 — 평타가 방금 들어간 "같은 대상"에게, 확률로 별도 피해 인스턴스
if (Random.value < critChance)
{
    float bonus = AttackDamage * critDamageMultiplier + critBonusDamage;
    target.TakeDamage(bonus, DamageTypeOf, AttackTypeOf, owner?.OwnerId ?? -1);
}
```

**같은 `DamageType`/`AttackType`으로, 평타와 별개의 `TakeDamage` 호출**을 쓴다 — 이러면
`EnemyDummy.MitigatedDamage`의 방어력 감폭·상성표를 평타와 완전히 동일하게 통과한다(§2의
가정이 맞다면 이게 원작과 같은 동작이다). AP 유닛이면 자동으로 방어력을 무시하는 것도 평타와
동일하게 따라간다 — 별도 분기가 필요 없다.

## 4. 데이터를 어디에 두나 — `UnitData` 필드 3개 + 읽는 코드까지

`SupportSkillData`(도움소)가 이미 쓰는 패턴 그대로 `UnitData`에 필드만 추가한다. 별도 에셋
타입은 안 만든다 — 유닛 하나에 값 하나씩이라 도움소 스킬처럼 여러 개를 조합할 필요가 없다.

```csharp
[Header("평타 강화(원작 Bash) — chance가 0이면 완전히 비활성")]
public float critChance;              // 0~1. 기본 0 — 값을 안 채우면 아무 일도 안 일어난다.
public float critDamageMultiplier = 1f; // 배수. chance=0이면 안 쓰이지만 안전하게 1로 둔다.
public float critBonusDamage;         // 고정 추가피해. 기본 0.
```

**"필드만 만들고 아무도 안 읽으면 `UnitData.skill`과 같은 껍데기가 된다"는 오늘의 교훈을
그대로 반영** — §3의 `UnitAttacker.Update()` 코드가 이 필드를 읽는 지점까지 이 설계에 포함된다.
필드 추가와 읽는 코드는 **같은 커밋**이어야 한다(스킬 필드처럼 따로 떨어지면 안 됨).

## 5. 기본값 안전성

`critChance = 0f`(기본값) → `Random.value < 0f`는 항상 거짓 → 추가 `TakeDamage` 호출 자체가
안 일어난다. **239종 전부 이 필드를 안 채운 상태로 커밋해도 게임 동작이 100% 그대로다** —
`critDamageMultiplier`/`critBonusDamage`가 어떤 값이든 `critChance=0`이면 영향 없다(ARMOR_SYSTEM_DESIGN.md
1~5단계와 같은 "회귀 위험 낮음" 패턴).

## 6. 원작 값을 우리 239종에 어떻게 붙이나 (다음 단계 — 이번엔 설계만)

[[name-mapping-impossible]]의 순위 배정 방식을 그대로 쓰되, 이번엔 두 층으로 나눠 배정한다:

1. **보유 여부(인시던스)** — 등급별 보유율(흔함 0% ~ 희귀함 44%)만큼만 우리 로스터에서도
   해당 등급 내 일부 유닛에 `critChance>0`을 준다(전 유닛에 안 준다). 보유율 자체를 등급별로
   그대로 옮긴다 — 발동 "확률"(20%)은 등급 무관 고정값을 쓴다.
2. **배수·추가피해** — 보유하는 유닛들 안에서 **"평타 대비 추가피해 배수"**(1.2배~12.5배,
   등급별 표 §1)를 등급 내 순위/분위수로 배정한다. 절대 `Hbh3` 값이 아니라 이 비율에 우리
   유닛의 실제 `attackPower`를 곱해서 `critBonusDamage`를 역산한다. `critDamageMultiplier`는
   등급을 안 타므로 등급별 중앙값(2~8, 표 §1)을 그대로 쓰거나, 더 단순하게 `critDamageMultiplier=1`
   로 고정하고 배수분까지 전부 `critBonusDamage`(비율 환산)에 흡수시켜도 된다 — **후자가 필드
   하나를 덜 다뤄서 더 단순하다**(사장님/PM 판단 필요).

**불멸(0.9배)·특수함(32.3배)은 표본이 작아 이상치일 수 있다** — 구현담당3이 신뢰하지 말라고
명시했으므로, 실제 배정 시엔 인접 등급 값으로 스무딩하거나 별도 재확인이 필요하다.

## 7. 이번 조사에서 다루지 않은 것

- **스턴**(`adur`/`ahdu`) — 원작 Bash 인스턴스 다수가 짧은 스턴을 동반하지만, 이번 지시 범위는
  "치명타 확률/배수/추가피해"였다. 넣을지는 별도 판단.
- **물리/마법 피해 타입 혼재** — 일부 Bash 툴팁이 "물리"/"마법"을 명시하는데, 이건 어빌리티
  필드가 아니라 유닛 자신의 평타 `DamageType`을 그대로 물려받는 것으로 보인다(엔진상 Bash
  추가피해는 별도 타입 필드가 없다) — §3 설계가 `DamageTypeOf`를 그대로 재사용하는 이유다.

## 8. 구현 순서 (승인 후)

1. `UnitData`에 필드 3개 추가(전부 중립 기본값 — 게임 동작 불변)
2. `UnitAttacker.Update()`에 §3 코드 추가(같은 커밋)
3. §2의 방어력 통과 여부 확인이 나온 뒤, §6의 인시던스+비율 배정으로 239종에 값 채우기
   (별도 커밋 — 밸런스가 실제로 바뀌는 지점이라 이번에도 처치시간/레인적재 비교표 필요)
