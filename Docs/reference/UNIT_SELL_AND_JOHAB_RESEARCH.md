> PM 지시로 두 시스템만 `war3map.j`·`war3map.w3u`·`war3map.w3q` 직접 읽어서 조사. **구현 안 함, 조사만.**
> 소스: 이 세션 scratchpad에 이미 있던 `war3map.j`(5.3MB, 트리거 전체) + `war3map.w3u`(유닛) +

## ① 유닛 판매 — **원작에 이름이 겹치는 서로 다른 두 시스템이 있다**

리서치담당이 인용한 "판매 → 누적 포인트, 3포인트마다 랜덤위습"이 정확히 뭔지 파보니, **`unique_sell1~7`
이라는 이름의 트리거군**이 나왔다. 그런데 이걸 파다가 **완전히 다른 진짜 "판매"(`EVENT_PLAYER_UNIT_SELL`)
시스템도 발견했다** — 해적단이 걸려있는 건 이쪽이다. 둘을 섞으면 안 돼서 나눠 적는다.

### A. `unique_sell1~7` — 이름은 "판매"지만 실제로는 **자폭형 스킬**

`EVENT_PLAYER_UNIT_SPELL_EFFECT`(스킬 시전) 이벤트다. WC3의 진짜 "판매"가 아니라, **유닛이 전용
스킬을 쓰면 그 유닛이 죽고 보상을 받는** 구조다. 원작자가 트리거 이름을 "sell"로 붙였을 뿐이다.

| 트리거 | 스킬ID | 효과 |
|---|---|---|
| unique_sell | A09G | 자폭, `Sell_Point1` 카운터+1. **3에 도달하면** 카운터 리셋 + 랜덤위습(`e0IX`) 1기, 35% 확률로 목재1. **이게 리서치담당이 인용한 그 시스템이다.** |
| unique_sell2 | A0B8 | 자폭, 50% 성공 시 "안흔함 판매성공"+랜덤위습1, 실패 시 "안흔함 판매실패"(아무것도 없음). 별도 20% 확률로 목재1(성공/실패와 무관하게 굴림) |
| unique_sell3 | A0BA | 자폭, 무조건 랜덤위습1 + 35% 확률 목재1 |
| unique_sell4 | A0B9 | 자폭, 무조건 랜덤위습2 + 목재1 (확률 없음) |
| unique_sell5 | A0BB | 자폭, 무조건 흔함선택위습(`e018`)1 + 목재1 |
| unique_sell6 | A080 | 자폭, 37% 성공 시 "노획물 판매성공"+랜덤위습1, 그중 40%가 추가로 골드100+목재1. 실패(63%) 시 아무것도 없음 |
| unique_sell7 | A0OE | 자폭, 무조건 흔함선택위습1. **텍스트는 "특성포인트1 획득"인데 실제 코드는 `PLAYER_STATE_RESOURCE_FOOD_USED`를 조정한다** — 텍스트와 실제 효과가 어긋난다. 원작 자체의 표시 버그로 보이나 확정은 못 했다. |

**이름 매핑**: 이 7개 스킬(A09G 등)을 가진 유닛을 `war3map.w3u`(238종 전체)에서 찾아봤는데 **하나도
없었다**. 즉 어느 이름의 캐릭터가 이 스킬을 갖는지 특정을 못 한다 — 아마 특정 캐릭터 고유 스킬이 아니라
런타임에 `UnitAddAbilityBJ`로 동적으로 붙여주는 구조로 보인다(다른 트리거들에서 이 패턴을 여러 번
봤다). **이름 매핑이 막힌다.** 이걸 그대로 이식하려면 "이 스킬을 가진 원작 유닛이 누구인지" 없이,
효과 표만 보고 우리 쪽에서 새로 설계해야 한다.

### B. 진짜 `EVENT_PLAYER_UNIT_SELL` — **해적단이 걸려있는 쪽이 이거다**

WC3의 진짜 "상점에 유닛을 판다" 이벤트(`GetSoldUnit()`)다. **전부 이름 없는 익명 토큰 유닛**을
판매 대상으로 쓴다 — 확인한 4종 전부 `unam`(이름)이 비어있고 base가 `hfoo`(WC3 기본 농장류
베이스)다. 즉 캐릭터가 아니라 "팔면 뭔가 나오는 소모품 유닛"이다.

| 판매 대상 | 트리거 | 효과 |
|---|---|---|
| H0AZ | Money_Gemble_3 | 41% 확률로 500~4500골드(누적 35000골드 도달 시 "돈도박-고급 졸업" — 유닛 교체 + 테크 연구), 실패 시 300~400골드 위로금 |
| h0AK | Money_trade | 무조건 목재1 |
| h0AL | Money_trade2 | 무조건 **특성포인트1** (표시 텍스트와 코드가 일치, unique_sell7과 달리 정상) |
| H0B0 | unique_unit_create | 4% 확률로 고정 희귀유닛(`h05X`), 아니면 1/38 확률로 `Random_UniqueSpecial` 그룹에서 뽑기, 그것도 아니면 `Random4` 그룹에서 뽑아 리롤 스킬(A0VX) 부여 |
| **H0AQ** | **Quest_waporu** | **60초 타이머 + 미니보스 소환 — 해적단 퀘스트가 여기 걸려있다.** 스테이지 머신(`Stage[0]→[1]→[2]`)으로 구현돼 있어 세부는 더 못 팠다. |

`Money_Gemble_2`도 같은 계열로 보이나(조건 함수를 못 찾아 완전히 못 읽었다) `RemoveUnit(GetSoldUnit())`
+30골드 + `johabzone`(아래 ②) 위치에 `unit_dobakGroup1`에서 뽑은 유닛을 스폰하는 걸 확인했다.

**이름 매핑**: **필요 없다.** 전부 익명 토큰이고, "이게 무슨 캐릭터냐"를 물을 필요 자체가 없는 구조다.
오히려 **우리 도박소(GamblingShop)의 "자원칸에 유닛을 놓으면 발동" 패턴과 골격이 거의 같다** — 판매
버튼 대신 "특정 칸에 갖다 놓기"로 이미 우리가 흉내 낸 셈이라, 새로 만들 게 있다면 "그 칸에 놓을 토큰
유닛 종류를 늘리는" 정도로 보인다.

### 결론 — PM 질문에 답

- **판매가로 무엇을 받나**: 시스템마다 다르다(위 두 표). 골드·목재·특성포인트·랜덤위습·희귀유닛 전부 등장.
- **`unique_sell` 1~7이 왜 일곱 개인가**: 등급별도 포인트구간별도 아니고, **서로 다른 7개의 독립
  스킬**이다(A안 표 참고) — 아마 서로 다른 유닛/상황에 붙는 각기 다른 "팔기 스킬" 세트로 보인다.
- **누적 포인트가 어디 저장되나**: `udg_Sell_Point1[플레이어]` — 세이브 시스템의 `PlayPoint`와는
  **별개 변수**다. `PlayPoint`는 게임 클리어 누적(세션을 넘어 저장), `Sell_Point1`은 이 판매 스킬
  전용 카운터로 3에서 리셋되는 인게임 값이다.
- **판매하면 유닛이 사라지나**: 그렇다. A는 전부 `KillUnit`, B는 전부 `RemoveUnit(GetSoldUnit())` —
  **되사기 없음**, 둘 다 확정 소멸이다.
- **연금술(분해)과 겹치나**: 겹치지 않는 걸로 보인다. 연금술은 우리 쪽에서 새로 설계한 "유닛 없애고
  자원 회수" 경로이고, 위 A/B는 원작에 있는 별개 메커니즘이다. 다만 **"유닛을 소모해서 뭔가 받는다"는
  기능적 성격 자체는 같다** — 셋(연금술/A/B)을 게임 안에 다 넣으면 유저 입장에서 "유닛을 없애는 방법이
  왜 세 개나 있냐"는 혼란이 생길 수 있어, 사장님이 통합할지 구분할지 정할 필요가 있어 보인다.

## ② 항법(`onedill_Tech`) — 진짜 자리를 찾았다, 그런데 Gold_Plus는 아니다

### 정체 — 영웅이 아니라 **건물**

`H0C4` = **"항해일지"**(`unam`: `|cffc0c0c0항해일지|r`), 이동 불가, `umdl`이 건물 모델
(`buildings\other\MagicVault\MagicVault.mdl`)이다. **영웅 유닛이 아니라 건물**이고, WC3의
"영웅이 스킬 배우듯 건물이 능력을 학습하는" 구조(`uhab` 필드에 학습 가능 스킬 목록)를 쓴다.
`EVENT_UNIT_HERO_SKILL`(스킬 학습) 이벤트로 감지한다.

### 5지선다다 — "패왕의길/연합세력" 둘만이 아니다

`Trig_onedill_Tech_Actions`를 직접 읽었다. **다섯 개 중 하나만 고르는 구조**다(전부 스위치식 —
같은 트리거 안에서 조건 5개를 차례로 검사):

| 선택 | 스킬ID | 실제 효과(코드 기준) |
|---|---|---|
| 패왕의길 | A15W | `Damage_level_Fixed[플레이어] += 2` (플레이어 전역 데미지레벨 +2 — 정확한 환산식은 이번 조사로 못 풂) + R02E 테크 등록 |
| 연합세력 | (학습 시 A0Z6 부여 후 제거) | `Tech_union[플레이어] = true` — 불리언 플래그만 세팅, 실제 효과는 이 트리거 밖 다른 곳에서 참조하는 걸로 보이나 이번 조사 범위 밖 |
| 도박광 | (A0ZY) | `Dobak_Tech_int[플레이어] = 1` — **`unique_rerole` 트리거에서 직접 확인**: 리롤 성공 실패율이 `20 - Dobak_Tech_int×80`이라 1이면 사실상 **리롤 100% 성공**, 리롤 가능 횟수도 `2 + Dobak_Tech_int`로 **2→3회** |
| 도움소 강화 | (A17D) | 도움소(`Manso`) 건물의 능력 3개(`A0ID`,`AOeq`,`A0JR`) 레벨을 1→2로. R037 테크도 등록(공격력+250/공속+3%, 대상은 "희귀함 타입" — 다만 이 텍스트가 다른 테크 R036에도 그대로 복붙돼 있어서 실제 효과인지 원작 자체의 템플릿 재사용 흔적인지 불확실) |
| 도움소 잠금 | (A17E) | `Tech_No_support[플레이어] = true` + R036 테크 등록(마나 -900 페널티 필드 — 어느 대상에 적용되는지는 못 풂) |

`H0C4`의 `uhab` 필드(학습 가능 스킬 목록)엔 `A15W,A15L,A15X,A15K,A15M`이 적혀 있는데, 트리거
조건이 검사하는 ID는 `A15W`(패왕의길만 일치) 외 나머지 넷은 다르다(`A0Z6`,`A0ZY`,`A17D`,`A17E`) —
**학습 시점에 스킬이 스왑되는 구조로 보이나 정확한 매커니즘은 못 풀었다.** 5개라는 것과 각각의 효과는
확실하다.

### Gold_Plus는 여기서 안 나온다 — **PM 가설과 다른 결과**

다섯 갈래 어디에도 골드 배율/추가 필드가 없다. `Damage_level_Fixed`(패왕의길), `Tech_union`(연합세력),
`Dobak_Tech_int`(도박광, 리롤 전용), 도움소 강화/잠금 — **전부 골드와 무관**하다. 즉 이전에 막혔던
"Gold_Plus +0.2/+0.3/+0.6 (나미 전설/영원함나미/버기/수배서)"는 **이 항법 시스템의 정답이 아니다**.
그 넷은 여전히 별개로 막힌 채 남는다 — 이름이 "항법"이라고 같은 시스템이라 단정하면 안 됐다.

### 이름 매핑 필요한가 — **필요 없다**

H0C4가 캐릭터가 아니라 건물이고, 다섯 선택지 전부 특정 유닛 이름과 무관한 **전역 플레이어 플래그/
테크**다. 다만 **원작 UI 자체가 "건물이 영웅스킬 배우듯 하나를 고른다"는 WC3 특유 구조**라, 그대로
옮기려면 최소 "1회용 5지선다 전역 선택" UI가 필요하다 — 우리가 이미 만든 백수생활 3지선다
위습(`InterludeGate`)과 골격이 비슷해서, 그 패턴을 5지선다로 늘리는 정도면 될 것 같다(구현은 안 함,
가능성만 적어둔다).

`johabzone[1~4]`(항해일지와 이름이 겹치지만 관계는 확인 못함)는 이 시스템과 무관하게 **플레이어별
고정 좌표 4개**였다 — `Money_Gemble_2`가 도박 보상 유닛을 스폰하는 위치로 쓰는 게 유일한 용례였다.
"항법 선택 결과에 따라 스폰 위치가 바뀐다"는 근거는 못 찾았다.

## 조사 방법 메모

`Tools/w3x/`의 기존 파서(`w3u.py`,`w3a.py`,`wts.py`)에 더해 이번에 `w3q.py`로 `war3map.w3q`(업그레이드)를
처음 열어봤다 — R036/R037 필드에서 `gub1`(설명 텍스트)이 서로 다른 테크(R036=마나페널티, R037=도움소강화)에
**똑같이 복붙**돼 있는 걸 발견했다(원작 개발자가 기존 업그레이드를 복제해서 만든 흔적으로 보인다) —
이 파일의 텍스트 필드는 실제 효과의 근거로 안 쓰고 수치 필드(`gba1`/`gmo1`)만 근거로 삼았다.
