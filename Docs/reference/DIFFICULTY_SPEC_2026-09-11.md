## 1. `udg_Mode`/`udg_Mode_int` 전수 census

- `udg_Mode`: `string`(전역 스칼라, 플레이어별 아님). `udg_Mode_int`: `integer`(역시 전역 스칼라).
- `udg_Mode==` **17건**, `udg_Mode!=` **2건**(둘 다 `!="어려움"`), 도합 19개 조건함수. 전부 위
  마스터 함수가 심어둔 6개 색코드 문자열과의 리터럴 비교다 — 별도 enum/정수 비교는 없다.
- 🔴 **`udg_Mode_int`는 마스터 함수의 6개 대입 외에 전체 JASS에서 단 한 번도 읽히지 않는다.**
  비교(`==`/`>=` 등) 0건. **게임 로직 분기에는 전혀 안 쓰인다** — 순수 기록용(세이브/UI 후보,
  확인 못함)이다. `Mode_int`로 뭔가를 게이팅하려는 설계는 원작에 없다.
- 19개 조건함수가 실제로 걸려 있는 지점(전부 확인):
  - `Trig_Round_boolean_Trigger`계열 8건 — 41/51/61/62·66·71라운드 로직(§2·§6·§8 참고)
  - `Trig_Enemy_Boss_create`계열 2건 — 보스 타임리밋 벌칙(§6)
  - `Trig_Round_10ver`계열 2건 — 신세계 진입 안내(41라운드 시점 카운트다운 대기 문구, 신/악몽)
  - `Trig_Story2`/`Trig_StoryUnitBirth`계열 4건 — 신/악몽 전용 스토리 생성 분기
  - `Trig_Start2`계열 1건(Func067C) — 게임시작 초기화 분기(지옥/신/악몽)
  - `Trig_sinside_attach_Actions` 1건 — `!=어려움`(하드 제외 사이드보스 부착, §8)
- **결론: 난이도 게이팅은 전부 `udg_Mode`(문자열) 하나의 축으로만 이뤄진다.** `Mode_int`는 죽은 변수다.

## 2. 총 라운드 수 — 나무위키 "60(<하드)/75" 주장 반박, 정확값은 50/60/75

`Trig_Round_boolean_Trigger_Actions`의 라운드51·61 분기(`Func031`/`Func032`)를 직접 읽었다:

```jass
if(Trig_Round_boolean_Trigger_Func031C())then      // udg_Level==51
  if(Mode==쉬움)then
    call TriggerExecute(gg_trg_Save_sido2_easy)
    call DisableTrigger(gg_trg_Round_10ver)
    call DestroyTrigger(gg_trg_Round_10ver)          // ← 라운드 진행 트리거 자체를 파괴
    call TimerDialogSetTitleBJ(...,"라운드 종료!")
  else
    call DisplayTimedTextToForce(...,"61라운드부터 신세계에 돌입합니다...")
  endif
  ...
if(Trig_Round_boolean_Trigger_Func032C())then      // udg_Level==61
  if(Mode==보통)then
    (위와 동일하게 Round_10ver Disable+Destroy, "라운드 종료!")
  else
    "61라운드부터 신세계에 돌입합니다..." (반복 안내)
  endif
```

`DisableTrigger`+`DestroyTrigger(gg_trg_Round_10ver)` 호출은 **전체 JASS에 이 두 곳뿐**이다.
어려움/지옥/신/악몽은 이 두 지점 어디에도 안 걸려 `Round_10ver`가 안 죽고 계속 돈다.
이 네 모드의 종료는 별도로 `Trig_Round_boolean_Trigger_Actions` 맨 끝의
`if udg_Level>=76 then call TriggerExecute(gg_trg_Save_sido3) + End.mp3 재생 endif`에서
처리된다(`Trig_Enemy_Boss_create_Func004Func005C`가 `Level>=75`일 때 `udg_Level=77`로
강제 점프시켜 이 조건에 확실히 닿게 만든다).

| 모드 | 마지막으로 실제로 플레이되는 라운드 | 종료 처리 시점 |
|---|---|---|
| 쉬움 | **50** | Level==51 도달 시 `Round_10ver` 파괴 |
| 보통 | **60** | Level==61 도달 시 `Round_10ver` 파괴 |
| 어려움·지옥·신·악몽 | **75** | Level>=76 도달 시 `Save_sido3`+종료음 |

**나무위키 "60(하드 미만)/75" 주장 판정: 반은 맞고 반은 틀렸다.** 하드 이상 4종=75는 정확하다.
그러나 "하드 미만"을 60 하나로 묶은 게 틀렸다 — **쉬움은 50, 보통만 60**이다(둘을 하나로
뭉뚱그리면 쉬움이 10라운드 과다 계상된다). `[파일확인]`

⚠️ PM이 이미 확인한 "41라운드 시점 지옥60/신55/악몽50"은 **이 총 라운드수와는 다른 값**이다
(그건 `udg_ModeEnemyInt`, §5 참고) — 이름이 비슷해 혼동하기 쉬우니 명확히 구분해서 옮길 것.

## 3. R00T/R00V/R00U/R00W — 라운드 구간마다 껐다 켜는가?

**아니다. 전 모드에서 정확히 4번씩만 등장하고, 전부 마스터 함수(§0) 안이다.**
`'R00T'`/`'R00V'`/`'R00U'`/`'R00W'` 각 4건(어려움·지옥·신·악몽 1회씩), `'R00A'` 5건(보통 포함)
— **전체 JASS 어디에도 이 밖의 참조가 없다.** 라운드 진행 트리거가 이들을 라운드 번호에
맞춰 다시 호출하는 코드는 **존재하지 않는다**. `[파일확인, 전체 파일 재검색으로 반증]`

→ **"15~30 라운드"/"31~50"/"51~60"/"61~80"이라는 업그레이드 이름은 순수 장부용 라벨이고,
실제 게임 동작은 모드선택 시점에 다섯 개(R00A+R00T+R00V+R00U+R00W) 전부를 동시에,
게임 시작부터 끝까지 계속 걸어둔다.** 이름이 암시하는 "그 구간에서만 발동"은 사실이 아니다
— 이전 `DIFFICULTY_RESEARCH.md`(09-04)의 "확인 못한 항목" 중 이 건이 이번에 완전히 닫혔다.

## 4. rhpo 계열 가산 vs 승산 — [엔진표준 근거로 판정, 파일 자체엔 연산자 표기 없음]

`war3map.w3q`를 직접 파싱해서 이름 붙은 업그레이드 전부를 다시 뽑았다. **핵심 발견: `R00A`
`R00T`/`R00V`/`R00U`/`R00W`(§3) `R00K`/`R00L`/`R00M`/`R00N`/`R00B`(보스 전용, 아래) 전부
**서로 다른, 독립적인 업그레이드 객체**다 — 공통 조상은 딱 하나, WC3 원본 스톡 업그레이드
`Robs`를 각각 복제해서 만든 것뿐이고(`base=Robs, new=R00A/R00K/...`), 서로를 참조하거나
포함하는 관계가 아니다.**

| 업그레이드 | 레벨당 증가(`gba1`=`gmo1`, 예외는 각주) | 대상 |
|---|---|---|
| R00A | +10%/레벨 | 전체(P6) |
| R00T | +27%/레벨 | 전체(P6, "15~30" 라벨) |
| R00V | +96%/레벨 | 전체(P6, "31~50" 라벨) |
| R00U | +100%/레벨 | 전체(P6, "51~60" 라벨) |
| R00W | L1=+100%, L2부터 +81%씩(`gba1≠gmo1`, base+increment 분리형) | 전체(P6, "61~80" 라벨) |
| R00B | 고정 -15% (레벨 개념 없음) | **보스 전용**, 쉬움 |
| R00N | 고정 0% | 보스 전용, 보통 |
| R00K | 고정 +200% | 보스 전용, 어려움 |
| R00L | 고정 +450% | 보스 전용, 지옥 |
| R00M | 고정 +725% | 보스 전용, 신·악몽 공용 |

**다섯 개(R00A/T/V/U/W)와 보스 전용 다섯 개(R00B/N/K/L/M) 전부가 `gef1='rhpo'`(같은
"Real - Hit Points Bonus(%)" 효과 필드)를 쓴다.** 이 필드가 같은 플레이어(Player 6)에 동시에
여러 업그레이드로 걸릴 때 가산인지 승산인지는 **`war3map.w3q`/`war3map_new.j` 어느 파일에도
연산자가 직접 적혀있지 않다** — WC3 엔진 자체의 "업그레이드 효과 적용" 코드는 맵 파일 밖(엔진
내장)이라 이 조사 범위로는 못 본다. 다만 **이건 WC3 오브젝트에디터의 표준·공개된 동작이다**:
같은 효과필드(`rhpo` 등급)를 쓰는 서로 다른 업그레이드 레코드가 같은 플레이어에 동시에
연구되어 있으면 **각각의 보너스가 합산되어 한 번만 기준값에 곱해진다(가산)** — 곱을 거듭
적용(승산 체이닝)하지 않는다. 이건 이 맵의 커스텀 설계가 아니라 **워크래프트3 엔진 표준
컨벤션**이므로 `[미확인]`이 아니라 `[엔진표준, 파일 직접확인은 불가]`로 표기한다.
→ **예: 악몽 모드 최종 배율 ≈ 1 + (R00A 15×10%) + (R00T 4×27%) + (R00V 6×96%) + (R00U 8×100%)
+ (R00W 1.0+8×0.81) + (보스면 R00M 725% 추가)** — 전부 가산 후 한 번만 곱해지는 것으로 판단.
정확한 연산자가 필요하면 엔진 소스나 실측(인게임 HP 로그)이 있어야 한다 — 이 조사의 한계.

## 5. `Rhme`의 정체 — 이번에 확정

`war3map.w3q`에서 **`base='Rhme', new=4바이트 널`** 항목을 발견했다(이전 세션이 빈 문자열로
잘못 판정 — `new or base` 파서 로직이 4바이트 널을 "빈 문자열"로 착각한 게 원인, 파서 자체를
수정하진 않고 raw 필드로 재확인). **`Rhme`는 커스터마이즈 안 된 WC3 원본 스톡 업그레이드**다.

```
gnam(레벨1) = "신모드이상 스턴 저항력"
glvl = 1 (단일 레벨)
```

**즉 `Rhme` = "신 모드 이상 스턴 저항력"(Stun Resistance) — 이름 자체가 적용 대상(신·악몽)을
명시한다.** 마스터 함수에서 `SetPlayerTechResearchedSwap('Rhme',1,Player(6))`이 신·악몽
분기에만 있는 것과 정확히 일치한다. `war3map_new.w3a`(능력)·`war3map_new.w3u`(유닛) 둘 다
재검색했지만 `Rhme`는 없다 — **업그레이드가 맞고, w3q 검색 자체가 처음에 파서 버그로
막혀 있었을 뿐**이다. `[파일확인]`

## 6. 하드모드 51라운드 스토리9(어인섬) 체크 — 도달 불가능한 죽은 코드

`Trig_Round_boolean_Trigger_Func031Func006C`(Mode==어려움) →
`Func031Func006Func001C`(`udg_Story_Logic==false`) → 거짓이면 4인 전원 `CustomDefeatBJ`
("어인섬 스토리를 격파하지 못하여 51라운드 이후를 진행하지 못했습니다.")

**그러나 `udg_Story_Logic`에 대한 대입은 전체 JASS에 딱 4곳뿐이다**: `InitGlobals`(초기값
`false`) + 마스터 함수의 **쉬움/보통/어려움 세 분기(`=true`)**. 어려움 모드는 마스터 함수
안에서 곧바로 `Story_Logic=true`로 **선세팅**되고, 이후 게임 전체에서 `Story_Logic`을 다시
`false`로 되돌리는 코드가 **단 한 줄도 없다**(전체 파일 재검색, 0건). 즉 어려움 모드에서
이 검사는 **항상 `false==false`가 거짓으로 평가**되어 패배 분기에 절대 도달하지 못한다.
`[파일확인 — 죽은 코드로 확정]`

→ 참고로 이 51라운드 분기는 **모드 무관하게 항상** `Rhan` 연구(전원)와 "61라운드부터
신세계 준비" 안내는 정상 실행된다 — 죽은 건 오직 하드모드의 패배 하위분기뿐이다.

**정상모드 이상에서 보스를 안 잡으면? — 살아있는, 실제로 작동하는 패배 메커니즘 발견**
(`Trig_Enemy_Boss_create_Actions`, 쉬움의 "보스 안 잡아도 안 짐"의 정확한 거울상):

```jass
Stage==1(구세계 보스 타임리밋 도달) →
  보스가 아직 살아있으면(IsUnitAliveBJ==true):
    if(Mode==쉬움) "쉬움 모드는 보스를 잡지 않아도 패배하지 않습니다." (텍스트만, 끝)
    else:  TRIGSTR_10804("제한시간안에 보스를 잡지 못해 패배하였습니다.")
           PlayerDeath[p]=1, SavePlayer, 골드·목재·인구 전부 0으로 초기화, Save_Death[p]=1
```

없다**(도달 불가능한 분기라 예외가 없어도 문제 없음). `[파일확인]`

### 8-1. 하드모드가 사이드보스를 제외하는 이유 — 조건은 확정, "왜"는 미기재

`Trig_Round_boolean_Trigger_Func033C`(`Level==62 or 66 or 71`) →
`Func033Func002C`(`udg_Mode!="어려움"`) → 참이면 `TriggerExecute(gg_trg_sinside3)`
(사이드보스 62/66/71 생성 트리거). **조건은 정확히 `Mode!=어려움` 하나뿐**이고, 그
이유(서사·밸런스상 근거)를 설명하는 주석이나 별도 로직은 파일에 없다 `[미확인 — 조건은
파일확인, 이유는 원작자 의도라 파일에 없음]`.

이 사이드보스(신세계 도플라밍고/빅맘/카이도, 유닛ID `n00M`/`n00N`/`n00O`)는 이전 세션
`ORIGINAL_BOSS_COMBAT_SPEC.md`에서 이미 캐스팅게이지·스턴게이지·무적·광폭화소환까지
전부 검증됐고, 이번 세션에서 그 HP값(62,195,000/78,195,000/84,195,000)을
`war3map_new.w3u`의 `n00M`/`n00N`/`n00O` `uhpm`과 **재대조해 정확히 일치함을 재확인**했다.
이 셋과 앞서 `o001`/`o02C`/`o02B`(R65/70/75 "라운드보스" 파일이 쓰는 값, 12,297,000/
12,750,000/13,595,000)는 **서로 다른, 독립된 두 보스 레이어**다 — 이름이 같아서(도플라밍고
등) 헷갈리기 쉬우니 주의. `[파일확인, 교차검증]`

### 8-2. 밴/잠금 시스템 — 🔴 "매 판 적용"이 아니라 악몽모드 전용이었다

`InitTrig_ban`: `gg_trg_ban`은 생성 즉시 `DisableTrigger(gg_trg_ban)`로 **비활성 상태로
생성**된다. 이 트리거를 실행하는 코드는 전체 JASS에서 **`call TriggerExecute(gg_trg_ban)`
단 한 곳뿐** — 마스터 함수의 **악몽 분기 안**이다(`SetPlayerTechResearchedSwap('R00W',9,...)`
직후, `Mode_int=6` 대입 직전). `TriggerExecute`는 트리거의 Disable 여부와 무관하게 액션을
즉시 실행하므로, 이 1회 호출로 `Trig_ban_Actions`(14개 `Ban_Trigger`/`Ban_unit` 쌍 배열
구성)가 딱 한 번 돈다 — **악몽 모드를 선택했을 때만.** 다른 5개 모드에서는 이 배열 설정
자체가 아예 실행되지 않는다. `[파일확인]`

**이건 기존 `BAN_SYSTEM_SPEC_2026-09-07.md`/메모리 노트("매 판 채팅언락 14개 무작위
영구잠금")의 암묵적 "매 판" 전제를 정정하는 발견이다** — 실제로는 **악몽 모드를 고른
판에서만** 이 14개 캐릭터 잠금 시스템이 가동된다.

**별도 시스템과의 혼동 주의**: `gg_trg_mapban`은 이름이 비슷하지만 **완전히 다른 기능**이다.
`InitTrig_mapban`은 Disable 없이 생성되고, 마스터 함수 공통 꼬리에서 **모드 무관하게 항상**
실행된다(`call TriggerExecute(gg_trg_mapban)`). `Trig_mapban_Actions`→
`Trig_mapban_Func001A`의 실제 동작은 `CustomDefeatBJ(GetEnumPlayer(),"해당 닉네임은
맵밴되어있는 닉네임입니다.")` — **플레이어 닉네임 블랙리스트**(특정 닉네임 접속 시 즉시
패배)이지, 14캐릭터 잠금과는 무관한 별개 시스템이다. 이름의 우연한 유사성이 이전 조사에서
두 시스템을 섞어 봤을 가능성이 있다. `[파일확인]`

## 9. 🔴 우리 적 95종 HP = 원작 기본값인가 — 전수 census, 결론: 아니다(17/95만 일치)

이전 세션 `ENEMY_DATA_AUDIT.md`(09-05/06)가 이미 **`Assets/Data/Enemies` 92개 전수**를
`udg_Round_UnitType[]`(라운드→원작 유닛ID 표)로 1:1 대조해 끝냈다 — 표본이 아니라 전수
(라운드 1~75 + 스토리 13 + 크립 3 + 해왕류 1). 이번 세션에 그 이후 늘어난 파일(현재 95개
— `Enemy_SideBoss62/66/71` 3종 신규)까지 포함해 **`war3map_new.w3u`로 재검증**했다.

**결론(그대로 유지, 이번에 재확인): "원작 값이 실제로 들어있는 건 17/95뿐이고, 나머지
78종(라운드 몹 61종 + 스토리 13종 + 이번엔 없음)은 우리가 만든 등비수열 공식(공비≈1.1712,
R01=135에서 시작)이다."** = **"우리 = 업그레이드 없는 원작 기본값" 가설은 틀렸다.**

| 분류 | 종수 | HP 출처 |
|---|---|---|
| 라운드 보스 9종(R10·20·30·40·50·60·"R65"·"R70"·"R75") | 9 | 원작 그대로(`o01V/o01W/o01X/o01Y/o01Z/o029/o001/o02C/o02B`) |

| R01(첫 라운드) | 1 | 원작 그대로(`o00I`, 135) |

## 5줄 결론 (PM 회신용 초안)

1. 총 라운드는 나무위키 주장과 달리 쉬움50/보통60/어려움~악몽75(60/75 이분법 아님).
2. R00T/V/U/W는 라운드 구간과 무관하게 게임 내내 동시 활성 — 이름은 장부용, rhpo 다중
   업그레이드는 엔진표준상 가산 후 1회 곱.
3. `Rhme`="신모드이상 스턴 저항력"(신·악몽 전용) 확정, 하드모드 51R 스토리9 패배는 죽은 코드,
   대신 보통 이상은 보스 타임리밋 미처치 시 실제로 패배함(쉬움만 예외).

   노트 정정 필요, `gg_trg_mapban`(닉네임 블랙리스트)과는 별개 시스템.

   78종은 우리 자체 등비공식 — "우리=원작 기본값" 가설은 틀렸다.
