## 1. `udg_Mode`/`udg_Mode_int` 전수 census

- `udg_Mode`: `string`(전역 스칼라, 플레이어별 아님). `udg_Mode_int`: `integer`(역시 전역 스칼라).
- `udg_Mode==` **17건**, `udg_Mode!=` **2건**(둘 다 `!="어려움"`), 도합 19개 조건함수. 전부 위
  마스터 함수가 심어둔 6개 색코드 문자열과의 리터럴 비교다 — 별도 enum/정수 비교는 없다.
- 🔴 **`udg_Mode_int`는 마스터 함수의 6개 대입 외에 전체 JASS에서 단 한 번도 읽히지 않는다.**
  비교(`==`/`>=` 등) 0건. **게임 로직 분기에는 전혀 안 쓰인다** — 순수 기록용(세이브/UI 후보,
  확인 못함)이다. `Mode_int`로 뭔가를 게이팅하려는 설계는 원작에 없다.
- 19개 조건함수가 실제로 걸려 있는 지점(전부 확인):
  - `Trig_Round_boolean_Trigger`계열 8건 — 41/51/61/62·66·71라운드 로직(§2·§6·§8 참고)
  - `Trig_Enemy_Boss_create`계열 2건 — 보스 타임리밋 벌칙(§6)
  - `Trig_Round_10ver`계열 2건 — 신세계 진입 안내(41라운드 시점 카운트다운 대기 문구, 신/악몽)
  - `Trig_Story2`/`Trig_StoryUnitBirth`계열 4건 — 신/악몽 전용 스토리 생성 분기
  - `Trig_Start2`계열 1건(Func067C) — 게임시작 초기화 분기(지옥/신/악몽)
  - `Trig_sinside_attach_Actions` 1건 — `!=어려움`(하드 제외 사이드보스 부착, §8)
- **결론: 난이도 게이팅은 전부 `udg_Mode`(문자열) 하나의 축으로만 이뤄진다.** `Mode_int`는 죽은 변수다.

## 2. 총 라운드 수 — 나무위키 "60(<하드)/75" 주장 반박, 정확값은 50/60/75

`Trig_Round_boolean_Trigger_Actions`의 라운드51·61 분기(`Func031`/`Func032`)를 직접 읽었다:

```jass
if(Trig_Round_boolean_Trigger_Func031C())then      // udg_Level==51
  if(Mode==쉬움)then
    call TriggerExecute(gg_trg_Save_sido2_easy)
    call DisableTrigger(gg_trg_Round_10ver)
    call DestroyTrigger(gg_trg_Round_10ver)          // ← 라운드 진행 트리거 자체를 파괴
    call TimerDialogSetTitleBJ(...,"라운드 종료!")
  else
    call DisplayTimedTextToForce(...,"61라운드부터 신세계에 돌입합니다...")
  endif
  ...
if(Trig_Round_boolean_Trigger_Func032C())then      // udg_Level==61
  if(Mode==보통)then
    (위와 동일하게 Round_10ver Disable+Destroy, "라운드 종료!")
  else
    "61라운드부터 신세계에 돌입합니다..." (반복 안내)
  endif
```

`DisableTrigger`+`DestroyTrigger(gg_trg_Round_10ver)` 호출은 **전체 JASS에 이 두 곳뿐**이다.
어려움/지옥/신/악몽은 이 두 지점 어디에도 안 걸려 `Round_10ver`가 안 죽고 계속 돈다.
이 네 모드의 종료는 별도로 `Trig_Round_boolean_Trigger_Actions` 맨 끝의
`if udg_Level>=76 then call TriggerExecute(gg_trg_Save_sido3) + End.mp3 재생 endif`에서
처리된다(`Trig_Enemy_Boss_create_Func004Func005C`가 `Level>=75`일 때 `udg_Level=77`로
강제 점프시켜 이 조건에 확실히 닿게 만든다).

| 모드 | 마지막으로 실제로 플레이되는 라운드 | 종료 처리 시점 |
|---|---|---|
| 쉬움 | **50** | Level==51 도달 시 `Round_10ver` 파괴 |
| 보통 | **60** | Level==61 도달 시 `Round_10ver` 파괴 |
| 어려움·지옥·신·악몽 | **75** | Level>=76 도달 시 `Save_sido3`+종료음 |

**나무위키 "60(하드 미만)/75" 주장 판정: 반은 맞고 반은 틀렸다.** 하드 이상 4종=75는 정확하다.
그러나 "하드 미만"을 60 하나로 묶은 게 틀렸다 — **쉬움은 50, 보통만 60**이다(둘을 하나로
뭉뚱그리면 쉬움이 10라운드 과다 계상된다). `[파일확인]`

⚠️ PM이 이미 확인한 "41라운드 시점 지옥60/신55/악몽50"은 **이 총 라운드수와는 다른 값**이다
(그건 `udg_ModeEnemyInt`, §5 참고) — 이름이 비슷해 혼동하기 쉬우니 명확히 구분해서 옮길 것.

## 3. R00T/R00V/R00U/R00W — 🔴 정정: 라운드 구간 이름은 장부용 라벨이 아니라 실제 적용범위다

**초판이 틀렸다.** "모드선택 때 한 번만 연구되고 이후 껐다 켜는 코드가 없다"는 것 자체는
맞지만(`SetPlayerTechResearchedSwap`가 §0 마스터 함수 밖에서 재호출되는 곳은 없음 —
이건 재확인해도 사실이다), **"그래서 전 라운드에 동시 적용된다"는 결론이 틀렸다.** WC3
엔진 규칙: 플레이어가 어떤 업그레이드를 연구했어도, **그 업그레이드 코드가 유닛 자신의
`upgr`(연구 목록) 필드에 적혀 있어야만** 그 유닛에 효과가 걸린다. `war3map_new.w3u`를
유닛별로 다시 열어 `upgr` 필드를 전수 대조했다:

| 라운드 구간 | 해당 라운드 몹의 `upgr` | 비고 |
|---|---|---|
| R1~14 | `R024,R00J,R00Q,R00R,R00P,R00S,R00A` | 기본 세트 |
| R15~29 | 기본 세트 + `R00T` | |
| R31~49(39 제외) | 기본 세트 + `R00V` | |
| R51~59 | 기본 세트 + `R00U` | |
| R61~75 | 기본 세트 + `R00W` | |
| **R39**(HP=1, 개그 라운드) | **`R024`만** | 이 라운드 몹은 R00A조차 안 받는다 — 난이도 스케일링에서 완전히 제외 |
| 라운드보스 9종(10~60·95/100/105) + 사이드보스 3종(82/86/91) | `R00O,R00B,R00N,R00K,R00L,R00M` | **R00A 없음** — 보스는 전체난이도 배율 대신 보스전용 배율만 받는다 |
| 해왕류 `o02N` | `R00O,R01E,R01D,R01C,R01B,R01A` | §10-3 참고 |

→ **모드선택 시점에 R00A/T/V/U/W가 전부 Player(6)에 한꺼번에 연구되는 건 맞지만
(§0은 그대로 유효), 그 연구가 실제로 어떤 몹에게 효과를 내는지는 그 몹 자신의 `upgr`
목록이 결정한다 — 그리고 그 목록은 정확히 업그레이드 이름이 말하는 라운드 구간과
일치한다.** "15~30 라운드" 라벨은 장부용이 아니라 **정확한 적용 스펙**이었다.
`[파일확인, war3map_new.w3u upgr 필드 전수 대조]`

## 4. rhpo 계열 가산 vs 승산 — [엔진표준 근거로 판정, 파일 자체엔 연산자 표기 없음]

§3 정정을 반영해 다시 정리한다. `R00A`(기본, R1~75 대부분)·`R00T`/`R00V`/`R00U`/`R00W`
(구간 한정, §3)·`R00K`/`R00L`/`R00M`/`R00N`/`R00B`(보스 전용) 전부 **서로 다른, 독립적인
업그레이드 객체**다 — 공통 조상은 WC3 원본 스톡 업그레이드 `Robs`를 각각 복제한 것뿐이고
(`base=Robs, new=R00A/R00K/...`), 서로를 참조하거나 포함하는 관계가 아니다.

| 업그레이드 | 레벨당 증가(`gba1`=`gmo1`, 예외는 각주) | upgr로 실제로 받는 대상(§3) |
|---|---|---|
| R00A | +10%/레벨 | R1~75 중 R39·보스·해왕류 제외 전부 |
| R00T | +27%/레벨 | R15~29 |
| R00V | +96%/레벨 | R31~49(39 제외) |
| R00U | +100%/레벨 | R51~59 |
| R00W | L1=+100%, L2부터 +81%씩(`gba1≠gmo1`) | R61~75 |
| R00B | 고정 -15%(레벨 없음) | 라운드·사이드보스 전부(쉬움 선택 시) |
| R00N | 고정 0% | 위와 동일(보통) |
| R00K | 고정 +200% | 위와 동일(어려움) |
| R00L | 고정 +450% | 위와 동일(지옥) |
| R00M | 고정 +725% | 위와 동일(신·악몽 공용) |

**정상 라운드 몹(보스 제외)이 R00A+구간업그레이드 두 개를 동시에 받고, 보스는 R00A 없이
보스전용 하나만 받는다 — 둘 다 같은 `gef1='rhpo'` 필드**다. 같은 필드를 쓰는 여러
업그레이드가 **같은 유닛**에 동시에 걸릴 때(예: R31~49 몹은 R00A+R00V 둘 다) 가산인지
승산인지는 `war3map.w3q`/`war3map_new.j` 어디에도 연산자가 안 적혀 있다 — WC3 엔진 자체의
"업그레이드 효과 적용" 코드는 맵 파일 밖(엔진 내장)이라 이 조사 범위로는 못 본다. 다만
이건 **WC3 오브젝트에디터의 표준·공개된 동작**이다: 같은 효과필드(`rhpo`)를 쓰는 여러
업그레이드가 한 유닛에 동시에 걸려 있으면 각 보너스가 **합산되어 기준값에 한 번만
곱해진다(가산)** — 승산 체이닝이 아니다. 맵 커스텀 설계가 아니라 엔진 표준 컨벤션이므로
`[엔진표준, 파일 직접확인은 불가]`로 표기한다.
→ 예: R31라운드 몹(어려움 모드) HP 배율 ≈ 1 + (R00A 5×10%) + (R00V 2×96%) = 1 + 50% + 192%
= 원본 uhpm의 3.42배. 보스(어려움)는 R00A 없이 R00K(+200%) 하나만 = 3.0배.
정확한 연산자가 필요하면 엔진 소스나 실측(인게임 HP 로그)이 있어야 한다 — 이 조사의 한계.

## 5. `Rhme`의 정체 — 이번에 확정

`war3map.w3q`에서 **`base='Rhme', new=4바이트 널`** 항목을 발견했다(이전 세션이 빈 문자열로
잘못 판정 — `new or base` 파서 로직이 4바이트 널을 "빈 문자열"로 착각한 게 원인, 파서 자체를
수정하진 않고 raw 필드로 재확인). **`Rhme`는 커스터마이즈 안 된 WC3 원본 스톡 업그레이드**다.

```
gnam(레벨1) = "신모드이상 스턴 저항력"
glvl = 1 (단일 레벨)
```

**즉 `Rhme` = "신 모드 이상 스턴 저항력"(Stun Resistance) — 이름 자체가 적용 대상(신·악몽)을
명시한다.** 마스터 함수에서 `SetPlayerTechResearchedSwap('Rhme',1,Player(6))`이 신·악몽
분기에만 있는 것과 정확히 일치한다. `war3map_new.w3a`(능력)·`war3map_new.w3u`(유닛) 둘 다
재검색했지만 `Rhme`는 없다 — **업그레이드가 맞고, w3q 검색 자체가 처음에 파서 버그로
막혀 있었을 뿐**이다. `[파일확인]`

## 6. 하드모드 51라운드 스토리9(어인섬) 체크 — 도달 불가능한 죽은 코드

`Trig_Round_boolean_Trigger_Func031Func006C`(Mode==어려움) →
`Func031Func006Func001C`(`udg_Story_Logic==false`) → 거짓이면 4인 전원 `CustomDefeatBJ`
("어인섬 스토리를 격파하지 못하여 51라운드 이후를 진행하지 못했습니다.")

**그러나 `udg_Story_Logic`에 대한 대입은 전체 JASS에 딱 4곳뿐이다**: `InitGlobals`(초기값
`false`) + 마스터 함수의 **쉬움/보통/어려움 세 분기(`=true`)**. 어려움 모드는 마스터 함수
안에서 곧바로 `Story_Logic=true`로 **선세팅**되고, 이후 게임 전체에서 `Story_Logic`을 다시
`false`로 되돌리는 코드가 **단 한 줄도 없다**(전체 파일 재검색, 0건). 즉 어려움 모드에서
이 검사는 **항상 `false==false`가 거짓으로 평가**되어 패배 분기에 절대 도달하지 못한다.
`[파일확인 — 죽은 코드로 확정]`

→ 참고로 이 51라운드 분기는 **모드 무관하게 항상** `Rhan` 연구(전원)와 "61라운드부터
신세계 준비" 안내는 정상 실행된다 — 죽은 건 오직 하드모드의 패배 하위분기뿐이다.

**정상모드 이상에서 보스를 안 잡으면? — 살아있는, 실제로 작동하는 패배 메커니즘 발견**
(`Trig_Enemy_Boss_create_Actions`, 쉬움의 "보스 안 잡아도 안 짐"의 정확한 거울상):

```jass
Stage==1(구세계 보스 타임리밋 도달) →
  보스가 아직 살아있으면(IsUnitAliveBJ==true):
    if(Mode==쉬움) "쉬움 모드는 보스를 잡지 않아도 패배하지 않습니다." (텍스트만, 끝)
    else:  TRIGSTR_10804("제한시간안에 보스를 잡지 못해 패배하였습니다.")
           PlayerDeath[p]=1, SavePlayer, 골드·목재·인구 전부 0으로 초기화, Save_Death[p]=1
Stage==3(신세계 보스 타임리밋 도달, Level>60 전용) →
  보스가 아직 살아있으면: **Mode 분기 자체가 없다** — 전원(쉬움 포함 개념상)
  동일하게 PlayerDeath[p]=1 처리(TRIGSTR_11584, 동일 문구)
```

**즉 "쉬움은 보스 안 잡아도 안 짐"은 딱 하나의 지점(Stage1, Level≤60 구세계 보스)에만
적용된다.** Stage3(신세계 보스, Level>60)에는 쉬움 예외가 코드상 아예 없다 — 다만 쉬움은
§2에서 확인했듯 Round 50에서 게임이 끝나 Level>60에 도달하지 않으므로 **실질적으로 모순은
없다**(도달 불가능한 분기라 예외가 없어도 문제 없음). `[파일확인]`

⚠️ **정정(§10-1에서 자세히)**: 위 Stage3 분기는 `Trig_Enemy_Boss_create` 안에 있는데, 그

## 9. 🔴 우리 적 95종 HP = 원작 기본값인가 — 정정: 82/95(라운드 75+크립3+사이드보스3+해왕류1)가 정확히 일치, 스토리 13종만 우리 콘텐츠

### 10-1. 보스 타임리밋 패배 — 정확한 초·대상·범위

`Trig_Enemy_Boss_create_Actions`는 **두 단계(Stage1/Stage3)로 보이지만, Stage3(else,
`Level>60`) 쪽은 `Round_UnitType[Level+50]`이라는 존재하지 않는 인덱스를 읽는다**
(`Round_UnitType`는 1~75·82·86·91·95·100·105까지만 정의됨, 65+50=115/70+50=120/75+50=125는
전부 미정의) — 이 분기는 **죽은 코드**로 판단한다(§6에서 이미 정정 반영).

**R10~60(구세계 6보스, Stage1)**: `s__TrigVariables_SleepForStageAdd(GlobalTV,75.30,1)` —
보스 생성 후 **정확히 75.30초** 뒤 Stage1 체크. 살아있으면(=쉬움 아니면) `PlayerDeath[p]=1`.

**R65/70/75(신세계 3보스)는 별도 트리거 `Trig_Enemy_Boss_sinsekai_Actions`가 전담한다**
(`(Boss_sin_number×5)+90` 인덱스로 `o001`/`o02C`/`o02B` 정확히 생성, §9에서 이미 이걸로
75/75 매치를 냈다). 이쪽은 `s__TrigVariables_Setreal(GlobalTV,5,34.80)` — **정확히 34.80초
고정**(모드 무관, `Mode_TimerReal` 관여 없음). 타임아웃 시 보스가 살아있으면 **Mode 분기
없이 전원 동일하게** `PlayerDeath[p]=1`, 자원 초기화, `SavePlayer` — 쉬움 예외가 이 트리거
안에는 없지만 §6에서 확인했듯 쉬움은 Round50에서 끝나 여기 도달하지 않는다.

**사이드보스 3종(62/66/71)은 이 타임리밋 시스템과 완전히 무관하다.** 이전 세션
`ORIGINAL_BOSS_COMBAT_SPEC.md`가 이미 확인한 대로 게이지(100, 25.0/초 충전 → 4초)가 다
차면 **광폭화 몬스터 1기를 소환할 뿐**, `PlayerDeath`를 쓰는 코드가 그 트리거들
(`Trig_sinside3`/`Trig_sin_boss_skill1~4`) 안에 없다 — 플레이어 탈락과 무관.

**대상은 전부 개인 단위다** — `udg_BossUnit[GetForLoopIndexB()]`/`PlayerDeath[GetForLoopIndexB()]`
처럼 플레이어 인덱스별 배열이라, 죽는 건 그 플레이어 한 명뿐이고 나머지 생존자는 계속
진행한다. `[파일확인]`

### 10-2. `rarm`(R00J·R00O) — %인지 고정값인지, [미확인]으로 유지

파일 자체엔 `gba1=0.1` 하나뿐이고 그게 "0.1(고정값)"인지 "10%"인지는 `gef1` 코드의
**의미**(WC3 오브젝트에디터가 그 rawcode를 어떤 효과 타입으로 등록했는지)에 달려 있는데,
이건 맵 파일 밖(엔진 내장 테이블)이라 이 조사로 확정할 근거가 없다. WC3 표준 지식으로는
방어력 업그레이드 효과(Armor Bonus류)는 보통 **퍼센트가 아니라 고정값 타입**이라(HP·마나
보너스만 `-Percentage` 변종이 따로 있음) `rarm=0.1`은 +0.1 고정 방어력(사실상 무의미한
크기)일 가능성이 **rhpo와 같은 방식으로 10%라고 읽는 것보다 높다고 본다** — 다만 이건
엔진지식 기반 추정이지 파일로 확정한 게 아니다. **`[미확인]`으로 유지한다.** 구현 시엔 두
경우 다 시험해보고 원작 인게임 방어력 로그(있다면)로 검증하는 게 안전하다.

### 10-3. 해왕류(`o02N`) — R01A~E가 걸린다, Player(5) 소유 확인

`o02N`은 `CreateUnitsForPlayer5` 안에서 `local player p=Player(5)`로 생성된다(정적
배치, `war3mapUnits.doo` 없는 이 맵답게 `CreateUnit` 하드코딩). §0에서 이미 확인했듯
R01A~E(신/악몽=R01A, 지옥=R01B, 어려움=R01C, 보통=R01E, 쉬움=R01D, 전부 +50% 고정)도
**Player(5)에 연구된다** — 소유자가 일치하므로 **실제로 걸린다.** `[파일확인]`
→ 우리 `Enemy_거대해왕류.asset`의 hp=36,000,000은 §9에서 확인한 `uhpm` 원시값과는
정확히 일치하지만, **모드 무관하게 +50%가 항상 걸리는 원작 실제값(=36,000,000×1.5=
54,000,000)보다는 낮다** — 다른 라운드 몹과 같은 성격의 저평가(§9 말미 참고).

### 10-4. R65/70/75 — 보스 라운드에도 라인몹이 같이 나오나: **그렇다**

§10-1에서 확인했듯 `Trig_Enemy_Boss_sinsekai_Actions`가 보스(`o001`/`o02C`/`o02B`)를
별도로 생성하는 것과 **완전히 별개로**, `Trig_Round_10ver_Actions`가 매 라운드 표준
루프에서 `CreateUnitAtLoc(Player(6), udg_Round_UnitType[udg_Level], ...)`를 **레벨
분기 없이(보스 라운드라고 건너뛰는 조건이 없이)** 항상 실행한다 — 즉 R65엔 `o01S`(트레볼)
라인몹과 `o001`(도플라밍고) 보스가 **동시에** 나온다. `[파일확인]`

### 10-5. R024 이속 — 라운드 몹 `umvs` 기준 비율

라운드 몹 기준 이속은 `umvs=300`(69종 전부 동일, `ENEMY_DATA_AUDIT.md` 교차검증).

### 10-6. `Rhme` 실제 효과값 — 없다, 이름뿐인 장식 업그레이드

`war3map.w3q`의 `Rhme` 항목은 `gef1=''`(효과 필드 자체가 비어 있음), `gba1`/`gmo1`
필드가 아예 없다 — **오브젝트에디터 표준 효과 시스템으로는 아무 것도 걸리지 않는다.**
전체 JASS에서 `'Rhme'`은 §0의 2회(신·악몽 연구 대입)뿐이고, 그 연구 상태를 **되읽는
코드는 0건**(`GetPlayerTechCount`/`GetPlayerTechResearched` 등으로 `Rhme`를 검사하는
곳이 전체 파일에 없음). **결론: `Rhme`("신모드이상 스턴 저항력")는 실질 효과가 없는
장식용 텍-트리 항목이다** — `iabi=A109`(무효과 스텁)·`R00P/Q/R`(gef1 없음)과 같은 패턴,
`item-research-traps`/`no-numbers-means-three-things` 메모리의 사례에 새로 추가할 만하다.
`[파일확인]`
