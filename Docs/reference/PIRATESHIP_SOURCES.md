### 왜 재료로 못 쓰는지 — 원문 근거

히든/영원/IM/포에버 조합의 재료 판정 필터는 전부 두 조건의 `GetBooleanAnd`다:

```jass

Trig_Hidden_Bal_Func003Func010001001002002 : return GetOwningPlayer(GetFilterUnit())==GetTriggerPlayer()
```

맵 전체 조합 필터를 세어보면 **유닛ID 판정 586건 / 소유자 판정 586건 — 1:1로 정확히 짝**이다.
즉 **모든 재료 판정이 「내 것」만 센다.** `Player(7)` 소유인 전시용 3기는 어떤 조합에도 걸리지 않는다.

> 구현담당1께: 「맵 시작 3기」를 만들면 **화면에 보이지만 조합에 안 쓰이는 장식**이 됩니다.

## ③ 확률의 정확한 형태 — 「실패 판정 먼저」 구조에 주의

도박 둘은 **확률이 두 단계**다. 순확률을 곧바로 쓰면 안 되고, 원작 순서를 지켜야 결과 분포가 같다.

```jass
Trig_Unit_Gemble_0_Actions:            (h06B 초급)
    if GetRandomPercentageBJ()<=15.00 then   →  "실패 !"           (15%)
    else
        if GetRandomPercentageBJ()<=2.00 then →  h060 해적선        (85% × 2%  = 1.70%)
        else                                  →  udg_unit_dobakGroup1 에서 랜덤 유닛 (83.30%)

Trig_Unit_Gemble_2_Actions:            (h06C 중급)
    if GetRandomPercentageBJ()<=30.00 then   →  "실패"             (30%)
    else
        if GetRandomPercentageBJ()<=3.50 then →  h060 해적선        (70% × 3.5% = 2.45%)
        else                                  →  udg_unit_dobakGroup2 에서 랜덤 유닛 (67.55%)
```

랜덤 뽑기는 한 단계다. `GetRandomPercentageBJ()<=0.24` → **0.24%**, 성공하면 일반 유닛 분기를 통째로 건너뛴다.

## ④ 툴팁이 코드와 다른 곳 2건 `[파일확인]`

「원작 툴팁 ≠ 원작 동작」이 또 나왔다. **코드 쪽이 맞다.**

| 능력 | 툴팁 | 실제 코드 |
|---|---|---|
| `A16Z` 폐함대선 판매 | 「25%확률로 목재 1 획득 또는 25%확률로 해적선 획득」 | `<=50.00` → 목재1, **else 해적선** = **50 / 50** |
| `A0OD` 레일리 도박 | 「27% 확률로 레일리를 획득」 | `GetRandomInt(1,100)<=25` = **25%** |

(해적선 도박 `A023`의 40%, 도박 유닛의 85%·70%는 툴팁과 코드가 일치한다.)

## ⑤ 그 밖에 확인해둔 것

- **해적선을 파는 곳은 없다.** 유닛 1,559종의 모든 문자열 필드를 훑어 `h060`이 `useu`(판매 유닛)·`utra`(훈련)·`ubui`(건설) 어디에도 없음을 확인했다.
- **도박 풀에도 없다.** `udg_Modelpack_R_unit`←`gg_rct_Model_Pack_R1Unit`, `udg_unit_dobakGroup1`←`Ran0`+`Ran_1`, `dobakGroup2`←`Ran_2` — 이 rect 4개의 범위를 3기의 좌표와 대조했고 **하나도 안 걸린다.**
- **변수를 통한 간접 생성도 없다.** `set udg_… = 'h060'` 형태의 대입이 맵 전체에 0건이라, 위 9곳의 리터럴이 전부다.
- **처분 경로**: 해적선이 가진 `A0BB` 「판매-특수」 → 「흔함 선택위습 1기 + 목재 1」. 되파는 값이 있다.
- **고대의 배(`h05Y`)는 1회용**이다. `A023` 시전 시 성공·실패 양쪽 다 `RemoveUnit(GetTriggerUnit())`을 부른다. 획득처는 두 곳 — 아이템 `I00S` 사용(`Trig_item_up2`), 스토리 7단계 보상(`Trig_Story_reward7`, 전 플레이어에게 6000엔·목재4와 함께 지급).
- **아이스버그 `A0Q3`은 레벨 3까지 정의돼 있지만 레벨 3에는 도달할 수 없다.** 레벨 2에서 쓰면 트리거가 능력을 제거하므로 「0번 사용가능」 툴팁은 죽은 표기다.

## ⑥ 크립 보상의 함정 — 조건과 수령자가 다른 축이다 `[파일확인]`

```jass
Trig_creep_reward_Func002Func002C:
    udg_creep_Logic[ GetConvertedPlayerId(GetOwningPlayer(GetKillingUnitBJ())) ] == false   ← 죽인 플레이어

Trig_creep_reward_Actions (그 안):
    CreateNUnitsAtLoc(1,'h060', ConvertedPlayer(GetUnitUserData(GetTriggerUnit())), …)      ← 크립의 UserData 플레이어
    udg_creep_Logic[ GetConvertedPlayerId(ConvertedPlayer(GetUnitUserData(GetTriggerUnit()))) ] = true
```

**조건은 「죽인 사람」으로 보고, 보상과 1회 플래그는 「크립에 적힌 사람」에게 간다.**
남의 크립을 대신 죽여주면 조건은 내 플래그로 통과하고 보상은 크립 주인이 받는 상태가 만들어진다.
원작 버그인지 의도인지는 판단하지 않는다 — **원문이 이렇게 적혀 있다는 것만 기록한다.**

## 조사 범위 공개

- `war3map.j` 8,156개 함수 전수에서 `'h060'` 리터럴을 검색 → **26개 함수**. 그중 유닛을 실제로 만드는 건 **9개**(액션 8 + 맵배치 1), 나머지 17개는 조합 재료 판정 필터다.
- 각 생성 지점의 조건은 `if/elseif/else/endif`를 스택으로 추적해 **감싸고 있는 조건 전부**를 모았고, `_Conditions`·`FuncNNNC` 조건 함수는 본문까지 펼쳐 읽었다.
- 능력 수치는 `war3map.w3a`, 유닛 필드는 `war3map.w3u`를 직접 파싱했다.
- **안 본 것**: `h05O` 아이스버그·`h06B/h06C` 도박 유닛 자체의 **획득 경로**는 이번 범위 밖이다 `[미확인]` — 해적선에서 한 단계 더 떨어져 있고, 뽑기 등급 체계 전체를 봐야 한다.
- **안 본 것**: `A0Q3`의 시전시간 10초는 **툴팁 표기**다. `w3a`의 시전시간 필드로는 확인하지 않았다 `[미확인]`.

## ⑦ 추가 (2026-09-06) — 랜덤 뽑기 포탈의 나머지 절반

PM 질문(「우리 1% 상붕카와 이 0.24%가 같은 뽑기인가」)에 답하며 `Trig_Random_Base1`을 끝까지 전개했다.

### 「배」는 하나뿐이다

배 모델(`*Ship*`/`*Boat*`/`*Transport*`)을 쓰는 유닛을 맵 전체에서 전수로 뽑으면 **넷**이고, 그중 플레이어가 가질 수 있는 건 하나다:

| 유닛 | 모델 | 정체 |
|---|---|---|
| **`h060` [히든]해적선** | `HumanDestroyerShip.mdl` | **플레이어 유닛 — 이것뿐이다** |
| `o01C` 레벨 32 폭시 해적단 | `NightElfTransportShip.mdl` | 적 |
| `n003` 3. 하늘섬 · `n004` 4. 워터세븐 | `HumanShipyard.mdl` | 스토리 섬 |

→ **우리 로스터의 「상붕카(배)」가 가리킬 수 있는 원작 유닛은 `h060` 해적선 하나뿐이다.**
(우리 `안흔함_상붕카.asset`은 HP 180·공격 90·안흔함이고 `h060`은 HP 10·공격 510·사거리 600·비행이라 **수치는 하나도 안 옮겨져 있다** — 커뮤니티 문서로 만든 자리표다.)

### 이 포탈의 보너스 분기는 **하나뿐이다**

```jass
Trig_Random_Base1_Actions:
    KillUnit(위습)
    if GetRandomPercentageBJ() <= 0.24 then
        CreateNUnitsAtLoc(1,'h060', …)          ← 해적선. 여기서 끝
    else
        … 흔함 9종 뽑기 …
```

**`else` 안에 1%짜리 세 번째 갈래는 없다.** 원작 랜덤 뽑기가 줄 수 있는 건 **해적선(0.24%) 아니면 흔함 9종**이고, 안흔함은 나오지 않는다.

흔함 9종 = `udg_Unit_type_Normal[1..9]` = 루피 `h003` · 조로 `h002` · 나미 `h001` · 우솝 `h007` · 상디 `h004` · 쵸파 `h008` · 버기 `h005` · 해군 총병 `h009` · 해군 칼병 `h006`.

### 🔴 놓치고 있던 것 — **8회마다 천장이 있다** `[파일확인]`

```jass
udg_correction_plaerint = 플레이어ID × 10
if udg_correction_Count[플레이어] == 7 then
    udg_correction_Count[플레이어] = 0
    udg_common_correction = udg_common_unit_Count[plaerint+1] + 1
    for i = 1..9:
        if udg_common_unit_Count[plaerint+i] < udg_common_correction then
            udg_common_correction = udg_common_unit_Count[plaerint+i]
            udg_int_Normal_Type   = i               ← 가장 적게 나온 종류
else
    udg_correction_Count[플레이어] += 1
    udg_int_Normal_Type = GetRandomInt(1,9)         ← 균등 랜덤
endif
…생성…
udg_common_unit_Count[plaerint + 종류] += 1         ← 종류별 누적 집계
```

- **8번째 뽑기마다** 균등 랜덤 대신 **지금까지 가장 적게 나온 종류를 확정 지급**한다. 그리고 카운터를 리셋한다.
- 집계는 **플레이어별 · 종류별**(`plaerint = 플레이어×10` 오프셋)이고 **게임 내내 누적**된다. 라운드 경계와 무관하다.
- 동률이면 **번호가 작은 쪽**이 이긴다(`count[1]+1`에서 시작해 **엄격히 작을 때만** 갱신하므로).
- **해적선이 나온 뽑기는 카운터도 집계도 올리지 않는다** — 0.24% 분기가 `else` 전체를 건너뛰기 때문이다. 즉 **해적선은 천장 주기를 소모하지 않는다.**

→ 원작 뽑기는 순수 랜덤이 아니라 **「7번 랜덤 + 1번 보정」의 8회 주기**다. 우리 포탈엔 이 축이 없다.

### 우리 「1%」·「목재1 40%」의 출처

둘 다 **맵 원문이 아니라 커뮤니티 문서(2차 자료)**에서 왔다(`RECIPES_LOW.md` 238행 · `GAMBLING.md` 28행).
원문과 대조하면:

| 우리 값 | 원문 | 차이 |
|---|---|---|
| 유닛 랜덤 **1%** | **0.24%** | 약 4배 과다 |
| 도박소 **목재 1** 소모 **40%** | 고대의 배 `A023`: **목재 4** 소모 **40%** | **확률은 정확히 일치**, 목재 수만 다름 |

**40%가 정확히 맞는 것은 우연으로 보기 어렵다** — 2차 자료가 같은 능력을 옮기면서 비용만 틀린 것으로 읽힌다.
다만 `GAMBLING.md`의 그 줄은 **「사용자 확정」**으로 표시돼 있어, 고칠지는 **사장님/PM 판단 사항**이다. 여기서는 원문만 적어둔다.
