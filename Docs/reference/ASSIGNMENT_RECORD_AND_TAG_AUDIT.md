# ㉠ **기록은 있다. 스크립트를 다시 돌릴 필요 없다**

배정 스크립트(`Tools/generate_unit_skill_damage_effects.py` 등)는 **중간 CSV나 로그를 남기지 않는다.**
그러나 **배정 시점에 각 에셋의 `description`에 그 배정을 글로 적었다.** 그게 기록이다.

```python
# generate_unit_skill_damage_effects.py:210~216
origin_label = row['출처'] if row['회수경로'] == '트리거' else f"더미:{row['출처']}"
description = (
    f"원작 트리거·더미 피해표(ORIGINAL_SKILL_DAMAGE_TABLE.csv) DPS 순위 배정 — "
    f"원작 {row['등급']} {row['유닛이름']}({origin_label})의 피해를 옮겼다. …"
)
```

## 현재 에셋에 살아 있는 배정 인용

| 인용 유형 | 건 |
|---|---|
| **1채널** — `원작 능력표(ORIGINAL_UNIT_ABILITIES.csv) … 원작 <등급> <유닛이름>(<유닛ID>)의 발동확률…` | **53** |
| **2채널 트리거 직접** — `… 원작 <등급> <유닛이름>(Trig_XXX)의 피해를 옮겼다` | **11** |
| **2채널 더미 경유** — `… 원작 <등급> <유닛이름>(더미 경로 Trig_XXX → eNNN(…) → ANNN)의 피해를 옮겼다` | **10** |
| | **합계 74건 / 76개 파일 / 서로 다른 원작 유닛 48기** |

**「트리거 직접」도 원작 유닛명과 트리거명이 둘 다 적혀 있다.** 예:
```
SkillData_원작능력_랜덤_모몬가.asset
  ← 원작 랜덤전용 쿠로사키 이치고 - 랜덤전용(Trig_ichigo1)의 피해를 옮겼다.
    원작 유닛 하나(행 4개)를 통째로 이 유닛에 배정했다
```
**행 개수까지 적혀 있다.** → `ORIGINAL_SKILL_DAMAGE_TABLE.csv`에서 `유닛이름 + 출처`로 되찾을 수 있다.

## ⚠️ 다만 두 가지 주의

1. **쪼개기가 description을 자식 파일에 복사했다면** 한 배정이 여러 파일에 나타난다.
   → **파일 수가 아니라 「원작 유닛 + 출처」 쌍으로 세야** 원래 배정 수가 나온다.
2. **PM이 말한 39건과 내가 센 11건이 다르다.** 쪼개기·리네임 뒤의 현재 파일만 셌기 때문일 수 있다.
   → 39건 목록을 주시면 그 파일들의 `description`을 직접 훑어 대조하겠다.

**스크립트를 다시 돌리지 않았다.** 뿌리 ⑱대로, 그건 기록이 아니라 새 배정이 된다.

# ㉡ 「피해 아님」 태그 감사 — **34건 중 오탐 1건**

`ORIGINAL_SKILL_DAMAGE_TABLE.csv`의 **`더미채널판정`** 열에 `❌ 피해 아님(버프·디버프·배율·지속)`이 **34행**.

## 🔴 오탐 **1건** — `A0F1` (구현담당1 지적이 맞다)

```
h05A 천냥광대 버기 - 영원한
  Trig_Bugi_Attack → h079(임펠다운 Lv.6죄수 버기의 부하 - 초월함) → A0F1
  A0F1 「!강력범-죄수크리」  base=ACbh
     Hbh1 = 20.0   Hbh2 = 1.5   Hbh3 = 0.0   atar = air,enemies,ground
```
→ **20% 확률로 1.5배 크리티컬이 실제로 돈다. 유효하다.** 태그를 정정하고 `더미채널판정_검증` 열에
**「✅ 유효 — 삭제 금지」**를 넣었다.

### 왜 오탐이 났나 — 그리고 **내 검사에도 같은 버그가 있었다**

원래 태그는 **`Hbh3`(추가피해)만 보고** 판정했다. `A0F1`은 `Hbh3=0`이라 「피해 없음」이 됐다.
그런데 **`ACbh`의 피해는 `Hbh3`(추가피해)와 `Hbh2`(배수) 둘 다에서 나온다.**

**나도 처음 교차대조를 돌렸을 때 똑같이 `Hbh3`만 봐서 「오탐 0건」이라는 틀린 답을 냈다.**
`Hbh2`를 넣어 다시 돌리고서야 `A0F1`이 나왔다.
→ **base마다 「피해를 낼 수 있는 필드를 전부」 나열해야 한다.** 하나만 보면 이 사고가 반복된다.

## ✅ 나머지 **33건은 태그가 맞다**

base·`atar`·필드값을 4단계로 대조했다. 33건의 base는 전부 오늘 「피해 필드 없음」으로 확정한 것들이다
(`AOae`·`AHad`·`Ablo`·`AUfa`·`Ainf`·`ANht`·`Apg2`·`Asph`·`Aroa`·`ANbr`·`AUls`·`AOwk` 등).

## 태그 사용 지침

> ⚠️ **이 태그는 「후보 좁히기」용이다. 단독으로 삭제 근거로 쓰지 말 것.**
> `더미채널판정_검증` 열이 `✅` 인 행만 삭제 후보로 보고, 그 열이 비었거나 🔴이면 손대지 말 것.
> 오늘 34건 중 1건이 오탐이었고, **그 1건은 이미 우리 게임에서 정상 작동 중**이었다.

# 덤 — PM이 물은 `A0EM` · `A0BL`

## `A0EM` 「!명왕의 검술」 — **채널이 다르다**

`h049`(실버즈 레일리 명왕 - 불멸의)의 **1채널 능력**(`uabi`에 직접 들어 있음)이다.
`ORIGINAL_UNIT_ABILITIES.csv`에 **행이 있다**:
```
h049,불멸의,실버즈 레일리 명왕 - 불멸의,,A0EM,ACbh,!명왕의 검술, 발동=[] 배수=[] 추가=[92500.0]
```
- **추가피해 92,500은 표에 있다.**
- **발동확률만 비어 있다** — `Hbh1`이 미지정이라 생성 시점에 못 채웠다. **오늘 스톡 15%로 닫혔다.**
- **`ORIGINAL_SKILL_DAMAGE_TABLE.csv`(2채널 표)에는 당연히 없다.** 1채널이기 때문이다.

→ **「일치하는 게 하나도 없다」는 2채널 표에서 찾았기 때문일 수 있다.** 1채널 표를 보면 있다.
(`불멸_고도현` 에셋은 1채널 `A0EM`을 얹으면서 effects는 2채널(시키 천신) 것을 썼다 — 그 혼선일 가능성이 크다.)

## `A0BL` 「0장풍 에이스 불주먹-5영원」 — **작동한다. 지우면 안 된다**

`e0AB`(E영원 에이스 특대화권 더미1)의 능력. `ACca`, `Ucs1 = 1,150,000`, 범위 210, 사거리 1700.

```jass
CreateNUnitsAtLoc(1,'e0AB',…)
call IssueTargetOrderById(GetLastCreatedUnit(), String2OrderIdBJ("frostarmor"), GetAttacker())      ← 첫 오더
call IssuePointOrderByIdLoc(GetLastCreatedUnit(), String2OrderIdBJ("carrionswarm"), udg_Eternal_LOC) ← 두 번째
```

**`carrionswarm`이 `ACca`와 맞는다 → 작동 확정.**

🔴 **경고**: 그 오더는 **두 번째**다. **오더 검사를 `re.search`(첫 것만)로 하면 「`frostarmor`이라 불일치 → 미작동」이라는 틀린 답이 나온다.**
**내가 오늘 고친 바로 그 버그다**(`findall`로 바꾸고 base 대조를 붙였다).
구현담당1이 같은 방식으로 검사 중이라면 **이 행을 잘못 지울 수 있다.**

**더미 하나에 오더가 여러 개 내려가는 경우가 실재한다** — 반드시 전부 모아서 base와 대조해야 한다.
