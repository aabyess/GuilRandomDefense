# 원작 고정수치를 우리 값으로 옮기는 법 — "동등 라운드 환산"

원작 능력 데이터엔 `22500`, `200000`처럼 **고정 데미지**가 많다. 원작 몹 HP는 R1 135 →
R75 16,210,000(12만 배)로 커서 이 숫자들이 원작 안에서는 말이 되지만, 그대로 우리 게임에
박으면 우리 몹 HP 스케일과 안 맞아 의미가 사라진다(너무 세거나 너무 약함). 이 문서는
"고정수치 하나를 다른 스케일로 옮기는" 절차와, **2026-09-04~05에 이 방법을 쓰다가 실제로
났던 사고**를 정리한다.

## ⚠️ 먼저 읽을 것 — 지금은 이 방법 자체가 대부분 필요 없다

**우리 몹 HP 커브가 2026-09-04 20:01(`de63a85`)부터 원작 몹 HP 커브와 완전히 같다:**

```
BASE_HP = 135, HP_GROWTH = 1.1712273519960352   (= (16210000/135)^(1/74))
R1 = 135 → R75 = 16,210,000                      (Tools/generate_waves.py:27)
```

원작도 정확히 같은 base·growth·R75다(원작 자체를 배율 없이 그대로 옮겼다 — `de63a85` 커밋
메시지 참고). **그러니 대상이 "몹 HP"인 고정 데미지는 환산하지 말고 원작 수치를 그대로
옮기면 된다.** 이 문서의 "환산 절차"는 **몹 커브가 아닌 다른 커브**(보스, 스토리 등)를
대상으로 하고 그 커브가 원작과 다를 때만 쓴다 — 아래 "안 통하는 경우"를 꼭 먼저 확인할 것.

## 사고 사례 — 낙뢰·독약(`c3fd1ea`, 2026-09-04 19:38)

도움소 스킬 낙뢰(원작 고정 22,500)·독약(원작 고정 200,000×2회)의 `damageBase`를 이 방법으로
구했는데, **두 가지가 겹쳐서 틀렸다.**

### 문제 1 — 몹 커브와 보스 커브를 이어붙였다

당시 썼던 식: `growth_ours = (88237/10)^(1/74) ≈ 1.13063`

`88237`은 그 시점 **우리 몹 R75 HP가 아니라 보스 R75 HP**(`BALANCE_RESEARCH.md`의 "보스 HP"
표, 몹 HP의 약 14.9배)였다. 몹 시작점(`10`, R1)에 보스 끝점(`88237`, R75)을 이어붙이는
바람에 성장률이 실제 몹 성장률(1.09)보다 부풀었다(1.13063). **서로 다른 두 커브를 하나로
착각한 것**이다 — 몹이면 끝까지 몹, 보스면 끝까지 보스로 짝을 맞춰야 한다.

### 문제 2 — 그 커브 자체가 23분 뒤 폐기됐다

`c3fd1ea`(19:38:35) 직후 `de63a85`(19:59:49 작업, 20:01:24 커밋)가 몹 HP 89종을 전부
원작값으로 교체했다. 계산에 쓴 "우리 몹 R75≈5,882"(base10·growth1.09)도, 잘못 섞어 쓴
"88237"도 **지금은 존재하지 않는 값**이다. 지금 로스터는 위 "먼저 읽을 것"의 커브다.

### 결과

`damageBase=530`(낙뢰)·`damageBase=2900`(독약, 1회분)으로 커밋됐는데, 지금 커브 기준
정답은 **원작 수치를 그대로 쓴 22,500 / 200,000**이다(방어력을 안 타는 마법피해라 방어력
스케일 문제도 없다). 재계산·재승인은 PM에게 별도 보고했다 — **이 값을 다른 스킬 계산의
"검증된 예시"로 베끼지 말 것.**

## 절차 (몹 커브가 아닌 다른 대상에 실제로 쓸 때)

1. **원작 커브 확정** — base, growth, 확인된 두 라운드(보통 R1·R75)를 원문(`war3map.w3a` 등
   1차 자료)에서 가져온다. `growth = (hp_R75 / hp_R1) ^ (1/74)`.
2. **우리 커브 확인 — 반드시 같은 종류로.** 대상이 몹이면 몹끼리, 보스면 보스끼리, 스토리면
   스토리끼리 맞춘다. **에셋을 직접 열어서 실측한다** — 문서(`ORIGINAL_VALUES.md`,
   `BALANCE_RESEARCH.md` 등)는 리밸런싱마다 낡는다. `Assets/Data/Enemies/*.asset`의
   `hp:` 필드나 해당 생성기(`Tools/generate_*.py`)의 상수가 진실이다.
3. **원작 고정수치가 원작 커브에서 몇 라운드째인지 역산**:
   `r = 1 + ln(damage / base_orig) / ln(growth_orig)`
4. **그 라운드를 우리 커브에 대입**:
   `converted = base_ours * growth_ours ^ (r - 1)`

## 검증 (틀렸던 계산 재현 — 참고용)

낙뢰 원작 22,500, 당시(틀린) `growth_orig=(16210000/135)^(1/74)≈1.17123`(이건 맞다 — 원작
몹 커브), `base_orig=135`:

```
r = 1 + ln(22500/135) / ln(1.17123) ≈ 1 + 5.116/0.15797 ≈ 33.37
```

여기까지는 맞다. 문제는 다음 줄, **틀린 growth_ours(1.13063)를 대입한 것**:

```
converted = 10 * 1.13063^(33.37-1) ≈ 532   (실제 커밋값 530)
```

같은 라운드(33.37)를 **올바른 몹 커브**(지금은 원작과 동일, growth 1.1712273519960352,
base 135)에 대입하면:

```
converted = 135 * 1.1712273519960352^(33.37-1) ≈ 22,497   (≈ 원작 22,500 그대로 — 당연하다,
지금 우리 커브가 원작 커브와 같으니까)
```

**커브가 같으면 역산→재대입 두 단계가 항등 변환이 된다.** 이게 "지금은 원작 수치를 그냥
쓰면 된다"는 말의 실제 이유다.

## 이 방법이 안 통하는 경우

- **대상이 몹 HP 커브가 아닐 때** (예: 와포루의 "스토리에 450만 마법데미지" — 대상이 스토리
  건물/유닛이지 라인몹이 아니다). **그 대상의 커브를 따로 확인해야 한다.** 몹 커브 값을
  갖다 쓰면 이번 사고와 같은 "다른 커브를 섞는" 실수가 된다. 스토리 쪽이 원작과 같은
  배율로 옮겨졌는지부터 먼저 확인할 것 — 아직 확인 안 됐다면 이 방법을 쓰기 전에 그것부터
  밝혀야 한다.
- **원작 수치가 고정값이 아니라 비율(%)일 때** — 이미 스케일 무관이라 환산이 필요 없다.
  예: 해루석의 "대상 HP 7%"는 `firstHitMaxHpPercent`에 7%를 그대로 넣으면 된다.
- **마나·쿨다운·지속시간처럼 배율과 무관한 값** — 원작 수치를 그대로 옮긴다(우리도 실제로
  낙뢰·독약의 마나·쿨다운은 이 방식으로 그대로 옮겼고, 그 부분은 문제 없다).
- **두 커브가 이미 같을 때**(지금 몹 HP가 그렇다) — 위 "검증" 절에서 보였듯 환산이 항등
  변환이 되므로 그냥 원작 값을 옮기면 된다. 이 경우에 굳이 이 절차를 돌리면 부동소수점
  반올림만 쌓인다.
- **끝점 두 개를 서로 다른 커브에서 가져올 때** — 이번 사고의 핵심 원인. `base_ours`와
  `hp_R75_ours`는 반드시 같은 데이터 출처, 같은 종류(몹/보스/스토리)여야 한다.

## 독약 `radius=12` — 발명값 메모

`SupportSkill_독약.asset`의 `radius=12`는 원작 능력 데이터에 범위(`aare`) 필드 자체가 없어
(`SUPPORT_SHOP.md` §"원작에 있는데 우리에게 없는 스킬" 참고) 새로 만든 값이다. 위 환산법과
무관하게 **그냥 지어낸 수치**이므로 밸런스 조정 여지가 있다는 걸 여기 남긴다.
