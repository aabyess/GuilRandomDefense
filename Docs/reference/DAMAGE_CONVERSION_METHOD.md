# 원작 고정수치를 우리 값으로 옮기는 법

> **우리 몹 HP 커브는 원작과 동일하다. 몹을 대상으로 하는 고정피해는 환산 없이 원작값을
> 그대로 쓴다.**

```
BASE_HP = 135, HP_GROWTH = 1.1712273519960352   (= (16210000/135)^(1/74))
R1 = 135 → R75 = 16,210,000                      (Tools/generate_waves.py:27)
```

2026-09-04 20:01(`de63a85`)부터 우리 몹 HP 89종이 이 base·growth로 원작을 배율 없이
그대로 옮긴 값이다. 원작도 정확히 같은 base·growth·R75다. **그러니 원작 능력 데이터에
있는 고정 데미지(예: `22500`, `200000`)를 몹 대상 스킬에 넣을 땐 계산하지 말고 그 숫자를
그대로 넣는다.** 아래 "절차"는 **몹 커브가 아닌 다른 커브**(보스, 스토리 등)를 대상으로
하고 그 커브가 원작과 갈라져 있을 때만 쓰는 예비 절차다 — 먼저 "언제 이 문서가 필요한가"
를 읽고 판단할 것.

## 언제 이 문서가 필요한가

- **필요 없음** — 대상이 몹 HP다. 원작 수치를 그대로 옮긴다. (지금 우리 게임의 대부분의
  경우가 이거다.)
- **필요 없음** — 원작 수치가 고정값이 아니라 비율(%)이거나, 마나·쿨다운·지속시간처럼
  스케일과 무관한 값이다. 그대로 옮긴다.
- **아래 "절차"가 필요함** — 대상이 몹이 아닌 다른 커브(보스, 스토리 등)이고, **그 커브가
  원작과 갈라져 있는지 아직 확인 안 됐거나 실제로 갈라져 있을 때.** 커브가 갈라졌는지부터
  `Assets/Data/Enemies/*.asset`(또는 해당 대상의 실제 에셋)을 열어 원작 수치와 대조해서
  먼저 확인한다 — 갈라져 있지 않으면 이 경우도 위 "필요 없음"으로 떨어진다.

전엔 원작 원문 수치를 그대로 쓰는 쪽이 항상 더 안전하다.**

## 절차 (예비 — 대상 커브가 원작과 실제로 갈라져 있을 때만)

1. **원작 커브 확정** — base, growth, 확인된 두 라운드(보통 R1·R75)를 원문(`war3map.w3a` 등
   1차 자료)에서 가져온다. `growth = (hp_R75 / hp_R1) ^ (1/74)`.
2. **우리 커브 확인 — 반드시 같은 종류로.** 대상이 몹이면 몹끼리, 보스면 보스끼리, 스토리면
   스토리끼리 맞춘다. **에셋을 직접 열어서 실측한다** — 문서(`ORIGINAL_VALUES.md`,
   `BALANCE_RESEARCH.md` 등)는 리밸런싱마다 낡는다. `Assets/Data/Enemies/*.asset`의
   `hp:` 필드나 해당 생성기(`Tools/generate_*.py`)의 상수가 진실이다.
3. **원작 고정수치가 원작 커브에서 몇 라운드째인지 역산**:
   `r = 1 + ln(damage / base_orig) / ln(growth_orig)`
4. **그 라운드를 우리 커브에 대입**:
   `converted = base_ours * growth_ours ^ (r - 1)`

## 검증 (틀렸던 계산 재현 — 참고용)

낙뢰 원작 22,500, `growth_orig=(16210000/135)^(1/74)≈1.17123`(원작 몹 커브, 이 부분은
맞았다), `base_orig=135`:

```
r = 1 + ln(22500/135) / ln(1.17123) ≈ 1 + 5.116/0.15797 ≈ 33.37
```

여기까지는 맞다. 문제는 다음 줄, **틀린 growth_ours(1.13063)를 대입한 것**:

```
converted = 10 * 1.13063^(33.37-1) ≈ 532   (실제 커밋값 530)
```

같은 라운드(33.37)를 **올바른 몹 커브**(지금은 원작과 동일, growth 1.1712273519960352,
base 135)에 대입하면:

```
converted = 135 * 1.1712273519960352^(33.37-1) ≈ 22,497   (≈ 원작 22,500 그대로 — 당연하다,
지금 우리 커브가 원작 커브와 같으니까)
```

**커브가 같으면 역산→재대입 두 단계가 항등 변환이 된다.** 이게 맨 위 결론("일단
환산하지 마라")의 실제 이유다 — 두 커브가 같은 이상 절차를 돌려봐야 원작 수치로
돌아올 뿐이고, 다르다고 착각하고 잘못된 끝점을 넣으면 이번처럼 조용히 틀린다.

## 절차가 통하지 않는 경우 (2단계에서 특히 주의)

- **끝점 두 개를 서로 다른 커브에서 가져올 때** — 이번 사고의 핵심 원인. `base_ours`와
  `hp_R75_ours`는 반드시 같은 데이터 출처, 같은 종류(몹/보스/스토리)여야 한다.
- **대상이 몹 HP 커브가 아닐 때** (예: 와포루의 "스토리에 450만 마법데미지" — 대상이 스토리
  건물/유닛이지 라인몹이 아니다). 몹 커브 값을 갖다 쓰면 이번 사고와 같은 "다른 커브를
  섞는" 실수가 된다. 스토리 쪽이 원작과 같은 배율로 옮겨졌는지부터 먼저 확인할 것.
- **원작 수치가 고정값이 아니라 비율(%)일 때** — 이미 스케일 무관이라 절차 자체가
  필요 없다. 예: 해루석의 "대상 HP 7%"는 `firstHitMaxHpPercent`에 7%를 그대로 넣는다.
- **두 커브가 이미 같을 때** — 위 "검증" 절에서 보였듯 절차를 돌려도 항등 변환이라
  원작 값과 같은 결과가 나온다. 이 경우 절차를 도는 건 부동소수점 반올림만 쌓는
  헛수고이니, 커브가 같은지부터 먼저 확인하고(위 "언제 이 문서가 필요한가") 같으면
  건너뛴다.

## 독약 `radius=12` — 발명값 메모

`SupportSkill_독약.asset`의 `radius=12`는 원작 능력 데이터에 범위(`aare`) 필드 자체가 없어

무관하게 **그냥 지어낸 수치**이므로 밸런스 조정 여지가 있다는 걸 여기 남긴다.
