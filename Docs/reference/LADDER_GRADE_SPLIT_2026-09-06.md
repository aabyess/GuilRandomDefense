# 서열 vs 사다리 분리 — 03번(랜덤유닛·다른세계 사다리 제외) 구현, 2026-09-06

PM 지시(2026-09-06): 사장님 03번 확정("랜덤유닛·다른세계를 등급 사다리에서 뺀다")을
반영하되, `Tier()`는 건드리지 않는다 — 조밀한 정수열이라 빼면 유령 티어/재번호매기기
대가가 크고, `GameHud` 정렬·`SupportShop` 해체 상한처럼 **서열**이 필요한 소비처가 있다.
그래서 「서열」(로스터 정렬·해체 상한)과 「측정 대상」(등급별 화력이 우상향하는가)을
갈랐다 — `Tier()` 하나가 지금까지 둘 다 하고 있었다.

## 변경

1. **`Assets/Scripts/Data/UnitData.cs`** — `UnitGradeExtensions.IsLadderGrade(this UnitGrade)`
   신규 추가. `RandomUnit`·`OtherWorld`·`TranscendentWisp` → `false`, 나머지 → `true`.
   `Tier()`는 값·순서·사장님 확정 주석 전부 그대로. 컴파일 확인 완료
   (`Tools/compile_check.sh`, exit 0).
2. **`Tools/simulate_balance.py`** — 구현담당2가 `f2114cc`로 처리(PM 배분이 겹쳐 같은 작업이
   두 세션에서 동시에 진행됐다 — 재작업 안 함). `parse_ladder_grades()`로 `IsLadderGrade()`를
   소스에서 직접 파싱(하드코딩 안 함, `parse_tier_mapping()`과 같은 정책).
   `median_dps_by_tier_ladder_only()`로 사다리가 아닌 등급을 등급별 집계에서 뺀 뒤 같은
   계산을 돌려, 리포트에 **"①' 등급별 median DPS — 사다리 전용"** 표를 추가했다(기존
   "①" 표는 그대로 둠 — 붕괴 라운드 모델(`run_backlog`)은 랜덤유닛·다른세계도 실제로
   뽑기·도박으로 확보 가능한 유닛이라 그대로 포함해서 돌린다, 03번 대상 아님).
   ⚠️ 이 표가 파싱하는 `IsLadderGrade()`는 항목 1(`UnitData.cs`)에 정의된다 — 커밋
   순서상 `UnitData.cs`가 먼저 들어가야 `parse_ladder_grades()`가 산다.
3. **`Tools/generate_recipe_assets.py`** — 재실행 금지 경고 추가(파일 최상단). 이 파일의
   자체 `GRADE`/`TIER` 딕셔너리는 낡은 9단계 스킴이라 지금 `Tier()`와 이미 어긋나 있다.
4. **`Docs/reference/BALANCE_SIMULATION_2026-09-05.md`·`WIRING_AUDIT.md`** — 수치는 안
   건드리고 주석만 추가(각 문서 참고). 기존 표는 "사다리 아닌 2등급을 포함해 집계된 것"
   임을 명시.

랜덤유닛(T7)·다른세계(T8)를 빼도 **T9(초월함)가 T6(영원함)보다 낮고, T11(불멸)이
T10(제한됨)보다 낮다** — 두 단절 다 그대로 남는다. 즉 지금까지 쫓던 사다리 붕괴는
랜덤유닛·다른세계가 사다리 안에 잘못 끼어 있었던 탓(만)이 아니다 — 전설→영원 이후
구간(영원·초월·제한됨·불멸 넷)의 구조적 문제는 그대로다. 이건 `PROC_RATE_REMEASURE_2026-09-06.md`가
발동률 쪽에서 이미 보고한 것("게이트 21건을 고쳐도 등급 중앙값은 안 움직였다")과
같은 방향의 신호다 — 등급 밀도·구조 쪽 원인이 유력하다는 근거가 하나 더 늘었다.
