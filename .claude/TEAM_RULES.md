# 팀 세션 운영 규칙 (TEAM_RULES)

## 구성

- **PM** (리더): 사용자의 지시를 직접 받는 유일한 창구. 작업을 분석해 구현담당1/2에게 배정하고, 본인도 코딩한다.
- **리서치담당** (부리더): 조사·탐색·분석·설계 검토 전담. 코드 파일을 **작성/수정하지 않는다** (Read/Grep/WebSearch 등 읽기 전용). 결과는 PM에게 보고한다.
- **구현담당1 / 구현담당2** (팀원): PM이 배정한 코딩 작업을 수행한다. 완료 후 PM에게 보고하고, PM이 요청하면 PM의 코드를 리뷰한다.

## 워크플로

1. 사용자가 PM에게 지시한다.
2. PM은 조사·분석·설계 판단이 필요하다고 보면 **리서치담당과 먼저 의견을 조율**한다 (SendMessage).
3. PM은 작업을 쪼개 구현담당1/2에게 배정한다. 배정 메시지에는 반드시 포함:
   - 목표, 대상 파일/폴더, 완료 조건, 건드리지 말아야 할 영역
4. 구현담당은 작업 완료 시 PM에게 보고: 변경 파일 목록 + 요약 + 검증 결과.
5. **코드리뷰 규칙**
   - PM이 코딩한 결과 → 구현담당1/2 중 **쉬고 있는 세션**에게 리뷰 요청.
   - 구현담당1/2가 코딩한 결과 → **PM**이 리뷰.
   - 리뷰어는 버그/누락/규칙 위반 위주로 지적하고, 승인 여부를 명확히 답한다.
6. 사용자에게 최종 보고는 PM이 한다.

## 충돌 방지

- 같은 파일을 두 세션이 동시에 수정하지 않는다. PM이 배정 시 파일 소유를 나눈다.
- 다른 세션이 소유한 파일을 고쳐야 하면 먼저 PM에게 알린다.
- `git commit`은 PM이 자주 수행한다 (씬 수정 전엔 반드시).
- **`git push`는 PM만 한다.** 팀원은 커밋까지만 하고 푸시하지 않는다.

## 언제 푸시하나 (PM)

사장님 확정(2026-09-03): **"좀 많이 변경됐다 싶으면 계속 푸시하셈"** — 매번 요청받을
필요 없이 PM이 판단한다. 다음 중 하나면 푸시한다:

- 기능 하나가 눈에 보이게 완성됐을 때 (사장님이 게임에서 확인할 수 있는 상태)
- 커밋이 10개쯤 쌓였을 때
- 씬·프리팹 같은 되돌리기 어려운 파일을 커밋한 직후

**푸시 전에 반드시 `HEAD`가 컴파일되는지 확인한다.** 팀원이 작업 중이라 작업트리가
깨져 있는 건 상관없다 — 커밋된 것만 나가기 때문이다. 확인 방법:

```
git stash push -- <남이 작업중인 파일들>
bash Tools/compile_check.sh
git stash pop
```

## 커밋 전 점검 (PM)

**코드를 고친 뒤에는 반드시** 실행한다:

```
Tools/compile_check.sh
```

컴파일이 실패하면 Unity는 **마지막으로 성공한 어셈블리를 그대로 유지한다.**
메뉴도 옛 코드로 계속 동작하므로, 겉보기에는 "고쳤는데 반영이 안 된다"로만 보인다.
실제로 이 함정에 두 번 빠졌고, 두 번 다 원인을 찾는 데 오래 걸렸다.

새 스크립트나 에셋을 만든 뒤에는 **푸시 전에 반드시** 실행한다:

```
python3 Tools/check_meta.py
```

`.meta`에는 GUID가 들어 있고 씬은 컴포넌트를 그 GUID로 참조한다.
`.meta` 없이 커밋하면 다른 컴퓨터에서 클론했을 때 Unity가 새 GUID를 발급하고,
그 스크립트를 쓰는 씬 참조가 전부 Missing Script가 된다.

Unity가 `.meta`를 만드는 시점이 스크립트를 만든 직후가 아니라 **에디터가 임포트할 때**라,
`git add`를 먼저 하면 매번 놓친다. 실제로 세 번 놓쳤다.

## 커밋은 반드시 pathspec 형태로

```
git diff --cached --name-only          # 먼저 눈으로 확인
git commit -m "..." -- 파일1 파일2      # -- 뒤에 경로를 나열
```

`git add` 뒤 `git commit`을 쓰면 **인덱스 전체**가 커밋된다.
여러 세션이 한 저장소를 쓰는데 **인덱스는 세션끼리 공유되므로**,
다른 세션이 같은 순간에 스테이징해둔 파일까지 같이 들어간다.
파일을 하나씩 `add`해도 이걸 못 막는다 — 막는 건 `--` 뒤의 경로 목록뿐이다.

2026-09-02에 실제로 났다. PM의 도박소 수정 커밋이 구현담당1의
`RoundManager.cs`·`MapGenerator.cs`·`Traits.meta`를 통째로 삼켰다.
코드는 안 날아갔지만 그 변경의 커밋 메시지가 사라져서,
나중에 이력을 읽는 사람이 왜 들어갔는지 알 수 없게 됐다.

**새 파일이 있으면 두 단계다.** 추적되지 않는 파일은 pathspec에 안 잡혀서
`git commit -- <새파일>`이 통째로 취소된다. 새 파일만 먼저 넣고 커밋한다:

```
git add -- 새파일1 새파일2
git commit -m "..." -- 새파일1 새파일2 고친파일1
```

`add`에도 `--` 뒤에 파일을 나열하는 건 같다. 보호 효과는 그대로다 —
커밋 범위를 정하는 건 여전히 `commit`의 `--` 뒤 목록이다.

`git add <디렉터리>`는 여전히 금지다. 그건 **내가 의도하지 않은 파일**을 막는 규칙이고,
이건 **남이 스테이징한 파일**을 막는 규칙이다. 둘 다 필요하다.

## 키를 새로 배정하기 전에 (Input System 단축키)

**코드를 쓰기 전에** 먼저 전체를 훑는다:

```
grep -rn "Keyboard.current\.[a-z0-9]*Key" Assets/Scripts/
```

**절대 `| head`를 붙이지 않는다.** 결과가 잘리면 뒤에 숨은 충돌을 못 본다 —
2026-09-02에 실제로 이렇게 놓쳤다: `| head`가 붙은 grep으로 "C키는 안 쓰인다"고 확인했는데,
`WarehouseController.cs`의 기존 C키 바인딩이 잘린 아래쪽에 있었다. 같은 훑기에서
`SelectionManager`(V, 모으기)와 `DebugHud`(V, 디버그 전용)가 겹치는 것도 같이 발견됐다 —
`DebugHud`는 `visible`일 때만 발동해서 평소엔 안 드러나다가 F1을 켜는 순간 같이 터지는 종류였다.

키 하나를 두 스크립트가 각자 `Update()`에서 `wasPressedThisFrame`으로 잡으면,
둘 다 같은 프레임에 그냥 발동한다 — 언어/엔진 차원에서 막아주는 게 없다.
겹치는 게 보이면 **게임 조작(플레이어 명령)이 우선이고, 디버그/보조 기능이 다른 키로 양보한다.**
한 키에 상황별로 다른 동작을 묶지 않는다 — 선택 상태에 따라 같은 키가 다른 일을 하면
사용자가 무엇이 일어날지 예측할 수 없다.

## 직렬화되는 enum은 **맨 뒤에만** 추가한다

`UnitGrade` · `ArmorType` · `TraitEffectKind` · `ResourceType` 처럼 에셋에 저장되는 enum은
**중간에 값을 끼우면 안 된다.** Unity는 enum을 이름이 아니라 **숫자로** 저장하므로,
중간에 하나 끼우면 그 뒤가 전부 한 칸씩 밀려서 **이미 저장된 값이 다른 것으로 읽힌다.**

**컴파일도 통과하고 오류도 안 난다.** 나중에 "강화했는데 엉뚱한 효과가 붙는다" 같은
증상으로만 보이고, 그때 enum 값을 의심하는 사람은 없다.

2026-09-04에 실제로 났다. `TraitEffectKind`에 `MagicArmorShred`를 `ArmorShred` 뒤에 넣어
그 뒤 여섯 개가 밀렸다. **마침 `effects`가 채워진 Trait 에셋이 0개라 피해가 없었을 뿐이다** —
하나라도 값이 있었으면 조용히 틀린 채로 커밋됐다.

넣은 사람이 그 enum 주석에 "맨 뒤에 붙여라"를 직접 써둔 당사자였다. **사람이 매번 기억해야
하는 규칙은 언젠가 깨진다** — 그래서 여기에도 적는다.

## `Tools/generate_*.py`는 파괴적이다

이 생성기들은 `Assets/Data/Units/Roster`에 **쓴다.** 돌리면 스탯이 0으로 덮이고
`.meta`의 GUID가 재발급돼서 **씬·조합식·가챠 테이블 참조가 전부 끊긴다.**

**검증하려고 실제 경로를 링크로 걸지 마라.** 스크래치 디렉터리에 실제 로스터를 심볼릭 링크로
연결해두고 "읽기만 하겠지" 하고 돌리면, 생성기는 그 링크를 따라가 **진짜 로스터에 쓴다.**
2026-09-02에 실제로 그렇게 190개가 덮이고 `기본_*` 임시 유닛 232개가 생겼다.
(복구는 `git checkout -- <경로>` + 미추적 파일 삭제로 됐지만, 커밋된 뒤였으면 훨씬 어려웠다.)

검증은 이렇게 한다:
- **함수만 따로 시험한다.** 생성기를 통째로 돌리지 말고 필요한 함수만 import해서 확인한다.
- 굳이 돌려야 하면 **출력 경로가 스크래치인지 먼저 확인한다.** 링크·상대경로 금지.

### 생성기가 만들지 않는 에셋을 재료로 이을 때

`generate_recipe_assets.py`의 `SPECIAL_MATERIALS`처럼, **다른 생성기나 손으로 만든 에셋**을
가리켜야 할 때가 있다. 이때 **결과 유닛으로 등록하지 마라** — 등록하면 생성기가 그 파일을
다시 쓰면서 스탯을 0으로 만들고 GUID를 새로 뽑는다. **참조만 잇고 GUID는 디스크의 `.meta`에서 읽어라.**
위 사고와 정확히 같은 피해가, 이번엔 커밋되어 남는다.

### pathspec은 파일 사이만 가른다 — 파일 안은 못 가른다

`git commit -- <파일>`은 **그 파일 안에 있는 남의 미커밋 변경까지 같이 넣는다.**
같은 파일을 두 세션이 동시에 만지면 pathspec으로도 못 막는다.

2026-09-04에 실제로 났다. 구현담당3이 `EnemyDummy.cs`에 작업 중이던 변경이
구현담당1의 골드 경제 커밋(`2f2f681`)에 딸려 들어갔다. 코드는 멀쩡했지만
커밋 메시지와 무관한 변경이 섞여서, 나중에 이력을 읽는 사람이
"이 줄은 왜 여기 있지"를 알 수 없게 됐다.

**예방책은 파일을 겹치지 않게 배분하는 것뿐이다.** PM이 작업을 나눌 때
어느 파일을 만질지 같이 정한다. 겹칠 수밖에 없으면:

1. **먼저 알린다.** "나 지금 `SupportShop.cs` 만진다"
2. **남의 변경이 섞여 있으면 커밋하지 않는다.** 그쪽 커밋에 딸려 가도록 두고
   상대에게 "내 N줄이 네 커밋에 들어갈 거다"라고 알린다
3. 커밋 전 `git diff -- <파일>`로 **내 변경만 있는지 눈으로 확인한다**

구현담당3이 2026-09-04에 `SupportShop.cs`를 이렇게 처리했다 —
구현담당2 작업이 같은 파일에 있어서 자기 4줄을 커밋하지 않고 알리기만 했다.

## 「완료」는 코드가 아니라 도달로 증명한다

**코드 경로가 있다고 도달하는 건 아니다.** 2026-09-04에 같은 함정을 하루에 세 번 밟았다:

1. `MobPrefab.damageTable`이 한 번도 배선된 적 없어 `null` — **배율표 전체가 곱해지지 않고 있었다.** 그 사이 PM은 "이번엔 진짜 동작이 바뀝니다"를 세 번 말했다
2. `PlayerContext.unitUpgrades`가 씬 4개 전부 `{fileID: 0}` — 유닛강화소 12개가 서 있는데 안 눌린다
3. **2번을 찾은 사람이 곧바로** "배선하면 다섯이 살아난다"고 보고했는데, 재보니 전투 수치는 하나도 안 바뀐다(특성 효과가 `unlockedTraits`에 매달려 있고 `Unlock()`을 부르는 코드가 없다). PM도 검증 없이 그대로 사장님께 옮겼다

**그러니 「완료」라고 쓰기 전에 셋을 다 확인한다:**

```
1. 코드가 있는가
2. 데이터(에셋)가 있는가
3. 둘이 실제로 연결돼 있는가      ← 1·2만 보면 위 셋을 다 놓친다
```

**3번은 「끝까지 따라가서」 확인한다.** 값이 흘러 실제로 곱해지는 지점까지 가야 한다. 중간에 빈 컬렉션·null·안 불리는 메서드가 하나라도 있으면 도달이 아니다.

**필드 단위 결측(2번, "데이터가 있는가")은 `Tools/audit_data.py`로 훑는다.** 2026-09-05에
도움소·적·유닛·조합식 필드 감사를 세 번 손으로 돌렸는데 매번 스크립트를 새로 짜고 지웠고,
그중 한 번은 리스트 내부 필드(`count:` 등)를 최상위로 잘못 세는 실수를 했다. 이 스크립트는
읽기 전용이고 값을 하드코딩하지 않는다(`Tier()`도 `UnitData.cs`에서 직접 파싱) — 매번 새로
짜지 말고 이걸 돌린다. 다만 "읽힘/누락/미사용"까지만 자동으로 낸다 — "이 필드는 특정 조건
에서만 쓰인다(해당없음)"는 사람이 코드를 읽고 판단해야 한다.

**값을 바꾸면 그 값이 적힌 문서를 같이 고친다.** 2026-09-05에 도움소 4~5종 값이 원작값으로
정정됐는데 `SUPPORT_SHOP.md`의 "우리 구현과 다른 점" 열이 옛 값 기준으로 남아 있었다 —
차이가 이미 없어졌는데 "차이 있음"으로 읽혀서, PM이 그걸 보고 이미 끝난 일을 다시 지시할
뻔했다. **문서를 지우지 말고 "언제 무엇으로 바뀌었다"를 이어 붙인다** — 지우면 그 문서가
왜 한때 다른 값을 적어뒀는지(조사 당시의 근거)가 같이 사라진다.

### 주석은 증거가 아니다

`UnitUpgradeShop.cs:9`가 *"`UnitAttacker`가 `UnitUpgrades.MultiplierFor(grade)`를 부른다"*고 적어 뒀는데 **`MultiplierFor`는 존재하지 않는 메서드다.** 주석이 없는 코드를 설명하고 있었고, 그걸 믿은 사람들이 "연결돼 있구나" 하고 지나갔다.

**「A가 B를 부른다」는 주석을 보면 B가 실재하는지, 부르는 곳이 있는지 확인한다.** 틀렸으면 그 자리에서 고친다 — 죽은 배선을 살아 있다고 말하는 문장이 제일 비싸다.

### 위험한 건 「없는 것을 가리키는 주석」이 아니다

주석 1,837줄을 기계로 훑었더니 **없는 멤버를 가리키는 건 딱 하나**였다. 정말 위험한 건 이쪽이다:

> **지목한 심볼이 전부 실재하는데, 그 사이 길이 끊긴 주석**

`UnitTraitData.cs:7-8`이 *"`ArmorShred`는 살아났다 — `EnemyDummy.AddArmorShred`로 쌓인다"*고 적어 뒀는데, 지목한 `ApplyArmorShred`·`ResolveUpgrades`·`EffectSum`·`AddArmorShred`가 **전부 실재한다.** 끊긴 건 그 사이 두 군데다(`unitUpgrades`가 null, `unlockedTraits`가 빈 집합).

**이건 스캔으로 안 나온다. 경로를 손으로 끝까지 따라가야 나온다.** 그러니 기계 검사를 돌렸다고 "전부 훑었다"고 쓰지 말 것 — **어느 계통을 손으로 따라갔는지**를 밝힌다.

### 죽어 있는 게 나은 경우가 있다

배선을 살리면 **유닛강화소가 12,000엔을 받고 아무것도 안 주게 된다**(올린 레벨을 읽는 코드가 없다). **「안 눌린다」보다 「돈을 먹고 속인다」가 나쁘다.** 배선 전에 "살리면 무엇이 어떻게 되는가"를 재고, 나빠지면 넣지 않는다.

### 「검산했다」가 순환논증일 수 있다

`EnemyDummy.cs:175`에 이렇게 적혀 있었다:

> *"원작이 워크3 시스템을 그대로 쓴다 — 「방어력 −20이면 71% 추가 피해」가
> `2 − 0.94^20 = 1.7099`와 정확히 맞는다(UNIT_STATS_RESEARCH 검산)"*

**검산이 아니었다.** `0.94`는 `1 − 0.06`이라, **공식이 0.06이라는 가정을 스스로 되풀이한 것**뿐이다.
서로 다른 두 출처가 맞아떨어진 게 아니라 **같은 가정이 두 번 나왔다.**
그리고 원작 맵은 실제로 `DefenseArmor=0.02`였다 — 그 「검산」은 이 맵을 확인해 준 적이 없다.

**「검산 완료」라고 적힌 주석이 제일 위험하다.** 다음 사람이 거기서 멈추기 때문이다.
검산을 적을 때는 **두 출처가 독립인지** 밝힌다: 무엇과 무엇을 맞춰봤는지, 그 둘이
같은 가정에서 나온 게 아닌지. 아니면 「검산」이라 쓰지 않는다.

2026-09-04에 이 정정이 선 이유가 그거다 — **계산**(71%는 K=0.06에서만 나오는 수)과
**검색**(맵 텍스트 전수 0건)이 **각각 독립으로** 도달했다. 한쪽만이었으면
"우리가 잘못 읽었나"로 남았을 것이다.

## `UnitGrade` enum 순서는 강함 순서가 아니다 — `Tier()`가 유일한 기준

enum을 **맨 뒤에만 추가**하는 규칙(중간 삽입은 직렬화된 값을 밀어버린다) 때문에
`UnitGrade`의 선언 순서와 실제 강함이 어긋나 있다:

```
enum 인덱스        Tier()
 4 히든             4
12 특수함           4   ← enum 12지만 히든과 같은 급(희귀함 바로 위)
 6 제한됨           7
 7 초월함           8  ┐
 8 불멸의           8  │  넷이 같은 급 「초월군」 — 서로 순서가 없다
11 다른세계         8  │
 9 영원함           8  ┘
10 랜덤유닛         6   ← enum 9·11 사이인데 실제로는 제한됨보다 아래
```

**enum 인덱스로 사다리를 세우면 조용히 틀린다.** 2026-09-04에 밸런스 시뮬레이션이
`0→1→…→9→11→12` 사다리를 타서 **최고 등급 유닛을 마지막에 특수함(Tier 4)으로
「승급」시켜 7단계 떨어뜨렸고**, 「조합할수록 약해진다」는 결론이 나올 뻔했다.

**등급을 비교·정렬·승급할 때는 반드시 `UnitGradeExtensions.Tier()`를 쓴다.**
`Tier()`는 사장님이 직접 정하신 순서이고, 새 등급을 더할 때 거기 `case`를 안 넣으면
`-1`로 떨어져 연금술에 분해된다.

### 수치가 0이라고 죽은 데이터가 아니다 — 표식일 수 있다

2026-09-05에 원작 능력 `ACbh` 469개를 「발동%·배수·추가피해가 전부 0」인 287개와
실효 116개로 갈랐다. **껍데기 287개 쪽이 트리거에서 더 많이 참조된다**(21% vs 5%).

수치가 없는 게 정상이었다. **효과가 아니라 「이 유닛이 누구인가」를 판정하는 꼬리표**다
(`!흔들흔들 열매`, `!삼천대천세계`). `Gold_Plus +0.6`의 발동 조건인 `A04X`가 바로
그 「완전 껍데기」 분류에 들어 있었다 — 죽은 줄 알았던 데이터가 골드 경제의 축이었다.

**빈 값을 「죽었다」로 세기 전에 그 ID를 참조하는 곳이 있는지 본다.**
같은 실수의 다른 얼굴: 원작이 워크3 스톡 능력을 **UI 버튼 껍데기**로 재활용한 것
(`Absk` 광폭화 = 「창고로 이동」 버튼), 그리고 `Asph` 70개가 **순수 시각 이펙트**라
피해·범위·마나 필드가 아예 없는 것. **셋 다 「수치가 없다」는 점만 같고 뜻이 전부 다르다.**

## 2026-09-05: 하루에 정정이 열 번 났다 — 전부 같은 뿌리

원인이 하나씩 달라 보였는데, 갈라보니 **네 가지**뿐이었다. 아래는 그날 실제로 난 것들이고,
같은 실수를 다시 하지 않기 위해 각각에 **막는 방법**을 붙인다.

### 뿌리 ① 우리 문서를 원문 대조 없이 믿었다

| 무엇 | 실제 |
|---|---|
| 「와포루 성공 시 스토리에 450만 마법피해」를 만들라고 지시 | **원작 트리거에 피해 호출이 0건.** 툴팁만 있고 배선이 없다 |
| 「스모커 보상 5,000골드」 | 원작도 코드도 **3,000**. 문서의 오기 |
| 「와포루는 21~30라운드」 | 툴팁뿐. **트리거는 시작부터 재고에 넣고 31라운드에 뺀다** |
| 「드레스로사 12,500골드」 | 실제 지급 호출은 **10,000** |

**원작 툴팁은 원작 동작이 아니다.** 워크3 맵 제작자도 툴팁과 트리거를 따로 쓰고,
고치다 만 것이 그대로 남는다. **판정은 언제나 트리거·오브젝트 데이터 쪽이다.**

**막는 방법:** 지시문이나 커밋에 숫자나 「원작은 이렇다」가 들어가면 **근거가 문서인지 원문인지 밝힌다.**
문서면 그 항목만이라도 원문을 다시 연다. 문서는 그때의 이해고, 코드가 바뀌면 문서만 남는다.

### 뿌리 ② 전제가 폐기됐는데 그 위에 쌓은 것이 남아 있었다

「원작 수치를 우리 스케일로 옮기는 환산법」으로 도움소 값 넷을 계산했는데,
**그 계산 23분 뒤에 적 로스터가 통째로 원작값으로 교체돼 환산이 불필요해졌다.**
아무도 옛 계산을 다시 보지 않아서 **낙뢰가 42배, 독약이 69배, 미니보스 HP가 29배 작은 채로** 남았다.

**막는 방법:** 「A라서 B로 했다」를 커밋에 적을 때 **A를 검증 가능한 형태로** 적는다
(어느 파일의 어느 상수인지). 그리고 **A를 바꾸는 커밋을 할 때 B를 검색한다.**
문서는 결론을 절차보다 **위에** 쓴다 — 절차만 남으면 다음 사람이 폐기된 절차를 따라 한다.

### 뿌리 ③ 「없다」의 탐색 범위가 좁았다

| 무엇 | 실제 |
|---|---|
| `StoryRewardData`는 참조 0건이니 지워도 된다 | **같은 파일 안에 6개 파일이 쓰는 `WispReward`가 있었다.** 지우자 컴파일이 깨졌다 |
| 초월위습은 조합식 결과도 아니고 뽑기에도 없으니 획득 불가 | **씬의 `UnitPortal`이 `specificUnit`으로 지급한다.** 에셋만 봤고 `.unity`를 안 봤다 |
| `critDamageMultiplier`가 238종 전부 1.0이니 결측이다 | **설계 문서가 제시한 두 안 중 하나를 택한 것.** 채웠으면 배수가 두 번 곱해졌다 |

**막는 방법:** **「어디에도 없다」를 쓸 때 무엇을 봤는지 같이 쓴다** — 에셋만인지, 씬·프리팹까지인지,
설계 문서까지인지. 범위를 안 밝힌 「없다」는 결론이 아니라 **그 범위 안에서의 관찰**일 뿐이다.
그리고 파일을 지우기 전엔 **파일이 아니라 그 안의 심볼 단위로** 참조를 센다.

### 뿌리 ④ 「했다」가 도달을 뜻하지 않았다

- `8dccf11`이 「해적단 퀘스트 계통 **구현**」이라 적었지만 **`MapGenerator`에 진입점이 없어 씬에 아예 안 붙었다.**
- `ffa10d5`가 「**239종 값**」이라 적었지만 네 축 중 하나는 안 채워졌다.
- 폭우가 `waveCount` 필드 자체가 에셋에 없어 **3웨이브가 아니라 1회성으로** 돌고 있었다.

**막는 방법:** 커밋 메시지에 **「구현」·「완료」·「N종 값」을 쓰기 전에 셋을 확인한다** —
코드 / 데이터 / **씬에서 이어지는가**. 셋째를 못 봤으면 **「미도달」이라고 함께 적는다.**
그리고 값 대조로는 **필드가 통째로 없는 것**을 못 잡는다 — 「필드 × 에셋 격자」로 따로 훑어야 한다
(그날 폭우가 그렇게 걸렸고, 조합식 12개의 YAML 들여쓰기 깨짐도 같은 방식으로 나왔다).

### 그리고: 되돌려주는 사람이 일을 제대로 한 것이다

그날 팀원이 **「이미 됐습니다」·「원작에 없습니다」·「제 헤드라인이 틀렸습니다」**로 세 번 돌려세웠고,
세 번 다 맞았다. **지시를 받은 쪽이 착수 전에 확인하는 것이 마지막 안전망**이다 —
지시가 근거를 밝히지 않았으면 물어보고, 확인해서 다르면 그대로 보고한다.

### 뿌리 ⑤ 「원작은 몇 개인가」를 우리 것과 섞어서 셌다 (2026-09-05 추가)

특성포인트 총량을 PM이 **「시작1+구매1+스토리1 = 3개, 세이브 3개 더하면 최소 6, 어쩌면 7」**이라 말했다.
앞의 셋은 **우리 게임의 구성**이었고, 원작을 실제로 세어보니 **시작은 0개**였다
(`Trig_Start2_Actions`가 게임 시작에 `FOOD_USED=0`을 명시적으로 넣는다).
「원작 총량」을 물으면서 **우리 구성표를 그대로 원작 칸에 옮겨 적은 것**이다.

**막는 방법:** 「원작은 N개」를 말할 때 **원작에서 그 N을 어디로 세었는지**를 같이 적는다.
개수 문제는 특히 **저장소(변수)를 먼저 찾고 그 변수의 쓰기 지점을 전수로 세는 것**이 정답이다 —
특성포인트는 `PLAYER_STATE_RESOURCE_FOOD_USED`에 들어 있었고, 쓰기 41곳을 다 세니
지급 8 · 소모 27 · 초기화 6으로 딱 맞아떨어졌다. **문구(「특성」 문자열)로 세면 지급처를 놓친다.**

### 뿌리 ① 의 새 얼굴: **복제한 능력은 툴팁도 같이 복제된다** (2026-09-05 추가)

PM이 04번(보스)을 **「A153 = 발동 5% · 범위 450 · 22만×3 물리 + 85만 마법」**으로 지시했다.
전부 `A153`의 **툴팁**에 적힌 값이었고, **실데이터는 「반경 850, 아군 방어력 +10 오라」**였다.
그 툴팁은 `A0CJ`(플레이어 유닛의 !수분흡수)에서 복사돼 온 것이고, **`A125`에도 같은 문구가 그대로** 붙어 있다.

**막는 방법 — 툴팁을 의심하는 값싼 방법 둘:**
1. **같은 툴팁 문구가 두 개 이상의 능력에 붙어 있으면 복제 흔적이다.** 툴팁으로 검색해 보면 3초에 걸린다.
2. **툴팁의 숫자를 데이터에서 역으로 찾아본다.** `850000`은 세 능력에 있었지만 **전부 플레이어 능력**이었고,
   `220000`은 **능력 데이터 어디에도 없었다.** 툴팁에만 있는 숫자는 배선이 없는 숫자다.

그리고 **`base`가 답을 먼저 말해준다** — `A153`의 base는 `AHad`(Devotion Aura)였다.
**오라 계열 base에 「단일 대상 피해」 툴팁이 붙어 있으면 그 시점에 이미 모순**이다.
([[base-is-not-the-ability]]의 반대 방향 사례 — 그때는 base가 거짓말했고, 이번엔 base가 진실이었다.
공통점은 **둘 중 하나만 보고 결론 내면 틀린다**는 것.)

### 뿌리 ⑥ 커밋 경로를 **`git status`에서 뽑으면** 남의 작업을 쓸어 담는다 (2026-09-05 추가)

규칙에 「`git commit -- <파일>` 형태로만 커밋한다」가 있었는데, PM이 **그 파일 목록을
`git status --porcelain`에서 뽑았다.** 그 순간 구현담당1·3이 막 끝낸 미커밋 작업까지
목록에 들어왔고, **49개를 커밋하려던 `9f1ff34`에 238개가 들어갔다.**

데이터는 안 깨졌다(내용은 각자 만든 그대로였고 재집계도 표와 일치). **깨진 건 이력이다** —
커밋 메시지는 「PM 담당 49종」인데 실제론 세 사람 몫이 들어 있어서, 나중에 이 커밋을 보는
사람이 나머지 189개가 왜 여기 있는지 못 찾는다.

**막는 방법:** 경로 명시만으로는 부족하다. **그 경로 목록을 「내가 방금 고친 파일」에서
만들어야 한다** — 스크립트가 고친 파일을 그때 리스트로 남기고 그걸로 커밋한다.
`git status`·`git diff --name-only`는 **저장소 전체의 상태**라 멀티세션에선 내 것이 아니다.
(같은 사고의 두 번째 커밋 `a584757`은 고친 목록에서 뽑아 21개로 정확히 나갔다.)

### 곁가지: 「사거리 순」 같은 규칙이 무력해질 수 있다

같은 날 하위 4등급 100종을 「사거리 긴 쪽부터」로 가르라고 지시했는데,
**흔함 전원 30.0 · 안흔함 32.5 · 특별함 35.0 · 희귀함 37.5로 등급 안에서 값이 전부 같았다.**
기준이 상수라 아무것도 못 가르고 이름 가나다순으로 떨어졌다.
**정렬 기준을 지시하기 전에 그 필드가 실제로 갈리는지 한 번 세어볼 것.**

### 뿌리 ⑥의 후속: **파일 단위 커밋으로는 못 막는다** (2026-09-05, 같은 날 두 번째)

⑥의 교훈(「경로를 `git status`가 아니라 내가 고친 목록에서 뽑아라」)을 지켰는데도 같은 일이 또 났다.
구현담당1이 **자기가 고친 `GameHud.cs` 하나만** 커밋했는데, 그 시점 그 파일 안에
**구현담당3이 아직 커밋 안 한 6줄**이 들어 있었다.

**경로를 정확히 대도 소용없다 — 작업트리를 공유하면 「파일」이 커밋 단위이지 「내 변경」이 아니다.**
`git commit -- <파일>`은 그 파일의 **현재 내용 전부**를 담는다.

**진짜 막는 법은 git 명령이 아니라 배차다:**
**같은 파일을 두 세션에 동시에 배정하지 않는다.** 이번 건은 PM이 구현담당1에게 `GameHud`의 특성 버튼을,
구현담당3에게 `GameHud`의 툴팁 줄을 **같은 시간대에** 시켜서 났다. **PM의 배차 실수다.**

**지시 전에 확인할 것:** 지금 그 파일을 만지고 있는 사람이 있는가.
겹치면 **순서를 세우거나(먼저 끝난 뒤 다음), 한 사람에게 둘 다 준다.**
겹친 걸 나중에 알았으면 **내용이 온전한지만 확인하고 되돌리지 않는다** — 이번엔 둘 다 온전히 들어갔다.

### 뿌리 ⑦ 「없다」를 말하기 전에 **그게 어떤 형식으로 저장되는지** 볼 것 (2026-09-05 저녁)

같은 날 「비어 있다」를 세 번 잘못 말했고, 매번 다른 얼굴이었다.

**① 필드가 없다 ≠ 값이 없다.** `takesPercentDamage`가 스토리 건물 13종·미니보스 7종의
에셋에 **아예 없었다.** 값을 보는 감사는 「0이 아닌 것」만 찾아서 못 잡았고, 실제로는
**C# 기본값 `true`로 읽혀 보스가 %체력 피해를 다 맞고 있었다.**
→ **에셋에 없는 필드가 어떤 기본값으로 읽히는지, 그 기본값이 안전한지**를 따로 세라.

**② 코드가 맞다 ≠ 씬에 닿는다.** 포탈 5종이 스킨 유닛에게 `OnTriggerEnter`를 못 받았다.
둘 다 Rigidbody가 없어서 유니티가 이벤트를 안 보낸 것이다 — 코드는 완벽했다.

**③ 형식을 모르면 비었다고 읽는다.** 유니티는 **enum 리스트를 16진 바이트**로 쓴다:
```yaml
acceptedGrades: 07000000      # 07 = 7 = 초월함. 비어 있는 게 아니다
```
PM이 `- 숫자` YAML 리스트만 찾다가 「22개 전부 비었다」고 팀과 사장님에게 보고했다.
(그 시점엔 실제로 비어 있었지만, 고친 뒤에도 같은 오독으로 「여전히 비었다」고 할 뻔했다.)

**막는 방법:** 「비어 있다」·「없다」를 결론으로 쓰기 전에 **같은 파일에서 값이 들어 있는
사례를 하나 찾아 형식을 대조한다.** 못 찾으면 그 타입이 처음 쓰이는 것이므로 더 의심한다.

### 곁가지: 상수를 박지 말고 데이터에서 유도할 것 (같은 날 세 번째)

스토리존 착지 거리를 **22로 박아뒀는데**, 사거리를 재배정하자 최소 사거리가 30→22.2가 되어
**여유가 0.2로 증발했다.** 시뮬레이터의 「등급 9단계」 하드코딩, 착지 오프셋의 「존 크기 25%」와
같은 사고다. **다른 데이터가 바뀌면 같이 움직여야 하는 값은 상수로 두지 않는다** —
지금은 `MinRosterAttackRange() × 0.8`로 유도한다.

### 뿌리 ⑧ 블록을 잘랐으면 **그 안쪽 중첩 `if`까지** 내려갈 것 — 그리고 「버프 미보유」는 쿨다운이다 (2026-09-05 밤)

특성 26종의 발동 게이트를 세 번에 걸쳐 잘못 읽었다. 순서대로:

**1차** — 같은 평타 트리거 안의 `GetRandomInt` 게이트를 모두 그 유닛의 특성 스킬 것으로 읽었다
(뿌리 ⑤와 같은 「섞어 세기」). 드래곤 「160타」·센고쿠 「확률 3개」가 여기서 나왔다.
**2차** — 정정하며 트리거를 **최상위 `if` 블록 단위로** 잘랐다. 맞는 방향이었는데
**블록 안쪽의 중첩 `if`를 다시 안 봤다.** 시키는 `if A0T4==1 then if GetRandomInt(1,33)==3`이라
1/33 확률이 있는데 「능력 보유 = 게이트, 확률 없음」이 됐고, 루피는 바깥 `1/80`이 빠졌다.
**3차** — 「버프 미보유 게이트(드래곤 `B00J`·제트 `B00M`)는 우리 축에 없다」고 결론냈다.
`.w3a`를 파싱하니 `B00J`는 **「5절대쿨 드래곤」이라는 이름의 Frost Armor**였고, 같은 꼴이
**21개**(「N절대쿨 ○○」, 유일한 손잡이 `Ufa1` = 1.75~14초). 스킬이 자기에게 버프를 걸어
N초 잠그는 **쿨다운**이다 — 우리 `SkillLevel.cooldown`이 정확히 그 자리다.

**막는 방법:**
- 트리거를 블록으로 잘랐으면 **각 블록 안을 끝까지 펼쳐서** 게이트를 전부 적는다. 「게이트가 하나」라고
  결론 내기 전에 그 블록에 `GetRandomInt`·`UnitHasBuff`·`GetUnitState`가 몇 개인지 센다.
- `UnitHasBuffBJ(...)==false` 게이트를 보면 **그 버프를 주는 능력을 `.w3a`에서 먼저 찾는다.**
  이름에 「쿨」이 있거나 `AUfa`/`Ablo` 기반이면 쿨다운·지속창이지 새 축이 아니다.
- 「우리 축에 없다」는 **원작 메커니즘을 끝까지 풀어낸 뒤에만** 말한다. 버프 이름 하나만 열어봤어도
  세 번째 오독은 없었다.

**뿌리 ⑧ 덧붙임 (같은 날 밤, 리서치담당 발견)** — 게이트는 「블록 안의 `if`」에만 있지 않다. **트리거 전체 조건(`_Conditions`)이나 조건 함수(`_FuncNNNC`)**에 있으면 블록 스택을 아무리 걸어도 안 보인다 — 트리거 *실행 자체*를 막는 조건이라서다(징베 `B00B`·시라호시 `B043`·빅맘 `B074`가 그랬다). 그리고 `CreateUnit(Player(N),…)`처럼 **같은 일을 하는 다른 표기**를 스캐너가 안 잡으면 그 블록은 「비어 있다」로 읽힌다(루피). **「게이트 안이 비어 있다」는 결론 전에 `_Conditions`·조건 함수·다른 표기를 다 본 뒤에만.**

### 뿌리 ⑨ 채널을 「유닛의 능력 목록」으로 잡으면 트리거 스킬은 원리적으로 안 걸린다 (2026-09-05 밤)

1채널(능력 수치)·2채널(평타 트리거 본문의 RRD 208행)·특성 26을 다 채운 뒤에야, **평타 트리거가 `TriggerExecute`로 부르는 별도 스킬 트리거**가 세 표 어디에도 없다는 걸 알았다. **96종 유닛에 200건, 전부 상위 등급**(초월함 31·전설적인 11·불멸의 11…, 흔함~특별함 0). 유닛당 최대 5개.
원인: 채널을 「유닛이 *가진* 것」(`uabi`, 평타 트리거 본문)으로 정의해서, 「유닛이 *부르는* 것」은 정의상 밖이었다. 수치를 하나씩 정확히 옮기면서도 **채널의 정의 자체가 빠뜨린 것**은 아무도 못 봤다 — 뿌리 ③(탐색 범위가 좁았다)의 큰 판본이다.
**막는 방법:** 원작에서 「X의 전부」를 뽑을 땐 **뽑는 방향을 두 번 잡는다** — 소유자에서 내려가는 방향과, 실행/호출 그래프에서 거슬러 올라가는 방향. 두 결과의 차집합이 0이 아니면 채널 정의가 틀린 것이다.

### 뿌리 ⑩ 엔진 지식은 **가설**이다 — 맞을 때도 틀릴 때도 있고, 근거는 따로 있다 (2026-09-05 밤)

PM이 원작 피해 밑바닥 셋을 한꺼번에 의심했다. 결과가 갈렸다.

| 의심 | 결과 | 무엇이 판정했나 |
|---|---|---|
| ① 피해표 열이 한 칸 밀렸다 | **틀림 — 우리 표가 맞았다** | 맵 자신의 `war3mapSkin.txt` 방어타입 툴팁(제작자가 배수를 숫자로 적어둠). 열 후보별 대조 12/12 |
| ② `ATTACK_TYPE_NORMAL`은 Spells 행이다 | **맞음** | 맵 밖 엔진 문서. 맵으로는 못 풀었다 |
| ③ `DAMAGE_TYPE_UNIVERSAL`은 방어를 뚫는다 | **맞음, 단 단서 있음** | 같은 문서. **상성 배수는 그대로 탄다** — 「뚫는다」를 「전부 무시」로 읽으면 틀린다 |

**셋 다 「PM의 엔진 지식」에서 나왔는데 하나는 틀렸다.** ①을 그대로 믿고 `DamageTable.asset`을 고쳤으면 모든 유닛의 모든 피해가 틀린 배수를 타게 됐다. 리서치담당이 **맵 안에서 반증거리를 찾아** 막았다.

**막는 방법:**
- 엔진 지식은 **의심의 출발점**이지 결론이 아니다. 「내가 아는 엔진 동작」과 「원문 근거」를 항상 갈라 적는다.
- **맵 안을 먼저 다 뒤진다.** `war3mapSkin.txt`처럼 아무도 안 보던 파일에 제작자가 답을 적어놨다. 툴팁이 근거가 못 되는 건 「능력 설명」일 때고([[docs-are-not-evidence]]), **엔진 상수를 재정의한 표시명**은 근거가 된다.
- 맵에 정말 없으면(엔진 상수 대응 같은 것) **맵 밖 자료로 확정하고 출처를 적는다.** 「불가」로 닫지 말 것.
- 확정된 규칙은 **단서까지 옮긴다.** ③의 「상성 배수는 탄다」가 빠지면 피해가 통째로 틀어진다.

**뿌리 ⑨ 덧붙임 — 전역으로 이름을 매핑하면 재사용된 이름에서 조용히 틀린다** (2026-09-05 밤, 리서치담당 발견)
`udg_Damage_Group_Robin` 하나를 **여러 스킬이 서로 다른 반경으로 채운다.** 그룹 변수 이름을 맵 전역에서 한 번만 매핑했더니 **엉뚱한 세 번째 지점의 700**이 로빈 두 스킬(실제 525·350)에 붙었고, 같은 방식으로 **14행의 반경이 틀려 있었다.** 유닛ID·능력ID에서 밟은 함정과 같은 종류다.
→ **이름으로 값을 끌어올 땐 항상 「그 트리거 계열 안에서만」 푼다.** 전역 `setdefault`는 이 맵에서 안전하지 않다.
같은 날 잡은 형제 사고: **파이썬이 큰 수를 지수표기(`2e+06`)로 내보내 표에 56행이 들어갔다.** 정규식으로 숫자를 뽑으면 `2`만 잡혀 **200만이 2가 된다 — 예외도 안 난다.** 표를 만들 땐 `format(v,'f')`로 십진수를 강제하고, 표를 쓸 땐 자릿수를 검산한다.

### 뿌리 ⑪ 이름이 뜻이 아니다 — 레지스터·변수 하나를 보고 일반화하면 40건이 틀린다 (2026-09-05 밤, PM 정정)

거프에서 원작 `realD`가 `UnitCountBuffsExBJ`(시전자 버프 개수)인 걸 확인했다. PM이 그걸
**「`realD` = 버프개수」로 일반화해 지시문에 박았고**, 그 전제로 `SkillEffect.casterBuffCountFactor`
필드까지 만들었다. 리서치담당이 계열-지역으로 46건을 추적하니:
```
영웅 능력치(STR/INT) 12 · 캐릭터 전용 누적변수 8 · 다른 레지스터 경유 9
계열 안 대입 없음 13 · 체력·그룹수·각도 4 · 버프 개수 6   ← 6/46
```
**`realD`는 스테이지 머신의 3번 레지스터다 — 이름이지 뜻이 아니다.** 계열마다 다른 게 담긴다.
그대로 갔으면 40건에 엉뚱한 축이 붙었다.

**막는 방법:** 원작에서 **변수·레지스터·그룹·핸들 이름**을 근거로 값을 끌어올 땐, **그 이름이
어디서 대입되는지를 계열 안에서 먼저 본다.** 한 사례에서 뜻을 확인했으면 그건 **그 사례의 뜻**이지
그 이름의 뜻이 아니다. 뿌리 ⑨(전역 이름 매핑)와 같은 뿌리이고, 이쪽이 더 조용하다 —
반경은 숫자가 튀어 눈에 띄지만 **의미는 안 튄다.**

### 뿌리 ⑫ 코드에 있다고 도는 게 아니다 — **호출자가 0건이면 그 경로는 없다** (2026-09-06, 리서치담당)

「이 능력을 읽는 트리거가 둘이라 어느 쪽인지 못 정한다」로 막혀 있던 것들이, **그 트리거를 부르는
호출자를 세어보자 전부 풀렸다.** 아카이누 `A0HG`는 `Akainu_01`과 `Bustercall_Etc1`이 둘 다 읽는데
**`Bustercall_Etc1`은 맵 전체에서 호출자가 0건**(죽은 트리거)이라 경로는 하나뿐이었다.
같은 방법으로 **「닫힌 사슬」**(능력을 언급하는 계열이 하나 + 그 계열을 부르는 호출자도 하나)을 만들면
**추정이 확정이 된다.** 게이트 대응이 확정10·추정4·애매2·미대응11 → **확정19·나머지 0**으로 닫혔다.

**뿌리 ④(「했다」가 도달을 뜻하지 않는다)의 역방향이다.** 그쪽은 「우리 코드가 있어도 안 닿는다」,
이쪽은 「원작 코드가 있어도 안 돈다」.
**막는 방법:** 후보가 여럿일 때 **각 후보의 호출자 수를 먼저 센다.** 0이면 후보에서 뺀다.

### 뿌리 ⑬ 시뮬이 「안 움직였다」와 「영향이 없다」는 다르다 (2026-09-06, 구현담당2)

원작 스폰 간격이 0.65 고정인데 우리는 1.6→0.69 곡선이었다. 고치면 **화면에 동시에 존재하는
적 수가 두 배 가까이 달라진다.** 그런데 **시뮬 숫자는 하나도 안 움직인다** — `run_backlog_dt`가
라운드를 「고정 길이 동안 dps로 총 HP를 녹이는 연속 풀」로만 봐서 **스폰 간격도 동시 존재 수도
모델에 없기 때문**이다.

**§15(사거리)보다 나쁜 유형이다.** 사거리는 「못 잰다」가 눈에 보이지만, 이건 **0.00 변화를 보고
「영향 없음」으로 읽게 만든다.**
**막는 방법:** 어떤 값을 바꾸기 전에 **시뮬이 그 축을 모델하는지 먼저 확인**한다. 안 하면
「측정했더니 그대로였다」를 근거로 쓰지 말고, **문서에 「이 축은 시뮬 밖」이라고 남긴다.**

### 뿌리 ⑭ 표본이 아니라 **분포**를 세라 — 76%가 기본값이면 나머지 24%가 안 보인다 (2026-09-06 밤)

원작 피해 함수 `RRD(a, b, c, min, max, 공격타입, 피해타입)`의 **4·5번째 인자를 통째로 무시**해 왔다.
정의는 `피해 = c × GetRandomReal(min, max)`다.
```
RRD 호출 649건 중  min=max=1.00 이 497건(76.6%)  →  나머지 152건(23.4%)이 배율 ≠ 1
  난수 1.0~1.5가 86건(평균 1.25) · 1.0~2.0 18 · 1.0~3.0 7 · 1.0~4.0 1
  고정  2.58 · 3.25 · 1.85 · 0.33 · 0.12
```
**표본을 몇 개 열면 전부 `1.00, 1.00`이 나온다.** 그래서 「안 쓰는 자리」로 굳었고, 아무도 다시 안 봤다.
**우리가 옮긴 원작 피해의 4분의 1이 틀린 값이었다** — 평균 1.25면 25% 과소, 0.12짜리는 8배 과다.

**막는 방법:** 원작 함수의 인자·필드를 「안 쓰는 것」으로 판정하기 전에 **전수로 세어 분포를 본다.**
`grep`으로 몇 개 열어보는 것으로는 다수값에 가려진 소수값이 안 보인다. **「값이 몇 종류이고 각각 몇 건인가」**가
판정 근거이고, 「내가 본 것들이 다 같았다」는 근거가 아니다.

**곁가지 — 조인 키도 같은 방식으로 속는다.** 표의 `RRD순번`은 `RRD`만 센 번호가 아니라
`UnitDamageTargetBJ`(40건)·`UnitDamageTarget`(5건)까지 **파일 순서로 함께 센 번호**였다.
`RRD`만 세어 붙이면 **45행이 안 붙고 11행이 엉뚱한 곳에 붙는다.**
→ 조인한 뒤 **붙은 행 수·안 붙은 행 수를 반드시 센다.** 100%가 아니면 키가 틀린 것이다.

### 뿌리 ⑮ 매칭 단위는 **원작 유닛**이다 — 행 단위로 매칭하면 한 캐릭터가 쪼개진다 (2026-09-06 밤)

원작→우리 로스터 배정에서 **같은 구조적 실수가 두 생성기에서 각각 다른 얼굴로** 나왔다.

**얼굴 ① 조용한 드롭** (`generate_unit_skills_by_gate.py`) — 등급 안에서 `n = min(원작 수, 가용 로스터 수)`로
자르고 넘치는 원작 유닛을 **경고 없이 버렸다.** 로그는 「가용이 0일 때」만 남기게 돼 있어 「있긴 한데 모자란」
경우가 안 보였다. **원작 13유닛 · 확정 19행**이 사라져 있었다.

**얼굴 ② 중복 분산** (`generate_unit_skill_damage_effects.py`) — CSV를 **행 단위**로 순위매칭했다.
한 트리거 아래 계산식이 여러 줄이면(벤 베크만 `Trig_Unique21` = Flat 한 줄 + 대상현재체력 한 줄)
**그 줄 수만큼 서로 다른 로스터 유닛에 쪼개진다.** **32개 원작 유닛 → 77개 로스터 슬롯(평균 2.4배).**
같은 능력이 두 유닛에서 동시에 피해를 내 등급 화력이 부풀고, 한 캐릭터의 스킬이 반쪽씩 흩어진다.
「원작 < 로스터라 남는 자리를 재사용한 것」이 아니다 — **원작이 로스터보다 훨씬 많은 등급에서도 똑같이 난다.**

**막는 방법:** 원작에서 우리로 옮길 땐 **매칭 단위를 「원작 유닛 하나」로 잡는다.** 한 원작 유닛의 행 전부가
**같은 로스터 유닛에** 가고, 그 안에서 게이트별로만 나뉜다. 게이지를 공유하는 스킬들이 한 캐릭터 안에
있어야 원작 동작이 재현되기 때문이다([[engine-damage-mapping]] 게이지 공유 참고).
**그리고 배정 스크립트는 「버린 것」과 「재사용한 것」을 반드시 로그로 남긴다** — 둘 다 조용하면 안 보인다.

**뿌리 ⑥의 구체적 처방 (2026-09-06 밤, 구현담당3이 실제로 밟고 즉시 되돌린 뒤 세운 것)**
`git add <파일>`로 스테이징했더라도 **`git commit -m ... -- <파일>`로 pathspec을 한 번 더 박는다.**
`add`만 믿으면 **이미 스테이징돼 있던 남의 파일이 같이 들어간다** — 실제로 남의 미커밋 128개가 딸려 들어갔다.
**복구는 `git reset --soft HEAD~1` → `git reset`**(작업 트리를 안 건드리므로 남의 작업이 안 날아간다).
그리고 **즉시 자기 신고**한다. 오늘 이 건은 신고→복구→재커밋까지 몇 분 안에 끝났고 아무것도 안 잃었다.

**뿌리 ⑮의 세 번째 얼굴 (2026-09-06 새벽) — 생성기 셋이 전부 같은 실수를 했다**
```
generate_unit_skills_by_gate.py          원작 > 로스터  →  넘치는 원작 유닛을 조용히 드롭   13유닛 19행
generate_unit_skill_damage_effects.py    행 단위 매칭   →  한 원작이 여러 로스터로 분산     32유닛 → 77슬롯
generate_unit_ability_skills.py          행 단위 매칭   →  같은 버그                        104 uid 중 22개가 능력 2개 이상
```
2채널을 고칠 때(`ca753e0`) **1채널은 확인 안 했다.** 하나를 고치고 「같은 꼴이 다른 데도 있나」를 안 물은 것이다.
→ **같은 실수가 두 번 나오면 세 번째를 찾아라.** 그리고 **각자 고치지 말고 공통 헬퍼 한 곳으로 모아라** —
「uid 단위로 묶는다」를 세 생성기가 각자 구현하면 네 번째가 또 난다.

**곁가지 — 태깅도 「포함」이 아니라 「출처」로 하라.** 채널을 「'2차 배정' 문자열이 파일에 있으면 2채널」로
태깅했더니, **1채널과 2채널 내용이 한 파일에 쌓인 경우**를 전부 2채널로 잘못 분류했다.
**어느 문구에서 그 키를 뽑았는지**가 정답이지, 파일 어딘가에 그 문자열이 있는지가 아니다.

### 뿌리 ⑯ 라벨이 뜻하는 것과 읽히는 것이 다르면, 읽히는 대로 쓰인다 (2026-09-06 새벽)

2채널 표 86행에 `해당없음(더미채널·RRD 아님)`이라 적혀 있었다. 쓴 사람의 뜻은 **「난수 배율이 없다」**였는데,
읽는 사람에겐 **「안 봐도 되는 행」**으로 읽혔다. 그래서 아무도 안 봤다.
열어보니 **52행이 진짜 피해**였고 **최대 2,000,000(트리거 채널과 같은 자릿수)**, 등급 분포도
**희귀함 14·전설 13·랜덤전용 7·불멸 6으로 상위에 몰려** 있었다. **후반 화력의 상당 부분이 거기 있었다.**

**막는 방법:** 표에 「해당없음」·「대상 아님」·「무관」을 쓸 땐 **무엇에 대해 해당없음인지**를 같이 적는다.
`해당없음(RRD 아님)`이 아니라 **`난수배율 해당없음 / 피해 여부는 별도 판정 필요`**처럼.
**한 컬럼의 값이 다른 컬럼의 판정까지 대신하는 것처럼 읽히면 안 된다.**
그리고 **「이 행들은 안 봐도 된다」는 결론은 표를 만든 사람이 아니라 쓰는 사람이 확인한다.**

**곁가지 — 「호출자 0건이면 없다」(뿌리 ⑫)의 역은 성립하지 않는다.**
내 검색이 못 찾은 것과 원문에 없는 것은 다르다. 뿌리 ⑫는 **후보를 지울 때** 쓰는 도구이지
**「존재하지 않음」을 증명하는 도구가 아니다.** 0건이 나오면 **검색식 자체를 먼저 의심**한다.

**뿌리 ⑪의 세 번째 적용 (2026-09-06 새벽) — 축뿐 아니라 「계수」도 계열마다 뽑아라**
「영웅능력치 항은 `상수 + STR×k` 구조라 상수에 흡수해도 왜곡이 작다」고 **PM이 승인**했다.
근거는 **타시기 한 사례(`STR × 2,500`, bonus의 6~8%)**였다. 계열별로 펼치니:
```
타시기 2,500 · Akainu 5,000 · Zoro_saza1 6,000~7,500 · Jimbe 17,500 · Zoro_raven 21,000
```
**타시기만 2,500이고 나머지는 2~8배 크다.** 넷은 **스탯항이 전체의 절반을 넘어**(최대 71%)
흡수하면 **화력이 반토막** 난다. 게다가 STR은 고정값이 아니라 **도움소에서 살 수 있고 레벨로 오르는
플레이어 진행도 값**이었다.
→ **축이 같아도 계수는 다르다.** 「구조가 같으니 하나로 처리하자」 전에 **계수를 전수로 뽑는다.**
→ 그리고 **반토막 난 값을 넣느니 비워 두는 게 낫다** — 넣으면 「넣었다」고 착각하게 된다.

**곁가지 — 세 번 맞은 가설 하나 (2026-09-06)**
`udg_XXX_damage[플레이어]` 꼴의 **캐릭터 전용 실수 배열은 `GetEventDamage()` 저장소**다.
카이도 8행 · 야마토/마르코 6행 · 앞선 `ReceivedDamage` 17행이 전부 그랬다.
원작이 전역에 담아두는 이유는 **스킬이 별도 트리거에서 지연 실행되기 때문**이지 다른 값이라서가 아니다.
→ `realD = udg_어떤캐릭터_damage`를 보면 **먼저 이 가설로 확인하라.**

### 뿌리 ⑰ 「이미 있는 축」의 반대편 — **누구의 것인가**가 다르면 안 담긴다 (2026-09-06 새벽)

오늘 「축 밖으로 분류한 것이 사실 우리에 이미 있었다」가 **네 번** 나왔다
(`ReceivedDamage` 31행 · `casterBuffCountFactor` 4 · `ResearchLevel` 1 · 게이지 5).
그래서 **「이미 있는 건 아닌가」를 먼저 묻는 것이 방법론**이 됐는데, 그 방법론에 **정확히 반대되는 함정**이 있다.

**호킨스 3행**은 `UnitCountBuffsExBJ(POSITIVE, EITHER, **대상**, …)` — **대상의** 버프 개수다.
「버프 개수 비례」로 뭉뚱그렸으면 **시전자 것을 세는 `casterBuffCountFactor`에 그대로 넣었을 자리**다.
징베의 「**대상의** `AId1` 레벨」도 같은 갈래로, 우리엔 자리가 없다.

**막는 방법:** 축 이름이 같아도 **「누구의 것인가」(시전자 / 대상 / 아군 / 전역)**를 먼저 확인한다.
`GetEventDamage()`·`UnitCountBuffs`·`GetUnitAbilityLevel` 전부 **인자에 대상이 들어간다** — 그 인자를 본다.
**「이미 있다」로 회수하려는 의욕이 이 구분을 건너뛰게 만든다.** 회수는 좋지만 **잘못 회수하면 조용히 틀린다.**

**뿌리 ⑰의 곁가지 둘 (2026-09-06 새벽, 리서치담당)**

**ⓐ 「축이 없다」고 적기 전에 크기를 재라.** 루치 3행이 「세이브 축이 없어서」 축밖에 묶여 있었는데,
그 항을 계산해보니 `(1 + 0.001 × 누적클리어횟수/200)`이고 **맵 상한 300회에서도 배율 ×1.0015 — 0.15%**였다.
**무시 가능한 크기**라 나머지를 그대로 담을 수 있었다. 「축이 없다」는 **담지 못할 이유가 되기도 하고
안 되기도 한다** — 크기를 재기 전엔 모른다.

**ⓑ 「이미 있는 축 둘로 쪼개진다」가 곧 「담긴다」는 아니다.**
`상수 + (대상최대체력 − 대상현재체력) × k`는 수식으로는 `TargetMaxHpPercent(+k)` + `TargetCurrentHpPercent(−k)`로
쪼개진다. **PM이 그렇게 제안했다.** 그런데 쪼개면 안 된다:
1. **효과가 둘이면 피해가 두 번 들어가 방어가 두 번 적용된다** — 원작은 한 번이다
2. **둘째 항이 음수 피해**라 회복으로 처리될 위험이 있다
→ **축이 있어도 「적용 방식」이 다르면 결과가 달라진다.** 수식이 나뉜다고 효과를 나누지 마라.
(여기선 흡수를 골랐다 — 왜곡 4.5%는 그대로, 14%는 꼬리표.)

### 뿌리 ⑱ 생성기가 **현재 에셋 트리를 스캔해서** 배정을 정하면, 재실행 결과가 매번 다르다 (2026-09-06 새벽)

배정 스크립트들(`fill_dummy_channel_damage.py` 등)이 **원작→로스터 대응표를 매번 새로 스캔**해서 만든다.
그런데 그 스캔 대상인 에셋 트리를 **다른 세션이 계속 커밋한다.** 그래서 **같은 스크립트를 두 번 돌리면
다른 배정이 나온다.**
실제로 재실행 시 **최소 5개 uid의 배정이 흔들려 두 uid의 내용이 통째로 사라지고 한 uid가 두 파일에 중복**됐다
(커밋 전에 발견해 되돌렸다). **입력 CSV는 그대로인데 결과가 달라진 것**이다.

이건 뿌리 ⑮(매칭 단위)와 다른 축이다. ⑮는 **무엇을 묶느냐**의 문제고, 이건 **무엇을 보고 정하느냐**의 문제다.
**멱등하지 않은 생성기는 「다시 돌리면 원래대로」가 성립하지 않는다** — 되돌릴 수단이 사라진다.

**막는 방법:**
- 배정의 **입력을 파일로 고정**한다. 대응표를 한 번 만들어 **CSV로 커밋해두고**, 생성기는 **그 파일만** 읽는다.
  에셋 트리를 매번 스캔하지 않는다.
- 그 전까지는 **재실행 직전에 `git status`로 남이 무엇을 건드렸는지 확인**하고, 다른 세션이 커밋한 뒤라면
  **그냥 재실행하지 않는다.**
- **생성기를 두 번 돌려 같은 결과가 나오는지**가 그 생성기를 믿을 수 있는지의 기준이다.

**뿌리 ⑱의 형제 (2026-09-06 06:00) — 출력 파일명을 「대상」 기준으로 지으면 다대일에서 조용히 덮어쓴다**
더미 채널 배선이 파일명을 **로스터 base 기준**(`SkillData_더미채널_{base}`)으로 지었다.
그런데 **원작 uid 둘이 같은 로스터 유닛을 타겟**으로 하면(h04F 가반 · h07M 카이도 → 둘 다 불멸_신지우)
**나중 것이 앞 것을 같은 경로에 덮어쓴다.** 41개 uid를 처리했는데 **파일이 40개**였고,
**h04F(가반, 더미 750,000)가 통째로 사라져 있었다.** 커밋 시점부터 그랬다 — 레이스와 무관한 별개 버그다.
발견 계기는 **「uid 수와 파일 수가 안 맞는다」**를 세어본 것뿐이었다.

**막는 방법:** 출력 파일명은 **입력 키(uid)로 짓거나**, 한 파일에 여러 uid가 들어갈 수 있으면
**append 방식**으로 쓴다(1채널·2채널은 이미 그렇게 한다). 그리고 **생성기는 끝에 「입력 키 수 == 출력 항목 수」를
스스로 검산**해서 안 맞으면 실패시킨다. 조용히 덮어쓰는 것이 제일 나쁘다.

### 뿌리 ⑲ 「못 푼 것」과 「내 도구가 못 편 것」을 구분하라 (2026-09-06 06:00, 리서치담당)

조용히 안 된 것이었다. 괄호 균형을 세도록 고치니 전부 펴졌다.

**결과가 「원문 그대로」·「함수 이름 그대로」·「빈 칸」이면 도구를 먼저 의심하라.**
오늘 같은 꼴이 세 번 났다 — `ForGroupBJ` 콜백을 `Condition(...)`이 가로챈 것,
계산식을 110자로 자른 뒤 그 잘린 문자열을 분해한 것, 그리고 이 괄호 건이다.
**「원문에 없다」와 「내가 못 찾았다」는 다르다**(뿌리 ⑯ 곁가지와 같은 뿌리).

**그리고 이 건의 결론이 오늘 밤 마지막 큰 정정이다** — 더미 52행을 「게이트를 못 찾아 매 타 발동」으로
근사해뒀는데, 다 풀고 보니 **게이트가 없는 행은 0건**이었다. 확률 40 · 마나 게이지 4 · 그 밖 8.

**「못 찾았으니 100%로 두자」는 언제나 과다 쪽으로 틀린다** — 찾을 때까지는 **가장 낮은 후보**로 두는 게 안전하다.

**뿌리 ⑫의 반례 (2026-09-06 아침) — 이 맵은 트리거를 「이름」이 아니라 「해시테이블」로 부른다**

`SaveTriggerHandle(udg_HashAttack, '유닛ID', 0, gg_trg_XXX)`로 **해시테이블에 유닛ID로 들어 있다.**
평타마다 `LoadTriggerHandle`로 꺼내 실행된다 — **그 트리거 자체가 그 유닛의 평타 트리거였다.**

하마터면 **여섯 유닛(죠즈·조로·베이비5·루피기어서드·후지토라·카이도)의 평타 스킬을 통째로 지울 뻔했다.**

→ **「호출자 0건」을 죽은 경로로 읽기 전에 「이름 말고 다른 방식으로 불리는가」를 본다.**
   이 맵에선 `udg_HashAttack` 등록을 먼저 확인한다.
→ 뿌리 ⑫는 **후보를 지우는 도구**이지 **존재하지 않음을 증명하는 도구가 아니다.** 이번이 그 실례다.

**곁가지 — 자기 도구가 조건을 오염시킨 사례(뿌리 ⑲의 실천)**
조건 스택을 쌓을 때 `if`/`then`을 **단어 경계 없이** 잘라 **`SetUnitLifeBJ` 안의 `if`가 `if`로 잡혔다.**
「시전자체력==75.00 AND eBJ(GetAttacker(),1.00) set udg_...」라는 **말이 안 되는 조건**이 나왔는데도
표에 그대로 실렸다. `\bif\b`로 고치고 **「조건에 `set `·`call `이 섞이면 오염 신호」**라는 자가검증을 넣었다.
→ **결과 문자열이 문법적으로 말이 안 되면 도구를 의심하라.** 사람이 읽으면 1초에 보이는 것이다.

### 뿌리 ⑳ 등급이 아닌 것을 등급 사다리에 끼워 넣고, 그 사다리가 무너졌다고 며칠을 쫓았다 (2026-09-06 아침)

우리 `Tier()` 사다리에서 **T6 영원함 → T7 랜덤유닛 → T8 다른세계 → T9 초월함**이 통째로 무너져 있었다.
「우리 배정이 잘못됐다」로 보고 여러 날 원인을 찾았다. **원작 사다리엔 무너진 곳이 한 군데도 없었다.**
```
흔함 38 · 안흔함 117 · 특별함 579 · 희귀함 5,503 · 전설적인 41,178 · 변화된 46,668
영원한 56,339 · 제한됨 66,409 · 초월함 67,191 · 불멸의 127,552      ← 한 번도 안 꺾인다
```
**원인: 「랜덤전용」과 「다른세계」는 등급이 아니었다.**
- **「다른세계」는 도박 버튼 이름**이다. 그 도박(`A0OC`, 목재7, 27%)이 뽑는 rect의 14기가 **전부 「랜덤전용」**이다.
- **「랜덤전용」은 작품 밖 콜라보 카테고리**다(메구밍·나루토·이치고·뱌쿠야…). **결정적 증거: `랜덤전용[제한됨]`이 10기 있다**
  — 등급이라면 둘이 겹칠 수 없다. **카테고리 + 등급의 이중 표기**다.

**우리 순서 자체는 원작과 같았다**(`영원한 < 제한됨 < 초월함`). **등급 아닌 둘을 끼워 넣어 무너져 보였을 뿐이다.**

🚩 **2026-09-06 정정** — 처음 이 조사에 딸려 온 「우리 평타가 전 등급 0.37~0.91배로 불균일하게 낮다 ·
`RandomUnit`이 9.65배 과다 · 비율이 제각각이라 일괄 배수로 못 고친다」는 **전부 틀렸다.**
검산이 우리 `attackSpeed`(**초당 공격 횟수**)를 원작 `ua1c`(**주기**)처럼 나눠서 생긴 오류였다 —
곱했어야 했고, 필드 뜻은 `UnitData.cs:244`에 **한 줄로 적혀 있었다.**
바로잡으면 **아홉 등급이 0.93~1.06이고 우리 평타 사다리도 단조 증가**다. **평타엔 붕괴가 없다.**
→ 그러니 이 뿌리의 교훈은 **「등급 아닌 원소를 축에 넣었다」 하나**다. 비율 경고는 근거가 없다.
→ 그리고 **자기가 만든 표에도 뿌리 ⑲를 적용하라** — 「전 등급이 절반 이하」라는 **결과 자체가 이상 신호**였는데
   데이터만 의심하고 **자기 공식은 안 봤다.** 우리 코드를 안 읽고 필드 이름으로 짐작한 것이다(뿌리 ⑪의 자기 적용 실패).

**막는 방법:** 사다리·순위·등급 같은 **순서 구조를 만들 때, 그 목록의 원소가 정말 같은 종류인지 먼저 확인한다.**
「이름이 등급 자리에 적혀 있다」는 등급이라는 증거가 아니다 — 이 맵은 **카테고리·획득경로·도박이름을 같은 칸에 쓴다.**
우리는 `초월위습`에 이미 「이것은 등급이 아니다」를 해뒀다([[UnitGrade]] 주석). **같은 처리가 둘 더 필요했다.**
→ **역전·모순이 안 풀리면, 고치기 전에 「이 축에 원소가 잘못 들어와 있지 않은가」를 먼저 묻는다.**

### 뿌리 ㉑ 두 수를 나란히 놓기 전에 **각각의 단위를 적어보라** (2026-09-06 아침)

「우리 초월함 스킬이 원작의 1/3」이라는 진단으로 **처방까지 나갔다**(값을 올린다 → 실제로 2건 수정).
그런데 **원작 쪽은 「고정피해 합」(원시 값)이고 우리 쪽은 「초당 기대 피해」(DPS)**였다. **단위가 달랐다.**
같은 축으로 다시 재니 결론이 **뒤집혔다**:
```
              원작       우리
원시 합 비    1.77배    4.78배   ← 값은 오히려 우리가 2.7배 크다
DPS 비        1.79배    0.33배   ← 뒤집힘
유효 발동률   0.083 : 0.084     0.390 : 0.027   ← 14배 벌어져 있다
```
**원작은 등급이 올라도 발동률을 안 올리고 값만 올린다.** 우리는 등급이 올라갈수록 발동률이 급락한다.
→ 처방이 **「값을 올린다」에서 「게이트를 고친다」로 통째로 바뀌었다.** 값을 올렸으면 **더 벌어졌을 것**이다.

**막는 방법:** 두 수를 비교하기 전에 **각각 옆에 단위를 적는다** — 「원시 합(피해)」·「초당(피해/초)」·
「비율(무차원)」. **단위가 다른 두 수를 나란히 놓으면 어느 쪽이 크든 그럴듯한 결론이 나온다.**
그리고 그 결론은 **처방까지 그럴듯하다** — 그래서 잡기 어렵다.
곁가지: **비율이 원시와 DPS에서 크게 다르면, 그 차이 자체가 「발동 빈도」라는 숨은 축을 가리킨다.**

**뿌리 ㉑의 확장 (2026-09-06, 리서치담당) — `median(A)/median(B)`는 `median(A/B)`가 아니다**
등급별 발동률을 **집계 중앙값끼리 나눠서**(`median(DPS)/median(원시합)`) 냈더니 두 등급이 `0.083 : 0.084`로
같게 나왔고, 거기서 **「원작은 등급이 올라도 발동률을 안 올리고 값만 올린다」**는 설계 원칙을 읽어냈다.
**유닛별로 먼저 나누고 그 중앙값을 잡으니 0.144 → 0.025로 단조 감소**였다 — **정반대 설계**다.
1.7배 차이가 **없는 설계 원칙 하나를 만들어냈다.**
→ **비율은 개별 단위에서 먼저 나누고, 그다음 집계한다.** 순서를 바꾸면 다른 수가 나온다.
→ 그리고 **비교표를 낼 땐 계산 순서를 표에 적어둔다** — 「유닛별로 나눈 뒤 중앙값」인지 「중앙값끼리 나눔」인지.
곁가지: 이 프로젝트에서 같은 뿌리(비교의 축)가 **연달아 두 번** 났다(단위 혼동 → 집계 순서).
**결론이 그럴듯할수록 계산 과정을 먼저 의심하라** — 「일정하다」·「반비례다」 같은 **깔끔한 법칙이 나오면 특히.**

**뿌리 ⑭ 곁가지의 재발 (2026-09-06 오전) — 지수표기에 세 번째로 걸렸다. 이번엔 「쓰는」 쪽이 아니라 「읽는」 쪽이다**
`([-\d.]+)`로 숫자를 읽으면 **`9.5e-05`에서 `9.5`만 잡고 `e-05`를 버린다** — **95,000배 과다**로 읽힌다.
`불멸_고도현`의 `triggerChance: 9.5e-05`가 **9.50(950%)**으로 읽혀 등급 발동률이 **2.66 → 실제 1.64**로
어긋나 있었다. **리서치담당과 PM이 각자 짠 스크립트가 같은 정규식으로 같은 오류를 냈다.**
이전에 `bonus`의 `2e+06`(56행)으로 이미 한 번 물린 함정이다.
→ **숫자 정규식은 언제나 `[-+0-9.eE]+`로.** 그리고 **한 사람이 이 함정에 걸렸으면 같은 코드를 짠 다른 사람도 걸렸다** —
   교차 확인할 것. 이번엔 리서치담당이 「PM 계산도 같은 정규식이면 같은 오류가 있을 수 있다」고 먼저 알려줘서 잡혔다.

**뿌리 ⑱의 사촌 (2026-09-06, 구현담당1이 구분) — 「배정이 흔들린다」와 「읽기-쓰기 시점이 겹친다」는 다르다**
로스터 두 유닛이 **존재하지 않는 SkillData guid**를 가리키고 있었다. 처음엔 뿌리 ⑱(생성기가 라이브 스캔)으로
읽었는데, 문제의 생성기를 열어보니 **`CLAIMED_BASES` 정적 하드코딩**이라 배정 결정은 코드에 고정돼 있었다.
실제 메커니즘은 **여러 세션이 같은 로스터 파일을 동시에 읽고-고치고-쓴 시점 겹침**이었다:
```
bd1b267  guid 생성  →  c6f6bf8  그 파일 삭제  →  f6fa527  중간 시점 로스터를 스캔해 죽은 guid를 다시 참조로 남김
```
**뿌리 ⑱의 처방(대응표를 CSV로 고정)으로는 이건 안 막힌다** — 결정이 아니라 **타이밍**이 문제라서다.
→ 이건 뿌리 ⑥(커밋 경합)의 데이터판이고, **처방은 스케줄링**이다. **같은 디렉터리를 두 세션이 동시에 쓰지 않는다.**
→ 그리고 **검사기가 잡게 한다** — 「참조는 있는데 에셋이 없음」(검사 ⑥)과 그 거울인 「에셋은 있는데 아무도 안 씀」(④).
   **막지 못하면 즉시 보이게** 하는 것이 차선이다.
**원인을 한 뿌리에 밀어넣지 말 것** — 증상이 같아도 메커니즘이 다르면 처방이 다르다.

A05S                 툴팁 「20%」                                    실제 Hbh1 = 15%
A0HD !용의 발톱      툴팁 「14%」는 트리거 채널용                    ACbh 4배 크리티컬은 툴팁에 아예 없이 15%로 돈다
A17K                 툴팁 「18%」 동상                               동상
```

**`A05R`이 특히 교훈적이다.** 툴팁의 `10000`과 `0.6초`는 `Hbh3=10000`·`adur=0.6`과 **정확히 일치**한다 —
즉 그 문장은 분명히 이 능력을 설명한 것이다. **그런데 확률만 틀렸다.** 「툴팁이 이 능력을 설명하는 게 맞는가」와
「툴팁의 각 숫자가 맞는가」는 **다른 질문**이고, 앞의 것이 참이어도 뒤의 것은 거짓일 수 있다.

→ **툴팁은 「어느 필드를 보라」는 안내로만 쓴다. 값은 언제나 필드에서 읽는다.**
→ 방어타입 쪽에도 같은 게 있었다: `ARMORTIP_MEDIUM` 텍스트가 `ARMORTIP_NORMAL`과 글자까지 똑같은 복붙인데
   실제 medium 행은 전부 1.00이다.

### 뿌리 ㉓ 그물을 어디에 쳤는지가 잡히는 것을 정한다 — `uabi`에서 출발하면 **런타임 부여 능력**은 영원히 안 잡힌다 (2026-09-06 오전)

특성 「능력교체」 8건의 피해가 우리 원작 표 3종 **어디에도 0건**이었다. 「원작에 값이 없다」로 읽고
사장님께 「지어낼까요」로 올렸는데, **원작에 다 있었다.**

이유는 두 겹이다:
1. **그 능력들은 유닛의 `uabi`에 처음부터 없다.** `T_Ability_hero`가 런타임에 `UnitAddAbilityBJ`로 붙인다.
   **우리 표 3종이 전부 `uabi`에서 출발했으니 원리적으로 못 잡힌다.**
2. 붙은 뒤에도 능력ID로 grep하면 안 나온다. `A10S`는 `udg_Law_Bool[플레이어]=true`를 켜고,
   **평타 트리거가 그 전역 불리언을 보고 강화판으로 분기**한다 — **다섯 번째 채널**이다.

**오늘 하루에 같은 형태가 세 번 나왔다**: 더미 채널 52행(뿌리 ⑯) → `Hbh1`(게이트가 트리거가 아니라 능력 필드) →

→ **0건이 나오면 「없다」로 적기 전에 「내 그물이 여기 닿는가」를 먼저 적어라.**
→ **채널을 하나 새로 찾으면, 그 채널로만 세어본다.** 기존 표에 합치기 전에 규모부터 잰다 —
   8건으로 끝나는지 200건인지가 처방을 바꾼다.
→ 부수 결과: 그 8건이 부르는 **미기록 더미·소환체 10기**가 또 나왔다. **「더미 채널 52행 전수 완료」는 참이 아니었다** —
   `uabi` 밖에서 붙는 능력이 부르는 더미는 애초에 셀 수 없었다.

### 뿌리 ㉑ 세 번째 적용 (2026-09-06 오전) — **원문 한 줄을 그대로 전달하면, 받는 쪽이 단위를 잃는다**

PM이 구현담당3에게 영웅 스탯 단서를 넘기며 원문을 그대로 붙였다:

> 적을 죽일 때마다 `AddHeroXP(영웅, **1**)`가 들어가 레벨이 오르고, 이 영웅들은 **레벨당 STR +0.85**다

**원문은 틀리지 않았다.** 「경험치가 들어가 레벨이 오른다」는 맞는 문장이다. 그런데 **바로 옆에 「레벨당 +0.85」가

→ **원문을 전달할 때는 단위를 내가 적어서 붙인다.** 「`1`은 경험치 점수다. 레벨 문턱은 아직 모른다」 한 줄이면 막혔다.
→ **모르는 변환이 중간에 있으면, 그 자리를 비워 고정해 둔다.** 고친 방식이 정확히 이거다 —
   `heroXp`만 올리고 `heroLevel`은 문턱이 확정될 때까지 **0에 고정**했다. 값을 넣어도 동작이 안 바뀐다.

### 뿌리 ㉓의 규모 실측 (2026-09-06 낮) — 「전수 완료」라고 적어둔 표가 **셋 중 하나만 담고 있었다**

뿌리 ㉓(그물을 어디에 쳤는지가 잡히는 것을 정한다)을 세운 직후, 그 규모를 실제로 쟀다.

```
트리거가 생성하는 유닛 타입              1,162
그중 더미 서명(Aloc/ewsp) + 피해 확정 능력    95기
그중 DUMMY_CHANNEL_GATES.csv에 있던 것       18기
그중 빠져 있던 것                          77기  ← 우리 표의 4배
```

**우리는 그 표에 「52/52 전수 완료」라고 적어뒀다.** 52는 우리가 친 그물 안에서의 전수였고,
그물 밖이 그보다 넓었다. **「전수」는 언제나 「내 방법 안에서의 전수」다** — 그렇게 적어야 한다.

→ **「전수 완료」라고 쓸 때는 출발점을 같이 쓴다.** 「`uabi`에서 출발한 전수」와 「트리거 생성 유닛에서
   출발한 전수」는 다른 문장이고, 앞의 것만 쓰면 뒤의 것으로 읽힌다(뿌리 ⑯).
→ **누락이 밝혀지면 「그럼 이 표는 무엇의 분모였나」를 다시 묻는다.** 이번 77기는 **원작 쪽 콘텐츠**라,
   「우리가 원작보다 스킬이 과잉」이라는 02번 판단의 **분모 자체를 흔든다.** 버리기 전에 넣어야 한다 —
   **순서를 거꾸로 하면 넣을 것을 버리고 다시 넣는다.**

**그리고 이번 조사가 제대로 한 것**: 「값이 있으면 피해」로 세지 않았다.
`Owk1`(0.90)은 윈드워크 **이동속도 배율**이고 13기에서 나왔다. `Oeq1`은 감속/건물피해,
`Nst1`은 정수 카운트, `Isx1`/`Idam`은 **소환체가 든 아이템 보너스**라 그 소환체의 평타로 나간다 —
더미 채널이 아니다. **넣었으면 표가 오염됐다.** 뿌리 ⑪(이름이 뜻이 아니다)의 예방 적용 사례다.

### 뿌리 ⑩ 네 번째 (2026-09-06 낮) — 「이 필드가 무엇인가」를 알아도 **「언제 읽히는가」를 모르면 65%가 뒤집힌다**

오전에 `Hbh1 = 발동 확률`을 확정하고 그대로 옮겼다. **판정은 맞았다.** 그런데 낮에 조건이 나왔다:

```
ACbh 파생 469개의 atar 분포
  atar = none            306 (65%)   🔴 엔진 배시가 아예 안 돈다
  atar에 enemies 포함     161        ✅ 돈다
  self / none,neutral      2        사실상 안 돎
```

**규칙:**
```
1) atar에 enemies가 없으면        → ACbh는 안 돈다. Hbh1/2/3을 읽지 말 것
2) atar에 enemies 있고 Hbh1 > 0   → 그 확률로 돈다
3) atar에 enemies 있고 Hbh1 미지정 → 스톡 15%
4) atar에 enemies 있고 Hbh1 = 0   → 안 돈다 (제작자가 명시적으로 껐다)
```

**맵이 스스로 증명한다** — `atar=none`인데 값이 큰 것들은 툴팁에 그 효과가 **한 글자도 없다**:
`A0LS`(시키)는 `Hbh3=700,000`·`adur=3.0`인데 툴팁은 「비행 / 쿨타임 10% 감소」뿐이고,
`A175`의 툴팁 「3.25배 크리티컬」은 실은 **같은 유닛이 든 다른 능력 `A15N`**의 것이다.
`atar=none`인데 `Hbh1`이 0이 아닌 게 **20건** — 전부 「적혀만 있고 안 도는」 값이다.

→ **필드의 뜻을 확정했으면, 다음 질문은 언제나 「이 필드가 언제 읽히는가」다.** 뜻만 알고 옮기면
   65%가 가짜다. 이번엔 `atar`가 그 조건이었다.
→ **그리고 이미 적용한 것을 되짚어야 한다.** 오전에 `Hbh1`로 고친 값들(GATE_FIX_9 10건, 안흔함 6종)이
   전부 재검증 대상이 됐다. **규칙이 조건부로 밝혀지면, 그 규칙으로 한 작업도 조건부가 된다.**

### 뿌리 ㉔ 파일을 덮어쓰는 도중에 예외가 나면, **원본도 새 내용도 없는 상태로 남는다** (2026-09-06, 리서치담당 자기보고)

`csv.DictWriter`가 새 열 이름에서 예외를 냈는데, **그 시점에 파일은 이미 truncate되고 6행까지 써진 뒤**였다.

→ 자기보고로 잡혔다. **조용히 고치면 두 번째인 줄 몰랐을 것이다.**

### 뿌리 ㉓ 세 번째 형태 (2026-09-06 오후) — 더미가 **가진** 능력과 **도는** 능력은 다르다. 오더 스트링을 보라

같은 날 세 번 나왔다. 셋 다 「`uabi`(가진 능력)를 읽고 값을 옮겼는데, 실제로는 안 도는 것」이었다:

|---|---|---|
| 019 샹크스 `e01T` | `uabi`에 `A08D`(425,000) | **명령이 안 나가 시전 안 됨** |
| `B00M` 제트 `e03S` | 능력 둘(`A0S4` 0.6초 / `A09D` 3.0초) | 오더는 `"bloodlust"` 하나 = `A0S4`만 돎 |

### 뿌리 ㉕ 시간으로 적힌 창은 **그 게임의 공격속도에서만** 그 뜻이다 (2026-09-06 오후)

원작 제트의 「0.6초 창 안의 다음 평타가 강화된다」를 **0.6초 그대로** 옮겼더니 발동률이 **0%**가 나왔다.
우리 공격간격이 2.25초라 창이 항상 먼저 만료된다. 원작은 공격간격이 **0.21초**(연구 +210% 반영)라
그 창이 **약 3대**를 덮는다. **0.6초는 「0.6초」가 아니라 「다음 3대」를 뜻했다.**

전수했더니 같은 위험군이 **8종**이었다(`SHORT_BUFF_WINDOW_GATES.md`). 창 0.20~1.40초, 덮는 대수 1~5.

→ **창은 초가 아니라 「덮는 평타 수」로 옮긴다.** 값을 바꾸는 게 아니라 **단위를 바꿔 옮기는 것**이고,
   그 구분을 주석에 적는다.
→ ⚠️ **반대 방향의 함정도 있다.** `B06G`(비비 0.20초)는 **원작에서도** 연구 초반엔 창이 한 대도 못 덮는다(0.3회).
   우리에서 0%가 나와도 **버그가 아니라 원작 재현**이다. 「죽었으니 살리자」고 손대면 **원작보다 강해진다.**
   → **「우리에서 안 돈다」를 보면, 먼저 「원작에서는 돌았나」를 묻는다.**
→ 이건 [[we-copied-design-not-layout]]의 수치판이다 — 가져온 건 설계지 숫자가 아니다.

### 뿌리 ⑯ 네 번째 (2026-09-06 오후) — **더미 이름 접두사는 제작자 라벨이지 등급이 아니다**

미기재 더미 79행을 로스터에 붙이려는데 **23행이 매칭 실패**했다. 「로우 @ 초월함인데 로우는
전설적인까지만 있다」 같은 식이었다. **원인은 우리가 더미 이름 접두사로 주인을 잡았기 때문**이고,
부모 트리거에서 진짜 주인을 역추적하니 **미해결 0**이 됐다. **표기가 틀린 것이 10건**이었다:

```
「U희귀함 에넬 뇌신 더미」      실제 주인 h024 와이퍼          — 캐릭터가 다르다
e0F5·e0F6·e0F8 (루치 접두사)   실제 주인 h07J 캐럿 스론(변화된) — 캐릭터가 다르다
e0MT 이치고 @ 전설적인          실제 h071 랜덤전용             — 등급이 다르다
「%제한됨변화」                 「제한됨 또는 변화된」 뭉뚱그림   — 등급을 안 가른다
```

→ **더미의 주인은 이름이 아니라 부모 트리거에서 역추적한다**(`udg_HashAttack` 등록 → `Conditions`의
   `GetUnitTypeId` → 호출자 체인). CSV에 `진짜주인_유닛ID`·`진짜주인_등급`·`표기_불일치` 열이 그 결과다.
→ **접두사를 매칭 키로 쓰지 않는다.** 뿌리 ⑮(매칭 단위는 원작 유닛)와 뿌리 ⑯(라벨은 읽히는 대로
   쓰인다)이 겹치는 자리이고, 이번엔 **제작자가 붙인 라벨**이 원인이었다 — 우리 라벨만 조심하면 안 된다.

**그리고 매칭 실패를 「원작에 없다」로 읽지 않은 것이 이번 건을 살렸다.** 구현담당1이 23행을
지어내지 않고 스킵한 채 「원작에 진짜 없는 건가, 우리가 못 잡은 건가」로 올렸고, 답은 후자였다.

지목했다. 실제로는 **아예 안 돌았다.** 하루 종일 과다만 쫓다 보니(145배·700,000·12.5배)
**위험을 한 방향으로만 상상했다.** 뿌리 ㉖의 짝이다 — **과소도 보라**는 규칙을 세운 당사자가
바로 다음 판단에서 또 과다 쪽으로 기울었다.

### 뿌리 ㉑ 네 번째 (2026-09-06 밤) — **「원작에서 높다」와 「원작보다 높다」는 다른 집합이다**

02번 「심하게 어긋난 등급만 깎아라」를 판정하는데, 리서치담당이 **원작 자기 등급들 사이의 밀도 순위**
(영원한 4.33 > 불멸의 2.94 > …)를 「심한 다섯」으로 냈다. **그건 어긋남이 아니라 원작의 분포다.**

```
원작 영원한 4.33 (1위)  ·  우리도 높다      → 어긋남 0. 깎을 대상이 아니다
원작 안흔함 0.29 (하위)  ·  우리가 1.0      → 3배 넘게 어긋났다. 순위엔 안 잡힌다
```

→ **차이를 물었으면 차이를 계산해야 한다.** 한쪽 표의 순위는 답이 아니다.
→ **그리고 두 표는 같은 규칙으로 세어져야 한다** — 원작은 「한 스킬 = 한 능력」으로 셌는데
   우리 표는 스킬 에셋 개수다. 축이 다르면 뺄셈 자체가 무의미하다.
→ 오늘 아침 PM이 방법 A와 방법 B를 나란히 놓고 틀린 처방을 낸 것과 **완전히 같은 형태**다.
   **네 번째다.** 이 함정은 사람을 가리지 않는다.

### 뿌리 ㉘ `description`은 사람이 읽는 설명이자 기계가 파싱하는 데이터다 — **설명이 데이터로 읽힌다** (2026-09-06 밤)

구현담당1이 쪼개기 결과 파일에 안내문을 넣었다:

> `PM 설계 결정 — 원작 능력 하나=파일 하나`

이 문장이 **검사기 ①의 「`원작 X(...)`」 패턴에 걸려**, 서로 다른 로스터 두 곳이 **가짜로 「같은 원작 유닛을 공유한다」**로 잡혔다. 데이터는 멀쩡했고 **설명 문구가 데이터로 파싱된 것**이다.

우리는 지금까지 **「라벨이 뜻과 다르다」**를 다섯 번 물렸다(더미 접두사 · `해당없음` 표기 · 파일명 등급 · `skillName` · 오더 수신자). **이건 그 반대편이다 — 라벨이 아닌 것이 라벨로 읽혔다.**

근본 원인은 `description` 하나가 **두 역할을 겸하는 것**이다. 사람에게는 서술이고 도구에게는 구조화된 데이터다.

→ **`description`에 설명을 쓸 때 데이터 패턴을 흉내 내지 않는다** — `원작 …(…)` · `· AXXX: 발동Y` · `더미 경로 …` 같은 꼴.
→ 장기적으로는 **설명과 데이터를 다른 필드로 가르는 게 맞다.** 지금은 규모가 커서 안 한다.
→ **가짜 양성을 「검사기가 틀렸다」로 넘기지 않은 것**이 이번 건을 살렸다. 원인을 찾아 문구를 고쳤고,
   그래서 검사기는 그대로 유효하다. **검사기가 틀린 것과 입력이 틀린 것은 다르다.**

확신도 낮음 6건의 값이 **4.0과 0.5**인데 **트리거 배수로도 흔한 값**이라, 한꺼번에 지웠으면
**멀쩡한 값을 죽였을 것**이다. **「같은 판정이라도 확신도가 다르면 처방이 다르다.」**

### 뿌리 ㉚ **라벨이 맞는데 데이터가 안 따라온 것** — 검사기도 못 잡는다 (2026-09-06 밤)

영웅 스탯을 켜려고 「스탯 비례로 배선된 3행」을 찾았는데, **그 3행의 `description`엔 `GetHeroStatBJ`가
적혀 있었지만 실제 `effects`는 여전히 `basis = Flat`**이었다. 상수만 들어 있었다.

**PM도 구현담당3도 그 3행을 「배선됨」으로 세고 있었다.** 설명을 읽고 센 것이다.

**오늘 라벨 사고가 여섯 번 났는데 다섯은 「라벨이 틀렸다」였다**(더미 접두사 · `해당없음` 표기 ·
파일명 등급 · `skillName` · 오더 수신자). **이건 여섯 번째이자 다른 종류다 — 라벨은 맞고 데이터가 안 따라왔다.**

**그래서 가장 조용하다.** 검사기가 못 잡는다 — `description`도 정상이고 `effects`도 형식상 정상이라
어느 불변식도 안 깨진다. **둘을 대조해야만 보인다.**

→ **「무엇이 되어 있나」를 셀 때는 설명이 아니라 데이터를 센다.** 설명은 의도이고 데이터가 사실이다.
→ **원작 축을 언급한 `description`과 실제 `basis`/`triggerType`을 대조하는 검사**를 넣을 값어치가 있다.
   (이번에 전수해보니 다른 사례는 0건이었다 — 그래도 다음에 또 생긴다.)
→ 뿌리 ㉘의 짝이다. ㉘은 **설명이 데이터로 읽힌 것**, ㉚은 **설명만 있고 데이터가 없는 것**.
   같은 뿌리에서 나온다 — **`description` 하나가 서술과 데이터를 겸한다.**

**같이 기록 — 효과를 쪼개도 되는 조건이 이번에 일반화됐다.**
예전에 「상수 + (최대체력−현재체력)×k」를 두 효과로 쪼개려다 철회했고, 이번엔 타시기의
「받은피해×3.75 + STR×2500」을 쪼갰는데 **이번 건은 안전하다.** 기준은 「AP라서」가 아니다:

> **시전자에서 대상까지 가는 모든 단계가 곱셈이거나 아예 없으면 쪼개도 된다.**
> 덧셈이나 정액 감산이 하나라도 끼면 안 된다.

타시기는 `AP + 스킬 피해`라 **방어 감산 단계가 원천적으로 없고**, 상성표와 `PercentDamageTaken`은
같은 대상이라 같은 상수라 `A×m + B×m = (A+B)×m`으로 분배된다.

### 뿌리 ㉜ **「축이 있는가」와 「축이 제대로 연결됐는가」는 다른 질문이다** (2026-09-06 밤)

하루에 세 번 나왔다. 셋 다 **축은 있었고 연결이 틀렸다.**

| 사례 | 축은 | 연결은 |
|---|---|---|
| `ResearchLevel` | `basis`에 있고 자산 9건이 쓴다 | `CountResearchLevel()`이 **하드코딩 `0` 스텁** → 상수항만 나갔다 |
| `A11S`(대상 피해 배율) | `percentDamageTaken`으로 **이미 보편 적용** 중 | 자산 13건이 계수를 값에 **baked** → **이중 적용**(`0.25×0.90=0.225`, 원작 `0.90`) |

**셋 다 「우리에 그 축이 없다」고 적힌 문서를 믿고 새로 만들려다 발견됐다.** 그리고 **세 번째가 가장 나쁘다** —
한 사고가 **양방향**으로 벌어져 있었다. 공속은 과소, 공격력은 과다. **어느 한쪽만 재면 정상으로 보인다.**

→ **「축이 없다」를 확인할 때 세 곳을 다 봐야 한다**: ⓐ 필드가 있는가 ⓑ 값이 채워져 있는가
   ⓒ **그 값을 읽는 코드가 그 값을 원래 자리에 쓰는가**. ⓒ가 오늘 세 번 다 문제였다.
→ **필드 이름이 용도를 보증하지 않는다**(뿌리 ⑯의 코드판). `statLevel1Multiplier`가 「공격력 배율」이라고
   적혀 있었지만 담긴 건 공속이었다.
→ ⚠️ **직렬화 필드 이름을 고쳐서 바로잡으려 하지 말 것.** 이름이 곧 직렬화 키라 **채워진 값이 전부 날아간다.**
   `[FormerlySerializedAs]`를 쓰거나, **이름은 두고 주석·문서를 고친다.**
→ ⚠️ **의미도 확인한다.** 원작 `gba1 = 2.10`은 「**+210%**」라 실제 배수는 `1 + 2.10 = 3.10`이다.
   그냥 곱하면 **연구 0단계에서 이미 2.1배**가 된다 — 뿌리 ㉑(단위)의 여섯 번째가 될 뻔했다.

**검산 하나가 이 종류를 다 잡는다**: **「축을 끄면(레벨 0·연구 0) 지금과 똑같은가」.**
같지 않으면 연결이 틀린 것이다.

**막은 방법도 기록해 둔다**: 「값이 어디에도 없다」는 보고를 받고 **PM이 `grep` 한 줄**을 돌렸다.

### 뿌리 ㉝ **측정 도구가 런타임과 다른 가정을 쓰면, 런타임 버그를 못 본다** (2026-09-06 오후)

오늘 축 넷이 잘못 연결돼 있었다(뿌리 ㉜). **그런데 하나도 시뮬레이터가 찾아주지 않았다:**

```
A11S 이중 적용     새 필드를 만들려다 코드를 읽고 발견
공속 오배선        만들기 전에 데이터를 다시 보다 발견

**넷 다 손으로 읽어서 찾았다.**

**`ResearchLevel` 건이 이유를 보여준다** — `simulate_balance.py`의 `skill_dps_for_unit`이 그 축을
**원래부터 「연구 0단계」로 고정 가정**해왔다. 그래서 낮 동안 런타임에서 **최대 21배**로 돌던 버그가
**시뮬레이터 출력엔 델타가 0**이었다. **런타임 버그였지 시뮬 버그가 아니었다.**

**즉 우리 유일한 측정 도구가 그 버그를 구조적으로 못 봤고, 우리는 그 도구로 며칠째 밸런스를 판단했다.**

   **그 가정이 지금도 정당한지**를 함께. 고치는 것과 별개로 **알고 쓰는 것과 모르고 쓰는 것은 다르다.**
→ ⚠️ **한때 정당했다가 지금은 아닌 가정**이 가장 위험하다. 「연구 0 고정」이 정확히 그랬다 —
   그 축이 없을 땐 정당한 바닥값이었고, **축이 생긴 순간 편향이 됐는데 아무도 다시 안 물었다.**
→ **측정이 정상으로 나오는 것은 「정상이다」의 증거가 아니다.** 도구가 그 축을 안 볼 수도 있다.

**같이 기록 — 오늘 넷을 찾아낸 실제 방법은 「만들기 전에 이미 있는지 확인한 것」이었다.**
셋은 새 필드·새 축을 만들려다 발견했다(뿌리 ㉛). **만들려는 순간이 가장 잘 보이는 순간이다** —
그때만 「이게 정말 없나」를 진지하게 확인하기 때문이다.

### 뿌리 ⑭ 세 번째 (2026-09-06 밤) — 숫자 정규식이 이번엔 **음수**를 놓쳤다

`multiplier: ([\d.]+)` 가 **`-0.2`에서 부호를 못 잡아 `0.2`로 읽었다.** 그래서
「그 능력의 값은 효과 목록에 안 들어갔다」는 **틀린 일반화**가 문서에 실렸고,
같은 건을 두 문서가 정반대로 판정하게 됐다(「전부 제거」 대 「전부 유지」).

**뿌리 ⑭에 이미 처방이 적혀 있었다** — **「숫자 정규식은 언제나 `[-+0-9.eE]+`로」**.
그때는 지수표기(`9.5e-05` → `9.5`, 95,000배)였고 이번은 음수인데, **그 패턴을 썼으면 둘 다 잡혔다.**

→ **`[\d.]+`를 쓰지 마라.** 게임 데이터의 숫자는 **음수·지수표기·부호**가 다 나온다.
→ 세 번째다. **규칙이 있는데 안 쓰였다** — 규칙을 세운 사람이 다음 스크립트에서 또 `[\d.]+`를 썼다.

### 뿌리 ㉟ **판정 단위가 파일이 아니라 효과다** (2026-09-06 밤)

「이 능력은 피해가 아니다」는 판정을 **파일 단위로 적용하면 멀쩡한 값이 같이 죽는다.**

한 파일에 **여러 트리거에서 온 효과가 섞여** 있다. `A0W6`(전설적인_엄태웅)이 그 예다:
```
multiplier 목록:  325000 · 325000 · -0.42
                  └── Trig_Legend25의 확정 RRD    └── A0W6(Oae1, 이동속도 감소)
```
**「`A0W6`은 피해 아님 → 이 파일 제거」로 밀었으면 확정값 325,000×2가 같이 날아갔다.**

→ **`effects` 목록에서 그 능력 고유의 필드값과 정확히 일치하는 항목만 골라 지운다.**
   같은 파일의 다른 항목은 그대로 둔다.
→ 이번 5건은 **전부 음수**였다 — 그 능력의 비피해 필드값(방어력·이동속도 감소)이
   `multiplier` 자리에 그대로 박혀 있었다. **음수가 보이면 피해가 아닐 확률이 높다.**
→ **「어긋나면 멈춘다」가 또 옳았다.** 두 문서가 정반대였고 **둘 다 절반만 맞았다** —
   기계적으로 한쪽을 따랐으면 어느 쪽이든 틀렸다.

### 뿌리 ㊱ **요약 라벨과 상세 분석이 갈리면, 이긴 쪽은 언제나 상세다** (2026-09-06 밤)

같은 조사 문서 안에서 **이름표와 본문이 정반대**를 가리키고 있었다.

```
BOOLEAN_FLAG_CHANNEL.md 요약 라벨   「등급 해금 플래그」        → 켜지면 열린다
BALANCE_RESEARCH.md 상세 트리거 분석 「하나 쓰면 나머지가 막힌다」 → 켜지면 잠긴다
```

**두 해석은 게임 설계가 통째로 갈리는 차이였다** — 상위 3등급을 「여러 기 보유 가능」으로
볼 것인가 「플레이어당 평생 1기」로 볼 것인가. 밸런스 결론 전부가 그 위에 서 있었다.

원문(`war3map.j`)이 상세 쪽 손을 들었다:
```jass
if(not(udg_Tech_Onedill[GetConvertedPlayerId(GetTriggerPlayer())]==false))then
return false
endif
```
**`not(flag==false)` = `flag==true`일 때 발동 거부.** 46개 트리거가 토씨 하나 안 틀리고
같은 형태였고, 각자의 `Actions`가 성공 분기에서 같은 플래그를 `true`로 세운다 —
**46개가 서로를 잠그는 플레이어당 슬롯 1개.**

→ **이중부정 조건을 눈으로 풀지 말고 손으로 풀어라.** `not(x==false)`는 읽는 순간
   「false면 통과」로 잘못 잡힌다. 실제로는 정반대다. 극성이 결론을 뒤집는 자리에서는
   **참값 두 개를 다 대입해보고** 넘어간다.
→ **라벨은 근거가 아니다.** 「해금 플래그」라는 이름은 조사자가 붙인 요약이지 원문이
   말한 게 아니었다. 뿌리 ㉚(라벨은 맞는데 데이터가 안 따라왔다)의 거울상이다 —
   이번엔 **데이터가 맞고 라벨이 틀렸다.**
→ **우리 포트 코드는 원작의 증거가 될 수 없다.** 「우리 `ChatUnlockManager.cs`에
   되돌리는 곳이 0곳」은 근거로 제출됐지만, 그 코드는 같은 문서를 읽고 짠 것이라
   **같은 문서를 두 번 센 것**이다. 순환이다. 원작 질문의 답은 원작에만 있다.
→ **개수가 같다는 사실은 방향을 말해주지 않는다.** 「켜는 곳 46 = 읽는 곳 46」은
   제한으로도 해금으로도 똑같이 읽힌다. 갈라준 건 **극성 한 줄**이었다.
